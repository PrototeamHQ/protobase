A **resource** describes one table of a database you already have: its columns as fields, its key, and the rules around it. It is plain TypeScript in `config/<resource>/data.ts`, exported from `config/index.ts`; [`protobase scaffold`](/reference/cli/#scaffold) writes a first version from the database. Every example on this page is a file in the repository that CI typechecks and tests.

## resource()

| | |
| --- | --- |
| [`resource(name)`](/api/schema/functions/resource/) | The name is the resource's address (`/api/v1/<name>`, `/<name>` in the admin) and how other config refers to it. It may not contain `/`, `:`, `?` or `#`, and must be unique. |
| `.table('schema.table')` | The table, with or without its schema. Required. |
| `.fields({ ... })` | The columns, by field name. `name: null` ignores a column on purpose (scaffold writes it, so it does not offer the column again). Required. |
| `.primaryKey((r) => r.id)` | The key, one field or a list (`(r) => [r.order_id, r.line_no]`). Required; records are addressed by it. |
| `.softDelete((r) => r.deleted_at)` | A nullable timestamp or date: deleting sets it, lists leave such rows out, `:undelete` clears it. See [REST API](/reference/api/#routes). |
| `.tenant((r) => r.organization_id, { across? })` | The column that separates tenants: every query is limited to the caller's tenant, creates set it, and a request body may not. With `across: 'memberships'`, lists read every organization the person is a member of, each with their role there; see [Lists across organizations](/reference/access/#lists-across-organizations). |
| `.owner((r) => r.owner_id)` | The field holding the owning user's id, which `.own` and `.team` capabilities filter on (see [Access](#access)). The server does not start when its column cannot hold the signed-in users' ids, such as an integer column with Better Auth's text ids; see [user ids](/reference/auth/#roles-and-access-in-the-api). |
| `.author((r) => r.author_id)` | The field holding the id of the user who created the record, such as a chat message's sender: every create sets it to the signed-in user's id, and no request may write it, so a body that names it is refused as read-only. A create by no one signed in, through a [public form](/reference/forms/), leaves it empty. Its column is checked at startup as an owner's is. |
| `.search((r) => [r.number, r.name])` | The fields that `search("...")` and bare words in a filter match, and what the admin's [global search](/reference/client/#global-search) looks in. Every word of the text must appear in one of them, ignoring case, and part of a word is enough: `port` finds "Portfolio". `r.phone.digitsEnd()` matches only the end of a field's digits instead, ignoring spaces, `+` and dashes, and only words written like phone numbers: `9623`, `47069623` and `+31 6 47069623` find "+31 6 47069623", `4706` and `+316` do not. Each field needs a pg_trgm index (`using gin (name gin_trgm_ops)`), a `digitsEnd` one on `regexp_replace(phone, '[^0-9]', '', 'g')`, or the API refuses the search. |
| `.position((r) => r.position, { within?, after? })` | The integer field holding the records' order by hand, 1 the first, which a list's **Reorder** button changes by dragging; with `within: (r) => r.invoice_id`, a filterable relation, each parent's records have an order of their own, sorted in its related section; with `after`, a record never ranks above the records it depends on. The field must be sortable. See [Reordering by hand](/reference/ui-config/#reordering-by-hand) and [Ranked after what they depend on](/reference/ui-config/#ranked-after-what-they-depend-on). |
| `.parent((r) => r.vm_id, 'update')` | The relation whose record each record belongs to, and the access on it (`'read'` or `'update'`) that creating, changing, deleting and undeleting a record needs, checked with the caller's own rules on that resource. With `'read'`, every read of its records also keeps to those whose parent the caller reads. The relation is one column, to a resource with a key of one field. See [Records that belong to another](/reference/access/#records-that-belong-to-another). |
| `.openExisting((r) => [r.organization_id, r.member_key])` | A unique key of the table whose conflict on create opens the record already holding those values, such as a direct message with the same members. See [Opening an existing record](#opening-an-existing-record). |
| `.validate((record) => issues)` | A rule over the whole record, run after the field checks on every create and update. It returns `[{ field, message }]` or `undefined`; issues answer `400` with the field named. |
| `.access({ ... })` | Rules per operation. See [Access](#access). |
| `.events((e, r) => [...])` | What changes of its records mean, such as `orders.created`, captured in the database for every write. See [Events](/reference/events/). |
| `.history()` | Keeps every change of its records with who made it, shown on the record page and listed for admins as Activity. See [Record history](/reference/history/). |
| `.comments()` | Lets whoever may read a record comment on it and @mention others who may, who are emailed; shown on the record page and listed for admins. See [Record comments](/reference/comments/). |

Field and resource names are snake_case by convention, like the columns: they are the names in URLs, the API, filters and sorts as written (`/stock_moves?order_by=moved_at desc`). The column is the snake_case of the name unless `.column()` says otherwise, so a camelCase name such as `movedAt` maps to `moved_at` too. [`protobase scaffold`](/reference/cli/#scaffold) writes snake_case names, and the built-in resources, such as `failed_jobs` and `webhook_subscriptions`, have them too. Nothing checks the convention: a resource or field may have any name.

## Field options

Every option returns a new [field](/api/schema/interfaces/field/), so they chain in any order.

| Option | Effect |
| --- | --- |
| `.optional()` | The column is nullable; the value may be `null`. |
| `.readOnly()` | Never written through the API: ids, computed columns, audit timestamps. |
| `.default(value)` | The value a create uses when none is given; the admin's create form shows it. |
| `.dbDefault()` | The database supplies a value when none is given (identity, `now()`, a sequence). |
| `.filterable()` | May appear in `filter`, in filter widgets and in `Stat`/`Table` filters. It needs an index: the API refuses a filter on a column no index serves (see the [scan guard](/reference/api/#safety)), and [`protobase doctor`](/reference/cli/#doctor) fails without one. |
| `.sortable()` | May appear in `order_by` and in sorts. It needs a btree index that serves it alone, as a filterable field does, since a list may be sorted by it. A list's header of a field without it is no button and says "This column can't be sorted" on hover and in its menu. |
| `.alias(...names)` | Other names filters may use for the field. |
| `.column('name')` | The column, when it is not the snake_case of the field name (`'EMP_NAME'`). |
| `.access({ read, create, update })` | Role rules for this column. See [Access](#access). |
| `.sensitive()` | Hidden like a password: no response carries it, and a caller who may read it reveals one record's value at a time. See [Sensitive fields](#sensitive-fields). |
| `.encrypted()` | Sensitive, and stored encrypted with the app's own key, so the database only ever holds ciphertext. Text only. See [Encrypted fields](#encrypted-fields). |
| `.strongSignIn({ minutes })` | Sensitive, and revealed only after a passkey or a second step in the last `minutes` (15 by default). See [Recent strong sign-in](#recent-strong-sign-in). |
| `.ai({ prompt })` | A job fills the field from `prompt`, `{field}` replaced by the record's values, after a create and after an update of a field the prompt reads, as the user who wrote. Text or enum, optional. See [AI fields and actions](/reference/ai/). |
| `.rollup({ from, via, fn, field })` | The database keeps the field from the records of another resource: their count, sum, average, least or greatest value. Read-only. See [Rollups and formulas](#rollups-and-formulas). |
| `.formula(expression)` | The database computes the field from the record's other number fields, as a generated column. Read-only. See [Rollups and formulas](#rollups-and-formulas). |

## Rollups and formulas

:::caution[Beta]
Not yet:

- <gap>A rollup over its own table is not supported yet.</gap>
- <gap>A rollup on a resource with a key of several columns is not supported yet.</gap>
- <gap>A rollup through a relation of several columns is not supported yet.</gap>
:::

A **rollup** is a value of the other records that point at a record, such as an order's total of its lines. A **formula** is a value computed from the record's own fields, such as a line's amount. Neither needs SQL: you declare the field, and [`protobase migration`](/reference/cli/#migration) writes its column into the project's next migration (`NNN_computed.sql`). Both are real columns, kept by the database in the transaction that writes, so they are right for writes from psql or other services too, and they filter and sort like any column once they have an index.

<Code code={rollups} lang="ts" title="docs-examples/reference/rollups.ts" />

`.rollup({ from, via, fn, field })` reads the records of resource `from` whose relation field `via` points at the record. They are the records that are not soft deleted, when `from` has soft delete.

| `fn` | Value | Field |
| --- | --- | --- |
| `count` | How many records there are; with `field`, how many have a value for it. 0 without records. | `f.integer()` or `f.bigint()` |
| `sum` | The sum of `field`. 0 without records. | a number field |
| `avg` | The average of `field`. Empty without records. | `f.decimal()`, `.optional()` |
| `min`, `max` | The least or greatest value of `field`. Empty without records. | a number field, `.optional()` |

Empty values of `field` are left out, as in SQL. The migration adds the column, a function in the `rollups` schema and a trigger on `from`'s table that sets the value after every insert, delete and update of the columns it reads, and then sets every record's value once. <gap>A rollup over its own table is not supported yet.</gap> <gap>A rollup on a resource with a key of several columns is not supported yet.</gap> <gap>A rollup through a relation of several columns is not supported yet.</gap>

`.formula(expression)` is a Postgres generated column. The expression reads the record's number fields, and takes numbers, `+ - * /`, parentheses, `coalesce(a, b, ...)` and `round(x)` or `round(x, digits)`. It is computed exactly as decimals, so `7 / 2` is 3.5, and is stored as the field's type, so an integer field rounds the result. A formula that reads an optional field is `.optional()` too, unless `coalesce()` gives that field a value. A formula cannot read another formula. When the expression changes, the migration drops the column and adds it again, so an index on it must be created again in the same migration.

Neither field can be written through the API, have a default, or be sensitive, an AI field, a file, or the key, tenant, owner or soft delete field, and a formula cannot read a sensitive field. The server does not start while a declared column, function or trigger is missing or out of date, with a message that names the fields; the migration fixes that. It stops with an error, without writing anything, when the column already exists as the project's own: a plain column where a formula is declared, a generated column it did not write, or a rollup column of another type.

## Sensitive fields

A sensitive field, such as a bank account number, is written like any other field but never read with the record: lists, gets, `:search`, `:seek`, create and update responses and batch results leave it out, and it cannot be filtered, sorted, searched, counted or picked with `fields`. The record page shows it masked, with an eye button. Showing it asks the server for that one value with `POST /{resource}/{key}:reveal` (see [REST API](/reference/api/#sensitive-fields-and-audit)), which needs the same access as reading the record and the field, inside the caller's tenant, and publishes an audit event before it answers.

```ts
iban: f.text().sensitive().access({ read: roles.can('screening.read') }),
```

A role may also set a sensitive field it cannot read, such as a sealed value only a worker reads, when the field's own `create` or `update` rule allows it: see [write-only fields](/reference/access/#write-only-fields).

A sensitive field cannot be `.filterable()`, `.sortable()`, aliased, searched, or the key, tenant, owner or soft delete field, and a view may only put it in a record page section: in a list, filter, chart, sidebar, title, recent-record group or action it would always be empty, so the config fails to load.

A [webhook subscription](/reference/webhooks/) delivering `as` a role runs that role's access rules on a captured change, which holds no sensitive field. A rule or row filter that reads one there throws, and the change is kept as failed for that subscription instead of delivered, so decide that access on a field that is not sensitive. A rule that reads the field before it checks the role, such as `record.api_secret == null || ctx.user.roles.includes('admin')`, fails even for `as: { roles: ['admin'] }`: check the role first, as in `ctx.user.roles.includes('admin') || ...`.

### Recent strong sign-in

A field such as a recovery code or an API secret can ask for more than read access: `.strongSignIn()` reveals it only to someone whose sign-in proved a passkey or a second step in the last 15 minutes, or `minutes` you give. It is sensitive too, so all of the above applies, and `/meta` marks it `strongSignIn: { minutes }`.

```ts
recoveryCode: f.text().encrypted().strongSignIn({ minutes: 10 }),
```

Without such a sign-in, the reveal is refused with `403` `strong-sign-in-required` and the number of minutes, before anything is decrypted or audited. The record page then asks the person to confirm it's them, with a passkey or the code of their authenticator app, whichever their account has, and shows the value once they did. A passkey sign-in counts, as does a password or emailed code followed by the [second step](/reference/auth/#two-factor-authentication); confirming later counts from then. Staff [signed in as someone](/reference/auth/#staff-sign-in) and an outside app acting as them, such as an MCP client, never count: they proved nothing as the person. See [Recent strong sign-in](/reference/auth/#recent-strong-sign-in) for how the server knows.

### Computed reveals

:::caution[Beta]
The record page does not show computed reveals yet: an app's own component reveals them with the client's `reveal`.
:::

Some secrets are not in the app's database, such as an API key another service keeps, or are built from several values, such as a file of settings. `.reveals()` names values revealed like a sensitive field but made when one is asked for:

```ts
resource('apps')
  // ...fields, key and tenant
  .reveals({
    env: {
      value: (app, caller) => secrets.envFile(app.id),
      read: roles.is('owner'),
      strongSignIn: { minutes: 15 },
    },
  })
```

`POST /apps/{key}:reveal` with `{ "field": "env" }` reads the record as a get does, inside the caller's tenant, row filter and record rules, so a record they cannot read is a `404`. `value` gets the record with every field the caller may read but the sensitive ones, and the caller's user and organization; its answer is the value, `null` when it returns nothing. `read` is a role rule like a field's own read rule, and a caller it leaves out gets `400` as for an unknown field. `strongSignIn` asks for a [recent strong sign-in](#recent-strong-sign-in), 15 minutes when it names no minutes. Each reveal publishes the same audit event as a field's, with the reveal's name as `field`, before the value is returned. A reveal cannot have the name of a field of its resource.

## Encrypted fields

An encrypted field is a [sensitive field](#sensitive-fields) whose value the server encrypts before it reaches the database, so a dump, a backup, a replica, a realtime subscriber or anyone running SQL sees only ciphertext. Only its reveal decrypts it, for a caller who may read the record and the field, and your own [jobs and functions](#reading-in-jobs-and-functions) on the server; every read is audited. Every API write encrypts it: the record form, REST, batches, imports, [public forms](/reference/forms/) and `records` in [API functions](/guides/api-functions/). The [Supabase-compatible REST API](/reference/supabase-rest/#encrypted-fields) refuses to write or filter it.

```ts
api_key: f.text().encrypted().access({ read: roles.can('keys.read') }),
```

It takes `f.text()` only, and cannot be `.readOnly()` or have a `.dbDefault()`. Its column must be `text`, with no length, pattern or unique constraint, index, default, trigger or generated column reading it: the database only ever sees ciphertext.

**Write it only through the API.** SQL of your own, in an API function's `db`, a write hook's transaction or the assistant's approved changes, stores the value unencrypted, and its reveal then fails until [`protobase encryption apply`](/reference/cli/#encryption-apply) encrypts it.

**Your code never sees the stored value, only whether it is set.** Access rules cannot filter on it: a rule that returns a filter on it fails the request. Record rules, validators and write hooks get a stored record with a set value as `encrypted` (exported from `@protobase/schema`) and an empty one as `null`. Check whether it is set with `== null`; the marker is never equal to anything, so a rule comparing it with a constant decides as if it held another value, and reading it as text throws. A [webhook subscription's access check](#sensitive-fields) cannot know whether it is set, as for every sensitive field. Rules and validators see the plaintext only where a write gives it, so a validator written this way checks each value written and leaves a stored one alone:

```ts
.validate((r) => (typeof r.iban === 'string' && !r.iban.startsWith('NL') ? [{ field: 'iban', message: 'A Dutch IBAN' }] : undefined))
```

When you change a `.sensitive()` field to `.encrypted()`, change every rule, validator and hook that reads its stored value: from then on it gets `encrypted`, and TypeScript flags reading it as text.

No other field of the resource may be over the column, as its own or as a relation's column, and another resource over the same table must leave the column out, or declare it `.encrypted()` too with the same `.table()`, tenant and key; the server does not start otherwise. A resource over a view of the table cannot be checked, so leave the column out of the view itself, not only out of the resource.

### Reading in jobs and functions

A value the app must use itself, such as the password of a backup share, is read on the server with `decryptField(resource, key, field)` of a [job's](/reference/jobs/) context and of a protected [API function's](/guides/api-functions/#the-context):

```ts
const password = await context.decryptField('backup_targets', target.id, 'password')
```

It returns the cleartext, or `null` when the field is empty. Like the context's `db`, it skips access rules, row filters and tenant scope, and reads only live records. `key` is the record's key, or its parts in the order of a composite key. A resource that is unknown, a field that does not exist or is not `.encrypted()`, and a record that does not exist are errors that name them, as is a value that does not decrypt.

Every read publishes a `field.revealed` [audit event](/reference/api/#sensitive-fields-and-audit), whose `reader` names the job (`{ job }`, with no `actor`) or the function (`{ function }`, with its caller as `actor`), and the value is only returned once the event is published: when publishing fails, so does the read. A public function has no `decryptField`, since anyone may call it: enqueue a job that reads the value instead. No HTTP request reaches it.

### The key

The app's key is `PROTOBASE_ENCRYPTION_KEY`: 32 random bytes in base64, such as the output of `openssl rand -base64 32`. It is its own: never the app's `secret` (`PROTOBASE_SECRET`) or an API key, nor derived from one, so rotating those loses nothing. Keep it apart from the database's backups, since whoever holds both reads every value. The server does not start with an encrypted field and no key, or a key that is not 32 bytes in base64.

To rotate it on several instances:

1. Add the new key to `PROTOBASE_ENCRYPTION_PREVIOUS_KEYS` (comma separated) everywhere, so every instance can read what it seals.
2. Make the new key `PROTOBASE_ENCRYPTION_KEY`, with the old one in `PROTOBASE_ENCRYPTION_PREVIOUS_KEYS`.
3. Run `protobase encryption apply`, which encrypts the old key's values with the new one.
4. Drop the old key once `protobase encryption status` shows none of its values. Keep retired keys as long as you keep backups made under them.

**A lost key loses its values.** Nothing can decrypt them; `status` lists them as `unknown-key`, and writing a new value replaces one. `apply` refuses to run while a column holds values under none of its keys, so a wrong key in a local `.env` does not seal values the app cannot read; clear values whose key is lost (set them to `null` with SQL) to go on.

<gap>There is no command that decrypts a field.</gap> Keep `.encrypted()` on a field while its column holds encrypted values; `status` reports encrypted values in a field that is not encrypted.

### What a value is bound to

A value opens only where it was sealed: its table as `.table()` names it (with or without the schema), its column, its record's tenant and its record's key. Copying it to another row, column or tenant makes it unreadable rather than readable there.

- Renaming the resource or the field in the config changes nothing.
- Renaming the table or the column, moving the table to another schema, or adding or changing the schema in `.table()` makes the field's values unreadable until `protobase encryption apply --rebind people --from-table <old table>` (or `--rebind people.iban --from-column <old column>`) runs. Run it at update time, like a migration; reveals fail until then.
- Changing a resource's declared key or tenant field makes its values unreadable. <gap>No command rebinds encrypted values after a change of a resource's key or tenant field.</gap> Make such a change before encrypting.
- The record key must be unique in its table, as [`protobase doctor`](/reference/cli/#doctor) checks, or at least within each tenant. A key changed in the database, by SQL, a trigger or a foreign key `on update cascade` (which `status` warns about), makes that row's values unreadable; the API refuses to change the key of a record with encrypted fields.

### Encrypting an existing column

1. With [events](/reference/events/), [history](/reference/history/) or live updates on the resource, [`protobase migration`](/reference/cli/#migration) writes the change of its capture trigger; apply it with your other migrations.
2. At update time, before the new version serves, run `protobase encryption apply`. It encrypts every plaintext value and removes the field's old values from the history and from the changes not yet dispatched.
3. With a rolling deploy, the old version writes plaintext until it stops: run `apply` again once the new version serves alone, and gate on `protobase encryption status`, which exits with 1 while anything is left. Until then, reveals of plaintext values fail.

Do not import ciphertext from elsewhere, such as another database's column encryption, into the column: `apply` would encrypt it as if it were plaintext. Export it decrypted instead.

What a move leaves behind: webhooks already sent carried the old values to their receivers, and webhook jobs keep their event, with the old values, in the jobs schema, a finished one for 7 days and a waiting one up to 14 days, so a backup made within a week of the move still holds them. Assistant conversations that showed the column keep what they showed. Older backups, the write-ahead log, replicas and the Postgres logs keep the old plaintext.

### What it protects against

It protects the values from database dumps, backups, replicas, and readers of raw SQL and realtime changes, who see only ciphertext. It does not protect them from whoever holds the key or the app's environment, or can run code in the server. Someone who can write to the database can change a row's tenant or roles, or put back an older value of the same record and field, from a backup say, which still opens. The ciphertext shows whether a value is empty, its length and when it changed. A key seals at most about 2³² values safely, as each gets a random IV; rotating starts a new key's count.

## Opening an existing record

A resource whose records are unique by some of their values, such as a direct message by its members, can have a create that repeats those values open the record that holds them instead of failing. `.openExisting()` names the unique key, as its fields:

```ts
resource('direct_messages')
  .table('direct_messages')
  .fields({
    id: f.integer().readOnly().dbDefault(),
    organization_id: f.relation('organizations'),
    member_ids: f.json(),
    // generated always as (...) stored: the members sorted, without repeats
    member_key: f.text().readOnly().dbDefault(),
  })
  .primaryKey((r) => r.id)
  .tenant((r) => r.organization_id)
  .openExisting((r) => [r.organization_id, r.member_key])
```

- The fields are exactly the columns of a unique index or constraint that covers every row, in any order, such as `unique (organization_id, member_key)`; a column the database generates counts. A create that conflicts on another unique key answers as without the option. Without such an index every create of the resource fails with a server error naming it, and [`protobase doctor`](/reference/cli/#doctor) reports it.
- A create that conflicts on the key answers the [`409` `conflict`](/reference/api/#errors) any unique violation answers, with `existing: { key }`, the key of the record holding those values, but only when the caller may read that record: in their tenant, inside their row filter and the parents they read, and passing a record-level read rule, as a `GET` of it checks. Otherwise the answer is the same plain `409`, so it never tells anyone that a record they cannot see exists. A soft-deleted record counts as one they cannot read.
- The create finds the record with `insert ... on conflict (...) do update ... where` a condition that only notes its key and is false, so nothing is updated and no update trigger runs, but the app's database role needs the update privilege on the table, as for any `on conflict do update`.
- Two creates of the same values at the same moment both end on one record: the second waits for the first and then answers with its key.
- The [create form](/reference/ui-config/#opening-the-existing-record) then opens that record instead of saying it could not save.
- An encrypted or file field cannot be part of the key: the API stores those as values that never match another record's.

## Access

Without rules everyone who can sign in may do everything. Rules come in three kinds, and the [Access](/reference/access/) reference explains the defaults:

- **Per operation** (`list`, `read`, `create`, `update`, `delete`): `.access({ update: rule })`. A rule returns `true`, `false`, or an AIP-160 filter that limits the rows, like row-level security. A rule that reads the record (`record.status`) is checked against the stored row on a get and a write; a caller it reads the record for may not list, so a rule that should list is a filter. See [Rules that read the record](/reference/access/#rules-that-read-the-record).
- **Per row**: a filter from a rule, or a `.own` or `.team` capability with `.owner(...)`: `.own` gives the records whose owner is the user, `.team` those owned by the users that `defineRoles(roles, { teamOf: (user) => ids })` returns for them.
- **Per field**: `.access({ read, create, update })` on the field. Field rules see only the user, never a record, so the fields a user can read are the same for every row.

[`defineRoles`](/api/schema/functions/defineroles/) turns roles into capabilities (`work_orders.update.own`, `money.read`, `*`), and `roles.can(...)` and `roles.is(...)` make rules of them; `.and()` and `.or()` combine rules.
