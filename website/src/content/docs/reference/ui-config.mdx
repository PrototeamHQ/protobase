A **view** says how the admin shows one resource: what its records are called, which columns the list has, which filters sit above it, how the record page is laid out, and which buttons it offers. It lives in `config/<resource>/ui.ts`; by convention every export of a `ui.ts` is picked up, and `config/index.ts` may export views too. A view only presents: what a user may see and do is decided by the [data config's access rules](/reference/data-config/#access), and `/api/meta` removes from each user's view every field they cannot read.

```ts
import { view } from '@protobase/schema'
import type { repairs } from './data'

export const repairsView = view<typeof repairs>('repairs')
```

[`view<typeof resource>(name)`](/api/schema/functions/view/) takes the resource's type, so every field reference below (`r.status`) is checked by TypeScript. A view is immutable: each [method](/api/schema/interfaces/viewbuilder/) returns a new view, so one view can build on another. The examples are the files of the [bike shop guide](/guides/table-to-admin/), where each step builds on the last.

Nowhere else shows it. |
| `.valueLabels({ value: text })` | How an enum's values read: `r.method.valueLabels({ ideal: 'iDEAL' })`. Only the enum's values are accepted. A value without a label shows as stored (`direct_debit`), so label every value that should read as words. |
| `.valueColors({ value: '#hex' })`, `.badgeShape('arrow')` | An enum's badges filled with a colour per value (the text turns white or black, whichever reads), and drawn as arrows pointing right, as on a rating scale. | `.widget(name, props?)` | Shows and edits the field with a [field type](/reference/plugins/#field-types) of the project or a plugin, such as `r.status.widget('steps')` or `r.score.widget('rating', { max: 5 })`; `props` are plain data. Without it, or on a storage type it does not show, the field shows as it would without the hint. |

An enum's value labels show everywhere the admin shows its values: badges, select options, list and related-table cells, filter options and chips, record titles, the sidebar and search results. They are part of the view in `/api/meta`, so an app with its own screens can show them too, and [`enumLabel(value, labels)`](/api/schema/functions/enumlabel/) from `@protobase/schema` reads a value the same way. A label for a value the enum does not have stops the server at startup, so renaming a value cannot leave a stale label behind.

`.filters((r, w) => [...])` puts widgets above the list, in order. Each needs a field that is `.filterable()`, which [`protobase build`](/reference/cli/#build) checks, and an index that serves it, as the [scan guard](/reference/api/#safety) and [`protobase doctor`](/reference/cli/#doctor) check; together they write the list's `?filter=`, so a filtered list can be bookmarked and shared.

| Widget | |
| --- | --- |
| `w.facets(r.status, { search? })` | A menu of the field's 50 most frequent values with counts, never all of them; `search` adds a search box that narrows those. On a relation it is a dropdown that shows the 50 most frequent too and searches the referenced records as you type, the first 20 matches, through the related resource's `search` fields (without any, the box narrows the 50 by name); on a number field, a range slider. |
| `w.dateRange(r.booked_on, { presets? })` | Buttons for `today`, `yesterday`, `7d`, `30d`, `90d`, `month`, `quarter`, `year`. |
| `w.range(r.estimate, { histogram? })` | A slider between the lowest and highest value; `histogram` draws the values' histogram behind it. The list filters when a thumb is let go of, or has rested a second. |
| `w.toggle(r.paid)` | A switch for a boolean field. |
| `w.flags([r.for_sale, r.for_rent], { label })` | A menu of boolean fields under one label, with how many records have each: a record shows when any chosen field is true, so one that is both shows under each. |

### Charts (graphs): records per day, week or month above a list

A list can show a graph of how many of its records fall on each hour, day, week or month, such as a daily graph of new listings. `.chart((r) => ({ field, range, granularity }))` draws records per day or week over a date or timestamp field above the list, following its filters: `range` is `7d`, `30d`, `90d`, `1y` or `all`, `granularity` `hour`, `day`, `week` or `month`.

## List displays

Besides its table, a list can show as cards, or as a component of the project's own, such as a board. The list stays at `/<resource>`, read through the list API, with its search, filters, chart, order and New button; only the way the rows are drawn changes.

| Display | |
| --- | --- |
| `d.cards({ image?, title?, subtitle?, amount?, badge?, meta?, footer?, flags? }, { name?, label?, icon?, card?, photos?, favorite? })` | A card per record, opening it: `image`, a [file field](/reference/files/), as a picture across the card's top (a raster image; anything else leaves the frame empty), then `title` (default: the view's `.title`) over `subtitle`, `badge` drawn as a badge with its value labels, `amount` the first of its fields with a value in bold (its suffix, such as ` /month`, not), such as a purchase price or else a rent, and a few small `meta` fields such as dates, each only when it has a value, after its field's `.icon` and as a badge when its field's format is `badge`. `footer` is a line at the card's bottom of its fields with a value, joined by bullets, such as a place and an agent. `flags` are boolean fields shown as small badges of their labels when true, such as a garden or parking. A relation shows the name of the record it points at. With `card`, a component declared with `component('RepairCard')` draws each card's content from the row of those fields instead (see [Record cards](/reference/custom-components/#record-cards)). With `photos`, the picture steps through more photos, by swipe or arrows (see [Card photos](#card-photos)). With `favorite`, a heart in the card's top right corner saves the record (see [Favorites](#favorites)). Named `cards` unless `name` says otherwise. |
| `d.map({ latitude, longitude, approximate?, exact?, radius?, area? }, { name?, label?, icon?, cards?, defaultRadius? })` | The matching records in the map's view, with how many there are below it; it asks again as it pans and zooms, through the list API's [`:map`](/reference/api/#maps). From far out it shows a count for each part of the map, which zooms in when chosen; close in, or with few records in view, the records themselves. Nearby records share a marker with their count; choosing one shows the record's card at the map's bottom, with arrows through the marker's records, and choosing the map elsewhere or closing the card clears it. The card is the one of the cards display `cards` names, else the list's first cards display, else the record's title. A record at an approximate position has a hollow marker and the area around it; see [Approximate positions](#approximate-positions). Named `map` unless `name` says otherwise. See [Maps](#maps). |
| `d.custom(Component, { name, label, fields, props?, icon? })` | The rows drawn by a [custom component](/reference/custom-components/#list-displays). `fields` are the fields it shows, loaded with the names of the records relations point at; `props` are plain data, with `r.field` where it takes a field. |

With displays, the list page has a switch at the right of its title: the table first, then each display by its `label`, with its `icon` (`table`, `cards`, `kanban`, `board`, `list` or `calendar`). Below the `md` breakpoint (768px) the switch is a menu of the same choices. The choice is in the address, `/repairs?display=cards`, so a reload, a bookmark or a shared link opens the same display; `default` names the display `/repairs` opens in, the table when it is left out. On a phone, below Tailwind's `sm` breakpoint (640px), a list with a cards display opens in it instead: the `default` when that is a cards display, else the first. A `?display=` in the address wins on any screen. A display without column headers has a sort menu over the sortable fields it shows, beside the filters, or below `md` in the filters sheet, whose button sits left of the search box. Selecting rows, deleting them in bulk and the row menu stay on the table, which every list keeps.

The table and the cards scroll with the page, which is as tall as all their rows, with the browser's own scrolling: only the rows and cards in view are drawn and loaded, so a list of any length scrolls at once, and Back returns to the same ones. The table's header stays below the top bar while the page scrolls. Every card is as tall as the tallest one drawn at that width. A custom display scrolls with the page as well, as every other page of the app does; the map fills the screen between the top bar and a phone's bottom bar instead, and does not scroll. Where scrollbars take room, as on Windows, the page keeps room for one even while it fits, so the cards keep their width as the scrollbar comes and goes.

Display names are checked when the config loads: unique, not `table`, and `default` names one. Their fields are checked when the server starts, and may not be [sensitive](/reference/data-config/#sensitive-fields). In `/api/meta`, a user's displays lose the fields they cannot read, and a custom display whose `props` name one is left out; the list then opens in the table when its default display went.

### Card photos

`photos: { resource, field, image, sort? }` names where a card's further photos come from: the records of `resource` whose relation `field` points at the card's record, in `sort` order, each shown by its file field `image`. The card's picture snaps photo by photo as it is swiped on a touch screen, and shows a left and a right arrow while the pointer is over it. The photos come with the list's records, in the same request through the list API's [`photos`](/reference/api/#card-photos), so every card on the page has them from the start, and a map's card too. The card's own `image` comes first and is not shown twice when it is among the photos too, and a card steps through ten pictures at most, its own among them; the arrows wrap around at both ends, dots under the picture mark the photo shown, and a card with no further photos has no arrows. Swiping or pressing an arrow does not open the record; tapping the picture does. In a row that scrolls sideways, as an embedded list shows its cards on a phone, a swipe scrolls the row instead, and the arrows show at all times on a touch screen. A card drawn by a `card` component has no arrows.

```ts
d.cards({ image: r.photo, title: r.address }, { photos: { resource: 'listing_photos', field: 'listing_id', image: 'photo', sort: 'position' } })
```

The server checks `photos` when it starts: `field` is a filterable relation to the list's resource, `image` a file field and `sort` a valid order on `resource`, and every cards display of the list names the same `photos`, since its records load with one set. One query reads the photos of the whole page, the first of each record by an index on `field` and the sorted fields, such as `unique (listing_id, position)`; the [scan guard](/reference/api/#safety) checks that one serves it, as it does a list's filter. In `/api/meta`, a user who cannot list those photos, or read `field`, `image` or the sorted fields, gets the cards without them, and the list API brings them only the photos they could list themselves.

### Favorites

`favorite: { resource, field, label? }` puts a heart in each card's top right corner that saves the card's record for the signed-in user: a record of `resource` whose relation `field` points at the card's record is created on a press and deleted on the next. The heart fills while the record is saved, at once on screen; a refused write puts it back and says why in a toast. It is a toggle button named `label` ("Favorite" by default) with `aria-pressed`, and like the photo arrows it sits over the card's link, so pressing it does not open the record. All of the user's saved records load once, page by page, for every card of the list.

A visitor who is not signed in gets the heart too, when the view of `resource` has a [sign-in prompt](#sign-in-prompts): pressing it tells them what signing in gives, in a modal on a desktop and a sheet from the bottom on a phone.

The view of the saved records' resource can list what they point at with `.listOf`: its list page then shows those records in their own resource's list, with its displays, filters, sort and search, under its own title and help. Unsaving a record there takes its card away. Its record pages and `/api/meta` model stay its own.

```ts
// listings/ui.ts
d.cards({ image: r.photo, title: r.address }, { favorite: { resource: 'favorites', field: 'listing_id', label: 'Save to favorites' } })

// favorites/ui.ts
view<typeof favorites>('favorites').names({ singular: 'Favorite', plural: 'Favorites' }).listOf((r) => r.listing_id)
```

The server checks `favorite` when it starts: `resource` has an [owner](/reference/data-config/#access) (`.owner(...)`), so the API lists and creates each user's own, and `field` is a filterable, writable relation to the list's resource, which has a single-column key; `.listOf` needs a relation to a resource with a single-column key. In `/api/meta`, a signed-in user who cannot list, create and delete those records, or write `field`, gets the cards without the heart.

### Saved searches

`.saveSearch({ resource, label? })` on a view puts a **Save search** button beside the list's title while its filters or search narrow it. A press asks for a name, which may be left empty unless the `name` field of `.searchesOf` has no `.optional()`, showing the filter's chips, then saves the list's filter, as the address holds it, as a record of `resource`, the signed-in user's own, with the name as given or `null`; the button is a toggle named `label` ("Save search" by default) with `aria-pressed`, pressed while that filter is saved, and the next press takes the search off again. Without a `name` field it saves at once. A visitor gets the button too when the view of `resource` has a [sign-in prompt](#sign-in-prompts), which a press opens.

The view of `resource` says what a saved search is with `.searchesOf(...)`, and its list page then shows the user's searches instead of rows, in its list's order. Each has its name, which links to its record page, and the filter's chips, which are its title instead when it has no name; its `controls`, enum fields as a menu and booleans as a switch, each saved as soon as it changes, which a toast confirms, a rename button, which asks for the name as saving does, a delete button, and the records the search finds, as a [`RecordRow`](/reference/blocks/#recordrow) shows them: how many, and the searched resource's cards in one row that scrolls sideways and loads more as it scrolls, up to `limit` when it is set. **View all results** opens the searched list with the search's filter, and names the search in the address, `?saved_search=<key>` (`addressWords.savedSearch`).

While the list's filter differs from the search it was opened from, and no other search has it, the button reads **Update** with the search's name, beside **Save as new search** (the noun from the names of the view of `resource`). **Update** asks first, in a dialog: each filter added, removed or changed, as the panel's chips name them, how many more or fewer records the search finds, and the records it would add and drop, the first 12 of each with their counts, drawn as its results are. Those come from the list API, with the filters `new AND NOT old` and `old AND NOT new`, where each condition of the negated filter also asks that its field has a value, so that a record the old filter cannot decide (a range on a rent it has none of) counts as not found by it, as the list shows. The dialog updates the search, saves the list's filter as a new one, asking for its name, or does nothing.

With `unseen: { seenAt, field }` the row is newest first by `field`, a timestamp of the searched resource, and the records new to the user, those whose `field` is after the search's `seenAt`, are marked **New** in their card's top left corner; when none are, the search says so beside its count. **View all results** sets `seenAt` to now. A search saved today marks what is published from today.

```ts
// listings/ui.ts
view<typeof listings>('listings').saveSearch({ resource: 'saved_searches' })

// saved_searches/ui.ts
view<typeof savedSearches>('saved_searches').searchesOf((r) => ({
  resource: 'listings',
  filter: r.filter,
  name: r.name,
  controls: [r.alert_frequency],
  unseen: { seenAt: r.seen_at, field: 'published_at' },
}))
```

The view checks its own fields when the config loads: `filter` and `name` are text fields, `seenAt` a timestamp and each control an enum or boolean. The server checks the rest when it starts: `resource` has an [owner](/reference/data-config/#access), the fields a save or a control writes are writable, `unseen.field` is a filterable timestamp or date of the searched resource, and a view of the resource a list saves to has `searchesOf` for that list. In `/api/meta`, a user who cannot list the searched resource or read `filter` gets the view without `searchesOf`, and its controls and `unseen` narrow to what they can write. A search's filter is checked like any list's when its records load; checking it on a write, against the searched resource, is the data config's: a `.validate` rule with `parseFilter` and `checkFilter`.

To tell users of new records, a job matches each new record against the saved filters with `evaluateFilter`, given the searched resource as `search` so that a search text in the filter looks in its search fields too, and sends an [email](/reference/email/). The [property portal example](https://github.com/PrototeamHQ/protobase/tree/main/examples/property-portal#alerts) mails at once or in a daily digest.

### Exports

Every list has an **Export** button beside its title, and **Export N** beside **Delete N** for the rows selected in its table. Both open one dialog that asks for the format, Excel (`.xlsx`) or CSV; the rows, those the list finds with its filters, search and sort, or the selected ones; the columns, the list's own in its order to start with, then any field the user may read, each moved up or down; and the values, **As shown**, as the list shows them (enum value labels, the names of related records, dates and numbers formatted with the view's prefix, suffix and decimals), or **Raw values**, as the API stores them (keys, codes, ISO dates). It says how many rows that is before it starts: counted exactly up to 10,000, the planner's estimate above.

The rows come through the list API as the user may read them, page by page with its page tokens (`POST /{resource}:search`, 500 a page), so the [scan guard](/reference/api/#safety), the role's row filter and its readable fields apply as on the list; a [sensitive field](/reference/data-config/#sensitive-fields) is never offered. The selected rows are found again by their key, so a resource with a composite key offers only the list's rows. The browser builds the file in a Web Worker, the server only answering the pages it reads anyway, and writes it as it goes: to the file the user picks where the browser has the [File System Access API](https://developer.mozilla.org/docs/Web/API/File_System_API), as a download otherwise. A progress dialog counts the rows, and **Cancel** stops after the page being read and discards the file.

A workbook has one sheet named after the records, a bold header row of the columns' labels that stays in view, columns as wide as their header and the first page's values, and typed cells: numbers, dates and times with a number format (as shown, the list's format; raw, `yyyy-mm-dd`), booleans as TRUE and FALSE, and text. Dates and times are in UTC, as the list shows them; a 64-bit integer past 2^53 stays text so that no digit is lost, and a text is cut at Excel's 32,767 characters. A sheet holds at most 1,048,575 rows. A CSV file is UTF-8 with a byte order mark, so Excel reads it as such, quoted as RFC 4180 has it, with a text that starts with `=`, `+`, `-`, `@`, a tab or a carriage return written after an apostrophe, so that a spreadsheet does not run it as a formula. The file is named after the records and the day, as `Orders 2026-10-16.xlsx`.

`.export(false)` takes Export off a view's list, and `.export({ maxRows })` limits how many rows a file holds: the dialog says when the list finds more, and the toast that ends the export says the file holds only the first rows. Like the rest of a view, this only shapes the page: what a user may read is the [data config's access rules](/reference/data-config/#access), and the API serves it as it does to the list.

```ts
view<typeof orders>('orders').export({ maxRows: 50_000 })
view<typeof auditLog>('audit_log').export(false)
```

## Importing records

A list page offers **Import** beside **New** to a user who may create the resource's records; `.import(false)` on the view turns it off. It opens a dialog that creates or updates records from an Excel workbook (`.xlsx`) or a CSV file (UTF-8, its delimiter a comma, semicolon or tab, found from the first line). See [Importing records from a spreadsheet](/guides/import-records/) for a walk through.

```ts
view<typeof invoices>('invoices').import(false)
```

1. **File.** The first row names the columns; a workbook with several sheets asks which one to read. A Web Worker reads the file, a CSV and a sheet's rows as they stream in, so a large file neither holds up the page nor is held whole in memory, and the file itself never goes to the server: only the writes of its rows do.
2. **Columns.** A column whose header is a field's label or name, ignoring case and spacing, fills that field; each mapping can be changed, or the column skipped. The fields are those the import can write: not read-only, not the tenant, not JSON or files, and relations to records with a key of one field. The fields a new record needs (not optional, without a default) that no column fills are listed, and a create waits for them. A relation's column holds the related record's key, or the value of a field the user picks under it, such as a customer's email. **Numbers** and **Dates** say how the file writes what text leaves open: `1,234.56` or `1.234,56`, the day or the month first; they start from the browser's language. Dates written as `2026-12-31` read the same either way, and a time without a zone is the browser's.
3. **Rows.** **Create** makes a record of each row. A user who may also update records can choose **Update**, which finds each row's record by a column the user picks, holding its key or a field no two records share (filterable, not sensitive), and skips a row that finds none, or **Create or update**, which creates that record instead.
4. **Check.** The whole file is read and every row converted before anything is written: the first rows as they will be saved, and each row's problems, also as a file to download. Nothing is guessed: an empty cell is `null`, never the field's default; numbers and dates in the chosen formats, true or false (`true`, `false`, `yes`, `no`, `1`, `0`), enum values by their [value labels](#names-and-columns) or values, and related records found by exactly one match convert, and anything else is a problem on its row. The import skips those rows.
5. **Import.** The rows are written in batches of 100 with [`POST /api/v1:batchWrite`](/reference/api/#batch-writes), so the server validates each and checks the user's access as it does a single write; an update is sent with the ETag `*`. Each batch is a transaction of its own, so an import is not all or nothing: a row the server refuses is set aside with the server's reason, and the rest of its batch is sent again. **Cancel import** stops between two batches, keeping what was written, and so does an error such as an expired session. The summary counts the rows created, updated, skipped (with problems in the file) and failed (refused by the server), and downloads the rows not imported as a CSV, the file's own columns followed by each row's line in the file and its problems, to fix and import again.

## Create pages

When a resource's records are made by a process rather than a form, such as an app a server sets up or an order from a cart, its view names a [composed page](/reference/layouts/) of the app's own that creates them, with `.create({ page })`:

```ts
view<typeof repairs>('repairs').create({ page: 'book-repair' })
```

- `/<resource>/new` shows that page instead of the create form, so the list's **New** button and every [create address](/reference/layouts/#addresses) open it. The breadcrumb reads the resource and **New**, as for the form.
- **New** shows to whoever `/api/meta` gives the page, as its `roles` say, whatever the resource's `create` access. The resource's API can then refuse creates (`create: () => false`) while the page creates through an [API function](/guides/api-functions/) that writes with `db`. Someone without the page gets no **New**, and `/<resource>/new` tells them they cannot create there: the create form never shows. **Import** still follows the resource's `create` access.
- The address's `values` stay in it. A component on the page reads them with `useAppAddress()` and can keep its answers there as they are given, so a reload, a link, or a round trip through another site keeps them. See [Create pages](/reference/custom-components/#create-pages).
- The server refuses a page that does not exist when it starts.

[A create page of your own](/guides/create-page/) builds one step by step.

## Sign-in prompts

`.signIn({ title, description, benefits?, icon?, signUp? })` on a view tells a visitor who is not signed in what they could do with the resource once signed in. Where a signed-in user sees the list, the visitor sees the prompt: an icon (`icon`, as for field hints, a sign-in icon by default), `title`, `description` and a line per `benefits`, with **Sign in**, which opens the sign-in page and comes back to the same address. A card's [favorite button](#favorites) that saves to the resource, and a list's [Save search](#saved-searches) button that saves to it, open the same prompt as a dialog, with **Not now** to close it. With [open sign-up](/reference/auth/#open-sign-up) on the server, the prompt also offers **Create an account**, which opens the app's own sign-up page. `signUp: { label, href }` names a page elsewhere instead, `https://`, `http://` or `mailto:`, opened in a new tab.

```ts
view<typeof favorites>('favorites').signIn({
  title: 'Keep the homes you like',
  description: 'Sign in to save listings to your favorites and find them again on any device.',
  benefits: ['Save a listing with the heart on its card', 'See all your saved homes on one page'],
  icon: 'heart',
})
```

Only a caller without a token gets the prompts, in `/api/meta` as `signIn`, for the resources they cannot see whose view for the `anonymous` role has one: its names, its sidebar place and the prompt. Those resources keep their place in the sidebar, the [bottom bar](/reference/bottom-bar/) and the [user menu](/reference/user-menu/). Pages of the project can show a prompt too: `SignInPrompt` from `@protobase/ui` takes it `as="page"` or `as="dialog"`, and `ResponsiveDialog` is the modal that becomes a sheet on a phone.

### Read view and edit

`.recordMode(mode)` says how the record page opens to a user who may change the record:

| Mode | |
| --- | --- |
| `'edit'` | The form, ready to change, as without the setting. The default. |
| `'read'` | A read view: each section a table of labels on the left and values on the right, as a property's features on a real estate site, and a text of several lines under its label, or a row of [key facts](#key-facts). **Edit**, among the record's actions, opens the form. |
| `'locked'` | The form, its fields locked until **Edit** is pressed, for records where reading and editing look alike but a change should be meant. |

The form that **Edit** opens has its own address, the record's with `?edit=true` (`{ kind: 'record', resource, key, edit: true }`), so it opens in a new tab and Back leaves it. It has **Cancel**, which drops the changes and goes back to the record, and **Save**, which goes back once the record saved. A user who may not change the record, such as a visitor who is not signed in, never gets the form, at that address too: they get the read view in every mode, without Edit. Values on the read view show as they do everywhere else, an empty one as `—` (key facts leave it out) and a boolean as Yes or No, and a sensitive field stays masked behind its eye. Changes not saved stay in the browser, as they do on the form: the read view then offers to continue editing them or discard them.

```ts
view<typeof listings>('listings').recordMode('read')
```

### Key facts

`presentation: 'facts'` on a section shows its fields on the read view as a real estate site shows a home's key facts: side by side, wrapping onto more rows as needed, each value under the icon its field's [`.icon(name)`](#names-and-columns) names, or under the field's label without one. A fact with an icon still has its label, for screen readers and as the tooltip. On a mobile screen, below the `sm` breakpoint (640px), the facts sit two to a row. A field without a value is left out rather than shown as `—`, and a section with none left is left out; a value of `0` or No stays. The form edits the section as any other, its fields under their labels.

```ts

  }))
  .layout((r) => [l.section('Key facts', [r.purchase_price, r.living_area, r.bedrooms, r.energy_label, r.garden], { presentation: 'facts' })])
```

### Help while editing

Help lines show on the record page and in forms by default. Those meant for whoever changes the record, such as where a value comes from, can show only while it is edited: on its form and the create form, not on the read view or a locked form. `.helpWhen('editing')` on the view says so for all of its fields and sections; a field's `.help(text, { when })` and a section's `helpWhen` say it for their own, and win over the view's.

```ts
view<typeof listings>('listings')
  .recordMode('read')
  .helpWhen('editing')
  .fields((r) => ({
    price: r.price.help('The asking price, without costs.'),
    agent_phone: r.agent_phone.help('Call to plan a viewing.', { when: 'always' }),
  }))
```

### Galleries

`l.gallery(title, { image?, photos? })` shows a record's photos as tiles in the main column: one large, the next four smaller beside it, the last counting the photos not drawn ("+12"). On a mobile screen it draws the large one with the number of photos. A tile opens a lightbox at its photo, at full size over the page, with a counter, arrows and the left and right keys to step through them all, stopping at the first and the last, a sideways swipe on a touch screen, and Escape or the close button to return. `image` is a file field of the record, shown first; `photos` names the records holding the further photos, as a cards display's [`photos`](#card-photos) does: those of `resource` whose relation `field` points at the record, in `sort` order, each shown by its file field `image`. A photo that is also the record's `image` is shown once, and files that are no image are left out. A record without photos has no gallery.

```ts
.layout((r) => [
  l.gallery('Photos', { image: r.photo, photos: { resource: 'listing_photos', field: 'listing_id', image: 'photo', sort: 'position' } }),
  l.section('Listing', [r.address, r.price]),
])
```

The photos are read with the list API under the user's own access, up to 500, so an index on `field` and the sorted fields serves them, which [`protobase doctor`](/reference/cli/#doctor) checks. In the lightbox, a photo held by a record of a resource the user may read has an info button, which shows that record's details, as does the `i` key: in a sidebar beside the photo, or on a mobile screen in a sheet over the lower part of the screen, which Escape, its close button or a swipe down on its header closes. The details start closed, and the browser remembers whether they were left open for the next photo and gallery. They are the fields its record page's sections show, less its file and the field pointing at the record, as a table of labels and values, as the record API answers the user, so the server decides what they see, and a link to its record page. A user who may not read that resource sees the photo alone, without the info button, as everyone does when it has no other field to show. In `/api/meta`, a user who cannot read `image` gets the gallery without it, and one who cannot list the photos without them; a gallery left with neither is left out. The server checks when it starts that `image` is a file field and that `photos` fits the resources.

### Maps

`l.map(title, { latitude, longitude })` draws a map centred on a pin at the record's position, read from two number fields (`integer`, `bigint` or `decimal`) in decimal degrees, WGS84, at `zoom` (default 15, from 0 to 22). It pans and zooms with two fingers on a phone, and with Ctrl or Cmd and the wheel elsewhere, so the page scrolls past it.

```ts
.layout((r) => [
  l.map('Location', { latitude: r.latitude, longitude: r.longitude }),
  l.section('Coordinates', [r.latitude, r.longitude]),
])
```

The map is drawn with [MapLibre](https://maplibre.org) from the style the server names: `createAdmin`'s `options.maps.style`, else `PROTOBASE_MAP_STYLE_URL`, an http(s) URL of a MapLibre style. The style's sources may be [PMTiles](https://docs.protomaps.com/pmtiles/) archives (`pmtiles://https://...`), so the tiles can be one file on a bucket of your own. The tiles, sprites and fonts are fetched by the browser, so their host must answer the app's origins with CORS, and an archive with range requests. Without a style there is no map, nor is there one for a record whose fields hold no position or for a user who may not read them. MapLibre loads with the first map drawn, so a page without one does not load it.

A map display takes two number fields that are `.filterable()`, since it asks for the records inside its view with a filter on them, and the server refuses to start otherwise; an index on them, such as `(latitude, longitude)`, lets Postgres find those records. The filter and search of the list narrow what it shows. Where it looks is in the address, `/listings?display=map&map=52.37,4.89,12` (latitude, longitude, zoom), so Back, a reload or a shared link opens the same view; without one it fits every matching record. When none is in view, **Show all** fits them again.

#### Approximate positions

Some records know their position only roughly, such as a listing that gives its street but not its number. A map display marks those positions by a boolean field: `approximate`, true for an approximate position, or `exact`, false for one. Their markers are hollow with a dashed edge, a marker's label to a screen reader says the position is approximate, and the chosen record's card says **Approximate position**. Without the field, or where it holds neither, a position is exact.

Around an approximate position the map draws the area the record states: the GeoJSON `Polygon`, `MultiPolygon`, `LineString` or `MultiLineString` its `area` field holds, as a `json` field or the text of one, a geometry or a feature of one, such as a block or the street; else a circle of its `radius` field, a number of metres; else a circle of `defaultRadius` metres when the display names one. A record that states none of them on a display without a default has only its hollow marker, so the map shows no more than the data says. An area is drawn faintly in the markers' colour, a line as a wide stroke, and the chosen record's darker. It fades in as the map zooms close enough for it to be wider than a marker, and only the records in view have theirs drawn.

```ts
d.map(
  { latitude: r.latitude, longitude: r.longitude, exact: r.coordinates_exact, radius: r.accuracy_m, area: r.street_outline },
  { label: 'Map', defaultRadius: 250 },
)
```

`radius`, `area` and `defaultRadius` need `approximate` or `exact`, and the server refuses to start when a field is of another type. A user who may not read the field that marks the positions sees them as exact.

<StoryFrame id="list-page-map-approximate-positions--approximate-positions" title="An exact home and approximate ones: in a circle, a block, on a street, and with no area" height={720} />

A map does not edit the position: list the fields in a section as well when users should change them. The [property portal example](https://github.com/PrototeamHQ/protobase/tree/main/examples/property-portal) shows a listing on a map, and its listings on one.

#### Map layers

`options.maps.layers` adds other maps of raster tiles, such as aerial photos, next to the style. With layers, every map (`l.map` and `d.map`) has a switch in its top left corner between **Map**, the style's map and the default, and each layer by its `label`. The choice is remembered in the browser for every map, and a layer the app no longer offers falls back to the default. The chosen layer is drawn over the style's map, under the areas and markers, and its `attribution` shows in the map's corner while it is.

```ts
createAdmin({
  // ...
  options: {
    maps: {
      layers: [
        {
          id: 'aerial_nl',
          label: 'Aerial (NL)',
          tiles: 'https://service.pdok.nl/hwh/luchtfotorgb/wmts/v1_0/Actueel_orthoHR/EPSG:3857/{z}/{x}/{y}.jpeg',
          attribution: 'Luchtfoto <a href="https://www.beeldmateriaal.nl/">Beeldmateriaal Nederland</a>, CC BY 4.0, via <a href="https://www.pdok.nl/">PDOK</a>',
          bounds: [3.2, 50.7, 7.3, 53.7],
          maxzoom: 21,
        },
      ],
    },
  },
})
```

| Field | What it is |
| --- | --- |
| `id` | Lowercase letters, digits and `_`, unique: what the browser remembers. |
| `label` | What the switch says. |
| `tiles` | The http(s) URL of 256-pixel Web Mercator tiles with `{z}`, `{x}` and `{y}`: an XYZ service, or a WMTS `GetTile` URL in its `GoogleMapsCompatible` or `EPSG:3857` tile matrix set, with `{z}` as the tile matrix, `{y}` the row and `{x}` the column. |
| `attribution` | The credit the tiles' licence asks for; it may hold links. |
| `bounds` | Optional `[west, south, east, north]` in degrees, where the tiles are. The layer is offered everywhere; outside its bounds no tiles are asked for and the style's map shows through. |
| `maxzoom` | Optional deepest zoom of the tiles, from 0 to 24 (default 22); closer in, the map enlarges them. |

The browser fetches the tiles, so their host must answer the app's origins with CORS. Layers need a style: without one there is no map to switch. A layer that is not as above stops the server at startup. Use only tiles whose terms allow it: open aerial photos are published per country, such as the Netherlands' [PDOK Luchtfoto](https://www.pdok.nl/-/open-data-hr-luchtfoto) and Spain's [PNOA](https://pnoa.ign.es/) from the IGN, both CC BY 4.0, free and without a key; the [property portal example](https://github.com/PrototeamHQ/protobase/tree/main/examples/property-portal) offers both.

### Related records

`l.related(title, options)` lists the first records of `resource` that point at the record on the page, in the table or display the resource's list page uses (with its switch, and on a phone its cards in one sideways row, as a [`Table` block](/reference/blocks/#table) shows them), and links to all of them in that list. They point at it directly, through a relation field, or through a join resource (`through`), such as the leases a tenant signed through `lease_tenants`:

| Option | |
| --- | --- |
| `resource` | The records listed. Required. |
| `field` | Without `through`: the relation on `resource` that holds this record's key. With it: the field of `resource` matched against the keys the join records hold. Filterable. Required. |
| `through` | `{ resource, field, key?, filter? }`: the join records whose `field` (a filterable relation) holds this record's key; their `key` values (default their primary key) pick the listed records. At most 500 join records are read. |
| `filter`, `sort` | AIP-160 and AIP-132 on `resource`, as in the list API. `filter` narrows the listed records, `through.filter` the join records. |
| `columns` | Fields of `resource`, through relations too (`unit_id.property_id`); default the view's list columns without `field`. The first opens the record. |
| `limit` | How many records it shows, 1 to 100; default 10. Before 0.13 this was `pageSize`, rows per page; rename it. |
| `display` | The display of `resource`'s list it opens in, such as `cards`; default the list's. |
| `help`, `empty` | A line under the title, and the text when nothing matches (default "Nothing here yet."). |
