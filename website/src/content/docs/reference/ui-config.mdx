A **view** says how the admin shows one resource: what its records are called, which columns the list has, which filters sit above it, how the record page is laid out, and which buttons it offers. It lives in `config/<resource>/ui.ts`; by convention every export of a `ui.ts` is picked up, and `config/index.ts` may export views too. A view only presents: what a user may see and do is decided by the [data config's access rules](/reference/data-config/#access), and `/api/meta` removes from each user's view every field they cannot read.

```ts
import { view } from '@protobase/schema'
import type { repairs } from './data'

export const repairsView = view<typeof repairs>('repairs')
```

[`view<typeof resource>(name)`](/api/schema/functions/view/) takes the resource's type, so every field reference below (`r.status`) is checked by TypeScript. A view is immutable: each [method](/api/schema/interfaces/viewbuilder/) returns a new view, so one view can build on another. The examples are the files of the [bike shop guide](/guides/table-to-admin/), where each step builds on the last.

## Names and columns

| Method | |
| --- | --- |
| `.names({ singular, plural })` | "New repair", "Repairs" in the sidebar and breadcrumbs. Default: the resource name in words. |
| `.title((r) => r.number)` | The field that names a record: in breadcrumbs, the record page's heading, relation links and search results. |
| `.searchResult((r) => ({ title?, subtitle? }))` | A record in the [global search](/reference/client/#global-search): `title` is one field or several joined by spaces (`[r.first_name, r.last_name]`, default: `.title`), `subtitle` the line under it (default: the first search field not in the title), replaced by the search field the text matched when neither line shows it. |
| `.list((r, d) => ({ columns, sort?, search?, displays?, default? }))` | The list's columns in order; its starting `sort` as `[[field, 'asc' \| 'desc'], ...]`; the fields the search box suggests (the resource's `.search` decides what search matches on the server); other ways to show it, see [List displays](#list-displays). |
| `.fields((r) => ({ name: r.name.label(...) }))` | Hints per field, below. Calls add up. |
| `.help(text)` | A line under the list's title. |
| `.nav({ group, order, hidden, recent })` | Where the resource sits in the sidebar, and its [recent-record group](/reference/sidebar/#recent-records). |
| `.icon(name)` | Carried in `/meta` for apps that render their own shell; the admin picks sidebar icons by resource name. |

Field hints:

| Hint | |
| --- | --- |
| `.label(text)` | Instead of the name in words (`customer_id` would be "Customer" anyway). |
| `.help(text)` | A line under the field on the record page and in forms. |
| `.format(format)` | `badge` shows statuses as coloured badges, `code` sets identifiers in monospace, `percent` adds a % sign. `relative`, `absolute` and `compact` are accepted and carried in `/meta` for apps that render their own lists; the admin does not use them yet. |
| `.prefix(text)`, `.suffix(text)`, `.decimals(n)` | Money and measures: `€` and `2` show `€1,234.50`, `.suffix(' m²')` shows `120 m²`. They show wherever the number does: records, cards, table cells, forms and the range filter. |
| `.icon(name)` | An icon before the value on a card's meta row: `bed`, `file-text`, `ruler`, `send` or `wallet`, as for [actions](/reference/layouts/#named-actions). Nowhere else shows it. |
| `.valueLabels({ value: text })` | How an enum's values read: `r.method.valueLabels({ ideal: 'iDEAL' })`. Only the enum's values are accepted. A value without a label shows as stored (`direct_debit`), so label every value that should read as words. |
| `.valueColors({ value: '#hex' })`, `.badgeShape('arrow')` | An enum's badges filled with a colour per value (the text turns white or black, whichever reads), and drawn as arrows pointing right, as on a rating scale. The property portal's energy label: `r.energy_label.format('badge').valueColors({ a: '#00a651', g: '#ed1c24' }).badgeShape('arrow')`. Only the enum's values are accepted. |
| `.widget(name, props?)` | Shows and edits the field with a [field type](/reference/plugins/#field-types) of the project or a plugin, such as `r.status.widget('steps')` or `r.score.widget('rating', { max: 5 })`; `props` are plain data. Without it, or on a storage type it does not show, the field shows as it would without the hint. |

An enum's value labels show everywhere the admin shows its values: badges, select options, list and related-table cells, filter options and chips, record titles, the sidebar and search results. They are part of the view in `/api/meta`, so an app with its own screens can show them too, and [`enumLabel(value, labels)`](/api/schema/functions/enumlabel/) from `@protobase/schema` reads a value the same way. A label for a value the enum does not have stops the server at startup, so renaming a value cannot leave a stale label behind.

## Filters and the chart

<Code code={step3} lang="ts" title="docs-examples/bike-shop/step-3.ts" />

`.filters((r, w) => [...])` puts widgets above the list, in order. Each needs a field that is `.filterable()`; together they write the list's `?filter=`, so a filtered list can be bookmarked and shared.

| Widget | |
| --- | --- |
| `w.facets(r.status, { search? })` | A menu of the field's values with counts; `search` adds a search box for long lists. On a relation it is a dropdown that searches the referenced records as you type and holds several of them; on a number field, a range slider. |
| `w.dateRange(r.booked_on, { presets? })` | Buttons for `today`, `yesterday`, `7d`, `30d`, `90d`, `month`, `quarter`, `year`. |
| `w.range(r.estimate, { histogram? })` | A slider between the lowest and highest value; `histogram` draws the values' histogram behind it. |
| `w.toggle(r.paid)` | A switch for a boolean field. |
| `w.flags([r.for_sale, r.for_rent], { label })` | A menu of boolean fields under one label, with how many records have each: a record shows when any chosen field is true, so one that is both shows under each. |

`.chart((r) => ({ field, range, granularity }))` draws records per day or week over a date or timestamp field above the list, following its filters: `range` is `7d`, `30d`, `90d`, `1y` or `all`, `granularity` `hour`, `day`, `week` or `month`.

## List displays

Besides its table, a list can show as cards, or as a component of the project's own, such as a board. The list stays at `/<resource>`, read through the list API, with its search, filters, chart, order and New button; only the way the rows are drawn changes.

<Code code={workshop} lang="ts" title="docs-examples/reference/workshop.ts" />

| Display | |
| --- | --- |
| `d.cards({ image?, title?, subtitle?, amount?, badge?, meta?, footer?, flags? }, { name?, label?, icon?, card?, photos? })` | A card per record, opening it: `image`, a [file field](/reference/files/), as a picture across the card's top (a raster image; anything else leaves the frame empty), then `title` (default: the view's `.title`) over `subtitle`, `badge` drawn as a badge with its value labels, `amount` the first of its fields with a value in bold (its suffix, such as ` /month`, not), such as a purchase price or else a rent, and a few small `meta` fields such as dates, each only when it has a value, after its field's `.icon` and as a badge when its field's format is `badge`. `footer` is a line at the card's bottom of its fields with a value, joined by bullets, such as a place and an agent. `flags` are boolean fields shown as small badges of their labels when true, such as a garden or parking. A relation shows the name of the record it points at. With `card`, a component declared with `component('RepairCard')` draws each card's content from the row of those fields instead (see [Record cards](/reference/custom-components/#record-cards)). With `photos`, the picture gets arrows through more photos (see [Card photos](#card-photos)). Named `cards` unless `name` says otherwise. |
| `d.map({ latitude, longitude }, { name?, label?, icon?, cards? })` | The matching records in the map's view, with how many there are below it; it asks again as it pans and zooms, through the list API's [`:map`](/reference/api/#maps). From far out it shows a count for each part of the map, which zooms in when chosen; close in, or with few records in view, the records themselves. Nearby records share a marker with their count; choosing one shows the record's card at the map's bottom, with arrows through the marker's records, and choosing the map elsewhere or closing the card clears it. The card is the one of the cards display `cards` names, else the list's first cards display, else the record's title. Named `map` unless `name` says otherwise. See [Maps](#maps). |
| `d.custom(Component, { name, label, fields, props?, icon? })` | The rows drawn by a [custom component](/reference/custom-components/#list-displays). `fields` are the fields it shows, loaded with the names of the records relations point at; `props` are plain data, with `r.field` where it takes a field. |

With displays, the list page has a switch at the right of its title: the table first, then each display by its `label`, with its `icon` (`table`, `cards`, `kanban`, `board`, `list` or `calendar`). Below the `md` breakpoint (768px) the switch is a menu of the same choices. The choice is in the address, `/repairs?display=cards`, so a reload, a bookmark or a shared link opens the same display; `default` names the display `/repairs` opens in, the table when it is left out. On a phone, below Tailwind's `sm` breakpoint (640px), a list with a cards display opens in it instead: the `default` when that is a cards display, else the first. A `?display=` in the address wins on any screen. A display without column headers has a sort menu over the sortable fields it shows, beside the filters, or below `md` in the filters sheet, whose button sits left of the search box. Selecting rows, deleting them in bulk and the row menu stay on the table, which every list keeps.

The table and the cards scroll with the page, which is as tall as all their rows, with the browser's own scrolling: only the rows and cards in view are drawn and loaded, so a list of any length scrolls at once, and Back returns to the same ones. The table's header stays below the top bar while the page scrolls. Every card is as tall as the tallest one drawn at that width.

Display names are checked when the config loads: unique, not `table`, and `default` names one. Their fields are checked when the server starts, and may not be [sensitive](/reference/data-config/#sensitive-fields). In `/api/meta`, a user's displays lose the fields they cannot read, and a custom display whose `props` name one is left out; the list then opens in the table when its default display went.

### Card photos

`photos: { resource, field, image, sort? }` names where a card's further photos come from: the records of `resource` whose relation `field` points at the card's record, in `sort` order, each shown by its file field `image`. The card's picture gets a left and a right arrow; the first press loads that card's photos with one request to the list API, so the list itself loads as fast as without them. The card's own `image` comes first and is not shown twice when it is among the photos too; the arrows wrap around at both ends, dots under the picture mark the photo shown (a count such as `3 / 24` past ten photos), and a card with no further photos loses its arrows once they have loaded. Pressing an arrow does not open the record. A card drawn by a `card` component has no arrows.

```ts
d.cards({ image: r.photo, title: r.address }, { photos: { resource: 'listing_photos', field: 'listing_id', image: 'photo', sort: 'position' } })
```

The server checks `photos` when it starts: `field` is a filterable relation to the list's resource, `image` a file field and `sort` a valid order on `resource`. In `/api/meta`, a user who cannot list those photos, or read `field`, `image` or the sorted fields, gets the cards without them.

## The record page

`.layout((r) => [...])` with [`l`](/api/schema/variables/l/) from `@protobase/schema`:

| Item | |
| --- | --- |
| `l.section(title, fields, { help? })` | A titled group of fields in the main column, editable where the user may write. |
| `l.sidebar(fields)` | A summary card beside it, read-only. |
| `l.related(title, { ... })` | A table of the records of another resource that point at this one, in the main column. See [Related records](#related-records). |
| `l.custom(Component, { title?, props?, sidebar? })` | A [custom component](/reference/custom-components/#record-sections) where it is listed: in the main column under `title`, or with `sidebar: true` as a sidebar card. |
| `l.map(title, { latitude, longitude, zoom?, sidebar? })` | A map with a pin at the record's position, in the main column or with `sidebar: true` as a sidebar card. See [Maps](#maps). |

A custom component draws only its part: the page around it stays the record page, at `/<resource>/<key>`, with its breadcrumbs, title and badge, Save, Discard and Delete, the action rail and the related records, and a layout may hold only custom components. The repairs above list the customer's earlier repairs under the bike:

Without a layout the record page shows one section with every field the user may change, or every field, read-only, to a user who may change none. A section or sidebar card with no field the user may see is left out. `.saveFeedback('button')` shows saving on the Save button instead of a toast (`'toast'`, the default). A [sensitive field](/reference/data-config/#sensitive-fields) in a section is masked, with an eye button that reveals it.

### Maps

`l.map(title, { latitude, longitude })` draws a map centred on a pin at the record's position, read from two number fields (`integer`, `bigint` or `decimal`) in decimal degrees, WGS84, at `zoom` (default 15, from 0 to 22). It pans and zooms with two fingers on a phone, and with Ctrl or Cmd and the wheel elsewhere, so the page scrolls past it.

```ts
.layout((r) => [
  l.map('Location', { latitude: r.latitude, longitude: r.longitude }),
  l.section('Coordinates', [r.latitude, r.longitude]),
])
```

The map is drawn with [MapLibre](https://maplibre.org) from the style the server names: `createAdmin`'s `options.maps.style`, else `PROTOBASE_MAP_STYLE_URL`, an http(s) URL of a MapLibre style. The style's sources may be [PMTiles](https://docs.protomaps.com/pmtiles/) archives (`pmtiles://https://...`), so the tiles can be one file on a bucket of your own. The tiles, sprites and fonts are fetched by the browser, so their host must answer the app's origins with CORS, and an archive with range requests. Without a style there is no map, nor is there one for a record whose fields hold no position or for a user who may not read them. MapLibre loads with the first map drawn, so a page without one does not load it.

A map display takes two number fields that are `.filterable()`, since it asks for the records inside its view with a filter on them, and the server refuses to start otherwise; an index on them, such as `(latitude, longitude)`, lets Postgres find those records. The filter and search of the list narrow what it shows. Where it looks is in the address, `/listings?display=map&map=52.37,4.89,12` (latitude, longitude, zoom), so Back, a reload or a shared link opens the same view; without one it fits every matching record. When none is in view, **Show all** fits them again.

A map does not edit the position: list the fields in a section as well when users should change them. The [property portal example](https://github.com/PrototeamHQ/protobase/tree/main/examples/property-portal) shows a listing on a map, and its listings on one.

### Related records

`l.related(title, options)` lists the first records of `resource` that point at the record on the page, in the table or display the resource's list page uses (with its switch, and on a phone its cards in one sideways row, as a [`Table` block](/reference/blocks/#table) shows them), and links to all of them in that list. They point at it directly, through a relation field, or through a join resource (`through`), such as the leases a tenant signed through `lease_tenants`:

| Option | |
| --- | --- |
| `resource` | The records listed. Required. |
| `field` | Without `through`: the relation on `resource` that holds this record's key. With it: the field of `resource` matched against the keys the join records hold. Filterable. Required. |
| `through` | `{ resource, field, key?, filter? }`: the join records whose `field` (a filterable relation) holds this record's key; their `key` values (default their primary key) pick the listed records. At most 500 join records are read. |
| `filter`, `sort` | AIP-160 and AIP-132 on `resource`, as in the list API. `filter` narrows the listed records, `through.filter` the join records. |
| `columns` | Fields of `resource`, through relations too (`unit_id.property_id`); default the view's list columns without `field`. The first opens the record. |
| `limit` | How many records it shows, 1 to 100; default 10. Before 0.13 this was `pageSize`, rows per page; rename it. |
| `display` | The display of `resource`'s list it opens in, such as `cards`; default the list's. |
| `help`, `empty` | A line under the title, and the text when nothing matches (default "Nothing here yet."). |

## Actions and views per role

`.actions((a) => [...])` names the moves a record page offers in its action rail, and composed pages can put the same actions on buttons. `a.update`, `a.remove` and `a.link` work without code; `a.action` runs a handler the app registers. They are described with [named actions](/reference/layouts/#named-actions).

`.forRoles([...])` makes a view for users with one of those roles: each user gets the first such view that matches their roles, and the view without roles otherwise. A per-role view is a whole view, so build it from another (`laidOut.forRoles(...)` above) and change what differs.
