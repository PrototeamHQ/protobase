The `protobase` command comes with `@protobase/cli`. Install it in a project next to the packages its config imports:

```sh
bun add @protobase/cli @protobase/schema @protobase/layout @protobase/server @protobase/ui
bun run protobase <command>                     # from the project, config folder defaults to ./config
bun run --cwd examples/erp protobase <command>  # in this repository, for an example
```

Any package manager installs the packages, and the command runs on Node or on Bun: `npm install` and `npx protobase <command>` work the same. The bin starts with `#!/usr/bin/env node`, so where Node is installed `bun run protobase` starts it on Node, unless the project's `bunfig.toml` sets `[run] bun = true`, as the presets' does.

## How it runs

The published `@protobase` packages are JavaScript: each is built with [tsdown](https://tsdown.dev) to ES modules and type declarations in `dist`, one file per source module, and packing them points their `exports`, `types` and `bin` at it (`publishConfig`). The installed `protobase` command (`bin/protobase.mjs`) runs `dist` on Node 22.12 or later, or on Bun. The project's own TypeScript is loaded with Vite on both: `users` and `doctor` import it through Vite's module runner, `dev` serves it and `build` bundles it.

In this repository nothing needs a build: the packages' `exports` point at `src`, and the workspace's `protobase` is `bin/protobase-source.mjs`, which imports `src/index.ts`: Bun loads it itself, Node through [tsx](https://tsx.is). `bun run build` builds every package to `dist`.

The serve runtime is bundled by `protobase build-serve` into one JavaScript file for Bun, so production needs neither `node_modules` nor the CLI (see [serve](#serve)).

The CLI reads the database with `default_transaction_read_only = on`, so it can never write.

## `scaffold`

```sh
protobase scaffold <connection string | --env DATABASE_URL> [target] [options]
```

`target` is `all` (default), `schema`, `schema.table` or `schema.table.column`. Tables are introspected from `pg_catalog`; `config/<resource>/data.ts` is created or extended.

| Option | Effect |
| --- | --- |
| `--config <dir>` | config folder, default `config` |
| `--yes` | accept every proposal, no prompts (required without a TTY) |
| `--dry-run` | print a diff, write nothing |
| `--ui` | also write `ui.ts` (`.names()` and `.list()`) |
| `--ui-list`, `--ui-section <names\|list>` | write only those `ui.ts` sections |
| `--exclude <schema[.table]>` | skip tables, repeatable |

Interactively, each new column shows its proposal: accept, edit (name, type) or ignore (writes `field: null`; key columns cannot be ignored).

### Inference

| Database | Field |
| --- | --- |
| `int2`, `int4` / `int8` | `f.integer()` / `f.bigint()` |
| `numeric(p,s)` | `f.decimal({ precision, scale })` (unconstrained: 38, 9) |
| `text`, `varchar`, `bpchar` | `f.text()` |
| `bool`, `date`, `timestamp(tz)`, `uuid`, `json(b)` | `f.boolean()`, `f.date()`, `f.timestamp()`, `f.uuid()`, `f.json()` |
| Postgres enum, or a `CHECK (col IN (...))` on text | `f.enum([...])` |
| foreign key | `f.relation('<resource>')`, `.columns([...])` for a composite key (on its first column) |
| anything else (`ltree`, arrays, ...) | `f.text().readOnly()` |

- `NOT NULL` absent: `.optional()`. Literal default: `.default(v)`.
- Computed defaults (function, sequence, expression, `GENERATED BY DEFAULT` identity): `.dbDefault()`. It also gets `.readOnly()` when the column is an identity column, a primary-key column, or an audit timestamp (`created_at`, `inserted_at`, `updated_at`, `modified_at`); other computed defaults, such as `order_date DEFAULT current_date`, stay editable. `GENERATED ALWAYS` identity and generated columns are only `.readOnly()`.
- Leading column of a non-partial index: `.filterable()`; of a btree: also `.sortable()`. Not applied to json.
- The text field that names a record (`name`, `title`, `number`, `sku`, `email`, `code` or `description`, else the first text field) becomes the resource's `.search(...)` when a non-partial pg_trgm index (`gin_trgm_ops` or `gist_trgm_ops`) serves it, so the [global search](/reference/client/#global-search) finds its records by name. Without one the API would refuse the search, so it is left out; add the index and run `protobase scaffold` on a new resource, or add `.search` by hand.
- Key: primary key (composite supported), else the first unique index with only `NOT NULL` columns, else the table is skipped with a warning.
- `deleted_at`, `removed_at`, `archived_at` (nullable timestamp/date) become `.softDelete`; `organization_id` and `tenant_id` become `.tenant`.
- Unique indexes are listed in the doc comment above the resource.
- Field names are the column names in snake_case; `.column()` is written only when the schema builder's default mapping would not give the column back (always for `hr."EMP_MASTER"`).
- Resource names are the table name in snake_case, prefixed with the schema on collisions, and exported under their camelCase name (`export const orderLines = resource('order_lines')`). Names already in `config/` win.

### Re-running

Existing `data.ts` files are edited with ts-morph: only columns that are neither declared nor `null` are added, at the end of `.fields({...})`. Nothing else is rewritten, and key, soft delete and tenant calls are only written when a resource is created. `ui.ts` gets only missing sections. `config/index.ts` gets exports for resources created in the run (all resources when it does not exist yet); existing lines are never touched. A run with nothing new changes nothing. `schema.table.column` on an unscaffolded table scaffolds the whole table.

### Drift report

After each run, declared fields are compared with the database: a column that no longer exists, a type that no longer fits (a relation fits `integer`/`bigint`/`uuid`/`text`, `currency` and `country` fit `text`), or different enum values. Each entry carries a suggested replacement. Drift is reported, never applied.

## `doctor`

```sh
protobase doctor <connection string | --env VAR> [--config <dir>]
```

Imports `config/index.ts` and the views of `config/*/ui.ts`, as the config module has them by convention, and checks every exported resource against the database:

- error: missing table or column, field type that does not fit the column (a file field needs a text column), table without a usable key, configured key not backed by a unique index
- error: a read the [scan guard](/reference/api/#safety) refuses, because no index serves a column it filters, sorts, searches or counts by. Doctor reads each table's indexes from the catalog, as the server does, and judges with the scan guard's own rule every read the API takes and the app makes: a filter on each `.filterable()` field, a sort by each `.sortable()` one, `search()` over the search fields, a role's own records (`.owner()`) and the names a relation shows; each view's list in its order, its filter widgets and their counts, its map and card photos, its related sections, its recent records and a saved search's new records; and each block of a [composed page](/reference/layouts/) that lists records. Each error is an index to add, with every request that needs it and where it comes from:

  ```
    error   agencies: no index serves the column "name", so the API refuses:
              GET /agencies?order_by=name asc ("name" is sortable; the agencies list's order)
            fix: create index on "market"."agencies" ("name");
  ```

  Reads are judged as the scan guard's default `reject` mode judges them, for a role that reads every row, such as admin; other access rules are code doctor does not run. A resource on a plain view or a foreign table is not judged, as the scan guard does not judge it.
- warning: enum values differ

Exit code is 1 when there are errors. Run it after the project's migrations and before a new version serves, as a platform's deploy does: a read it fails is one the API would refuse once the version runs. `protobase build` needs no database, so the indexes are doctor's to check.

## `dev`

```sh
protobase dev [--port 5173] [--env DATABASE_URL] [--cache-dir <dir>] [--allowed-hosts <hosts>] [--extend <dir>]   # run inside a project, e.g. bun run --cwd examples/erp dev
```

One process, one port: Vite serves the admin app from `@protobase/ui`'s `src/app/` (`dist/app/` when installed; `index.html` and `main.tsx`, or `main.js`; the command fails with a clear message when they are missing) and `@hono/vite-dev-server` mounts the Hono app from `createAdmin` under `/api`, supabase-js's `/api/sb` included. Open `http://localhost:<port>`; the API reference is at `/api/docs`.

- **Database:** the URL comes from the variable named by `--env`, read from the environment or the nearest `.env` at or above the project. The connection is checked before anything starts; if it fails, the command names host, port and reason (and points to its `db:up` script when it has one). The project needs `pg` installed, because the API connects with Kysely over the project's own `pg`.
- **Cache:** Vite's dependency cache is `node_modules/.vite`; two dev servers sharing it can disturb each other's optimisation, so pass `--cache-dir` for a second one (the integration test does).
- **Login:** real sign-in only, with the `authenticate` and `auth` exported by `protobase.config.ts` (see [Login with Better Auth](/reference/auth/)). A project without an authenticator fails at startup with a message pointing there, one whose auth schema is behind with the tables and columns it lacks (see [`auth migration`](#auth-migration)), and one with a resource whose [events](/reference/events/) or [history](/reference/history/) lack their triggers, or whose [comments](/reference/comments/) lack their table, or whose [rollup and formula fields](/reference/data-config/#rollups-and-formulas) lack their columns or triggers, which it checks again on every reload (see [`migration`](#migration)), and one with an [AI field or action](/reference/ai/#the-model) and no model key; there is no development login. Create the first admin with `protobase users create`.
- **Mobile releases:** see [below](#mobile-releases).
- **Jobs:** with [jobs](/reference/jobs/) in the config it runs them in its process, once the jobs schema checks out (see [`migration`](#migration)); an edited job runs its new code from the next job on.
- **Tunnels and other hosts:** Vite only answers `localhost` by default. `--allowed-hosts .trycloudflare.com,app.example.com` adds Host headers (a leading dot matches all subdomains). Hot reload needs no extra setting: the Vite client takes protocol, host and port from the page, so behind an HTTPS tunnel it connects over `wss` on 443 as long as the tunnel forwards WebSockets.
- **Project discovery**, by convention: `config/index.ts` exports the resources (and views), and every `config/*/ui.ts` export that is not already exported by the index is added as a view. Each `functions/<name>.ts` (or `functions/<name>/index.ts`) is an [API function](/guides/api-functions/) at `/api/functions/<name>`. A `protobase.config.ts` in the project root replaces the convention; its default export may contain any of:

  ```ts
  import * as config from './config'
  export default {
    config,                      // module whose exports are resources and views
    db,                          // Kysely instance, instead of DATABASE_URL
    authenticate,                // Authenticator, required
    auth,                        // Better Auth (AdminAuth); its routes are mounted under /api/auth
    functions,                   // API functions by name, instead of ./functions
    jobs,                        // module whose exports are jobs (defineJob), see Jobs
    options,                     // AdminOptions (scan guard, write hooks, ...)
  }
  ```

  `defineConfig` from `@protobase/server` types it, and its `extends` merges other configs in (see [Extending a config](#extending-a-config)).
- **Project UI:** the app imports `protobase.ui.tsx` from the project root, with hot reload, when it exists (see [Custom components](/reference/custom-components/)): the same contract as the plugin `protobase build` makes of it, built into the dev page instead. Layout files are checked as they load, as `protobase build` checks them.
- **Theme:** the page links `/protobase.theme.css`, which the dev server answers from the project's [theme](/reference/theme/), checked as the build checks it, on every request, so an edit shows on the next reload. It links `/protobase.favicon.svg` too, the project's [favicon](/reference/theme/#logo-and-favicon) or Protobase's, and `/protobase.apple-touch-icon.png`, which it answers with the PNG [icons](/reference/app-identity/#the-icons) the project has.
- **Extensions:** `--extend <dir>` merges an extension in, its UI built into the dev page beside the project's, to try one out; its files reload like the project's.
- **Hot reload:** server code, data configs, `ui.ts` views, layouts and `protobase.config.ts` are loaded through Vite's SSR module graph. A change inside the project (or, in this repository, in `packages/server`, `packages/query`, `packages/schema`) rebuilds the API on the next request without a restart; `/meta` and `X-Meta-Version` change, so open tabs refetch. The database pool survives reloads. Newly added `ui.ts` files appear after the next change inside the project.

### Extending a config

A config can extend others by importing them, like Vite's `defineConfig`. `extends` lists configs merged in order, each after the ones it extends itself, and the extending config last:

```ts
// protobase.config.ts
import { defineConfig } from '@protobase/server'
import tasks from 'some-extension/protobase.config'

export default defineConfig({ extends: [tasks], config, auth, authenticate, options: { roles } })
```

```tsx
// protobase.ui.tsx
import { defineUi } from '@protobase/ui'
import * as tasksUi from 'some-extension/protobase.ui'

export { UsageChart } from './components/usage-chart'
export default defineUi({ extends: [tasksUi] })
```

| What | How it merges | The same name twice |
| --- | --- | --- |
| `config` exports: resources, views, pages | all kept | an error naming both configs |
| user menu | at most one among all configs | an error |
| `options.assistant.tools` | the extended configs' first, in order, then the app's | an error naming the tool and both configs |
| `jobs` | all kept, by job name | an error naming the job and both configs |
| `options.writeHooks` | all run, in the same order | |
| every other value (`db`, `auth`, `authenticate`, `roles`, `assistant.url`, ...) | the app's own; otherwise the last config that sets it | |
| UI components (exported by name or in `components`), `actions` | all kept | an error naming the name and both configs |
| UI `shell.actions`, `shell.rightPanel` | all drawn, the extended configs' first | |
| UI `shell.logo` | the app's own; otherwise the last config that sets it | |

A config's `name` names it in these errors; an extension should set one. Nothing is namespaced, so a collision is always an error, never a silent override. Names starting with `Protobase` (components) and `protobase_` (tools) belong to Protobase's own extensions, such as `ProtobaseCloudTask` and `protobase_cloud_create_proposal`; give yours other names. `mergeConfig(...configs)` from `@protobase/server` and `mergeUi(...configs)` from `@protobase/ui` merge the same way in code.

## `build`

```sh
protobase build [--out dist] [--bun] [--extend <dir>] [--source-maps]   # run inside a project, e.g. bun run --cwd examples/erp protobase build
```

Writes the project's deploy bundle, the folder a deployment ships:

```
dist/
  protobase.config.js       the config module for serve
  migrations/               the project's db/migrations/*.sql, which the runtime's migrate applies; only with some
  node_modules/             the packages it loads from disk, only when it imports native add-ons
  public/
    index.html, assets/     the admin app: the shell, the same for every project
    protobase.sw.js         the shell's service worker (see Installable app)
    plugins/app/            the project's protobase.ui.tsx, built as a plugin
    plugins/<extension>/    each --extend folder's protobase.ui.tsx, built as a plugin
    protobase.theme.css     the project's theme, checked and minified; empty without one
    protobase.favicon.svg   the project's favicon; Protobase's without one
    protobase.*.png         the project's PNG icons, the ones it has (see App identity)
  protobase.bundle.json     the manifest
```

The output folder is not emptied; `public/`, `migrations/` and `node_modules/` are replaced on every build. `migrations/` and `node_modules/` are deleted only when the previous build's manifest names them, so a build into a folder with a project's own `node_modules` fails instead. Of the project's server config only the config folder runs at build time, `config/index.ts` and `config/*/ui.ts` with what they import, never `protobase.config.ts`, so the build needs no secrets and no database. It is loaded once in Node to check each view against its resource: a filter widget or the chart on a field that is not `.filterable()`, a list sorted by one that is not `.sortable()`, or a list search on a field outside the resource's `.search(...)` fails the build, naming the view and the field, since the API would refuse it once a page asked. Whether an index serves those reads needs the database, which [`doctor`](#doctor) checks. Its browser code is loaded once in Node too: to check its component names (see [The UI](#the-ui)) and to read the field types each plugin registers.

A token the [theme](/reference/theme/) sets that the app does not read prints a `warning:` line, a likely typo; the build still succeeds.

By default the bundle runs on Node and on Bun. `--bun` makes it a bundle for Bun only, as the Protobase images and the cloud serve it: Bun's bundler writes the config module (see [the config module](#the-config-module)), so the build needs `bun` on `PATH` and fails without it.

`--source-maps` writes a source map beside each script of the shell and the plugins, `assets/<name>-<hash>.js.map`, for an error tracker to read the browser's stack frames with. Each script ends with a `//# debugId=<uuid>` comment, and its map carries the same `debugId`; the scripts name no map, but a host serves the maps with the rest of `public/` unless it moves them out. The shell's maps come prebuilt in `@protobase/ui`'s `dist/shell-source-maps/`. Without the option the bundle has no maps.

### Extensions

`--extend <dir>` (repeatable) adds an extension to the bundle without touching the project's files: a folder with a `protobase.config.ts`, a `protobase.ui.tsx` or both. Its `protobase.config.ts` is merged into the config module before the project's own, as if the project [extended](#extending-a-config) it, in the order given. Its `protobase.ui.tsx` becomes one more [plugin](/reference/plugins/) of the bundle, in `public/plugins/<name>/`, named by its `package.json`'s `name`, else its folder's. A host adds its own assistant tools and widgets to every app it builds this way; to add React code to apps without building them, serve a plugin instead.

- The extension's imports of `@protobase/*` resolve from the project, so it runs on the app's own versions; `react`, `react-dom` and `@protobase/ui` are the app's at runtime, as for every plugin. Everything else it imports resolves from its own folder and is built into its plugin, with a stylesheet of the classes its files use.
- A component, action handler or field type that the extension and the project both define fails the build, naming both. To find them, the build loads the merged UI configs once in Node: only browser code, which needs no secrets. The server config still does not run at build time, so a tool both define fails when the bundle is served, naming both.
- An error names a config by its `name`, otherwise by its file. Two extensions whose plugins would have one name fail the build.

### The manifest

`protobase.bundle.json` is the contract between a bundle and the host that serves it:

```json
{
  "version": 3,
  "protobase": "0.12.0",
  "server": "protobase.config.js",
  "public": "public",
  "spa": "index.html",
  "api": ["/api", "/.well-known/oauth-authorization-server", "/.well-known/oauth-protected-resource"],
  "theme": "protobase.theme.css",
  "plugins": [
    { "name": "app", "path": "plugins/app/plugin.json", "api": 1, "protobase": ">=0.12.0", "fields": { "steps": ["enum"] } }
  ],
  "shell": { "protobase": "0.12.0", "pluginApi": 1, "paths": ["/index.html", "/assets", "/protobase.sw.js"] },
  "native": { "@capacitor/core": "8.5.3", "@capacitor/ios": "8.5.3" },
  "nodeModules": "node_modules",
  "migrations": "migrations"
}
```

- `protobase` is the Protobase version that built the bundle. The serve runtime serves only bundles of a compatible version: below 1.0 the same minor, from 1.0 the same major and the runtime's minor or an older one (see [Versioning](/reference/versioning/#bundles-and-runtimes)).
- `server`, `public`, `nodeModules` and `migrations` are relative to the bundle folder; `spa`, `theme` and each plugin's `path` to `public`.
- `plugins` are the bundle's own plugins, in the order the app merges them: the extensions', then the project's (`app`). Each names its `plugin.json`, the plugin API and Protobase versions it is built for, and the [field types](/reference/plugins/#field-types) it registers with the storage types each shows, which the serve runtime checks the views against at startup. `/api/meta` names them to everyone, before any other plugin.
- `shell` is the admin app `public/` holds a copy of: its Protobase version and plugin API, and its files as URL paths. A host with a shell of its own, of a release every plugin of the bundle loads in, may serve its own for those paths instead (see [The UI](#the-ui)), so the app gets that release's fixes without a rebuild.
- `native` is the native packages, name to version, that `shell` runs on in the [mobile app](/guides/mobile-app/): those `@protobase/mobile` pins. The fingerprint of the bundle's [mobile release](#mobile-releases) names them. A bundle built before it serves no mobile release.
- `theme` is the project's [theme](/reference/theme/), which the app links at `/protobase.theme.css`. It is always there, empty when the project has none.
- `nodeModules` is present only when the config module imports [native packages](#native-packages). It is always the `node_modules` folder beside `server`, where Bun and Node resolve the module's imports from, and holds plain packages: JavaScript, `package.json` files and native binaries for linux x64 and arm64 (glibc), which the runtime loads with `dlopen`. A host keeps it next to the server module and must not mount it `noexec` (an add-on there then fails with `failed to map segment from shared object`). Its binaries link nothing but glibc, `libstdc++.so.6`, `libgcc_s.so.1` and libraries in the bundle itself, so the run image must have those three. Without `nodeModules`, the server module is the only file the runtime reads.
- `migrations` is present only when the project has a `db/migrations` folder: its `.sql` files, which the runtime's `migrate` applies (see [Deploy](/guides/deploy/)). A host never serves it.
- `api` lists the path prefixes the server answers. A path is under a prefix when it equals it or continues it with `/` (`/api` covers `/api/meta` and `/api/v1:batchWrite`, not `/apiary`). It is always `/api` and the two OAuth discovery documents [MCP clients](/reference/auth/#oauth-for-mcp-clients) read, which answer 404 without MCP: a bundle assumes the API lives under `/api`, with the resources at the default `basePath` `/api/v1`, `/api/meta`, the docs, the API functions and the built-in assistant beside them and Better Auth at `/api/auth`. A bundle built before them sends them to the UI: rebuild it. The serve runtime refuses a config that sets another `options.basePath`.
- Every other path is the UI's. A `GET` or `HEAD` for a file in `public` gets that file; a folder gets its `index.html`. Otherwise a request whose `Accept` header contains `text/html` (a navigation) gets `spa` with status 200, so deep links such as `/orders/42` load the app; anything else gets 404. Other methods get 405.
- Files under an `assets/` folder, `public/assets/` and each plugin's, are named by their content hash and never change: serve them with `Cache-Control: public, max-age=31536000, immutable`, and everything else, `index.html`, each `plugin.json` and the theme, with `no-cache`.
- `version` is the format of the manifest, not a Protobase version. A host that does not know it must refuse the bundle. Version 3 replaced version 2 when the project's UI became a plugin beside a prebuilt app, and gained `plugins`, `theme` and `shell`; version 2 replaced version 1 when the config module started to import [every module the runtime supplies](#the-config-module), and gained `nodeModules`. `protobase serve` refuses an older bundle; rebuild it with `protobase build`.

### The UI

`public/` holds two parts that are built apart.

- **The shell**, `index.html`, `assets/` and `protobase.sw.js`: the admin app, a production build of `@protobase/ui`'s `src/app` with no project code in it, the same for every project on a release. `@protobase/ui`'s package ships it prebuilt in `dist/shell/` and the [protobase image](/guides/deploy/#images) at `/opt/protobase/shell/`; the build copies it. It calls the API on its own origin under `/api`, so the same bundle works under any hostname, and reads everything else at runtime: the resources, views, pages and roles from `/api/meta`, sign-in from `/api/auth`, the project's UI from its plugins and its look from `/protobase.theme.css`, which it links after its own stylesheets, its tab icon from `/protobase.favicon.svg`, and its [web app manifest](/reference/installable-app/) from `/api/manifest.webmanifest`.
- **The plugins**, `plugins/<name>/`: the project's `protobase.ui.tsx` as the plugin `app`, and each [extension](#extensions)'s, each built as [`build-plugin`](#build-plugin) builds one, against the `@protobase/ui` installed in the project. `/api/meta` names them, and the shell loads them as it loads any [plugin](/reference/plugins/). A component or field type the config declares but no `protobase.ui.tsx` exports fails the build (see [Components](/reference/custom-components/#components)).

The modules the app shares with plugins, `react`, `react/jsx-runtime`, `react-dom` and `@protobase/ui`, are entries of their own, `/assets/shared-<name>-<hash>.js`, each exporting every name of its module. `index.html` maps the four names to them with an import map, ahead of every script, so a plugin's imports of them run on the app's copies.

### The config module

`protobase.config.js` is one ES module. The entry is found as `protobase dev` finds it: the default export of `protobase.config.ts`, with `config` taken from the convention (`config/index.ts` plus `config/*/ui.ts`) and `functions` from `functions/` when it exports none.

- Vite bundles the config into plain ES modules in UTF-8, which Node and Bun both load as they are.
- With `--bun`, Vite writes to a scratch folder and `bun build --target bun` writes the final module. Bun's output starts with `// @bun`, which tells Bun the file is already plain JavaScript: Bun neither transpiles it nor writes its transpiler cache. Bun reads such a file as Latin-1, so only Bun's own output can carry that line: its bundler writes non-ASCII text as escapes (`€` as `\u20AC`). Raw UTF-8 with that line would load as `â¬`.
- The `@protobase` packages and every package in their `dependencies` belong to the serve runtime: their imports stay `import` statements and the runtime supplies them, so the bundle carries no copy and shares the runtime's. It supplies these modules:

  | Modules | |
  | --- | --- |
  | `@protobase/schema`, `@protobase/layout`, `@protobase/layout/jsx-runtime`, `@protobase/query`, `@protobase/server` | the server entry points of the `@protobase` packages, and what [layout files](/reference/layouts/) compile to |
  | `kysely`, `kysely/helpers/postgres`, `pg`, `postgres` | the database |
  | `better-auth`, `hono`, `jose`, `zod`, `aip-parsers`, `@hono/node-server`, `@scalar/hono-api-reference` | the main entry of each other dependency the `@protobase` packages run on the server |
  | `hono/cors`, `hono/http-exception`, `hono/validator` | Hono middleware for [API functions](/guides/api-functions/) |
  | `react`, `react/jsx-runtime`, `@react-email/render` | what [email templates](/reference/email/#in-a-bundle) render with, so a template's component and the renderer share one React |
  | `@protobase/server/email` | the [look of Protobase's own mail](/reference/email/#the-look-of-protobases-own-mail), loaded when the bundle first imports it rather than when the runtime starts |

  `react-email` is a dependency of `@protobase/server` that the runtime does not supply: the server loads it only to send its own mail, or for `@protobase/server/email`, so a config that imports it inlines its own copy, like any other package.

  Importing any other `@protobase` package or dependency of one (`@protobase/ui`, `react-dom`, `better-auth/plugins`, `zod/v4`, ...) fails the build with this list, also from inside an inlined package, when the finished bundle still imports it: an inlined package may re-export a module that imports one, as `react-email` does with `tailwindcss`, as long as the project leaves that export unused. So does a copy the project installs in another version than the `@protobase` packages use (another major, or another minor below 1.0), which the runtime's would replace. The list is `packages/cli/src/serve/host-module-ids.ts`; the set of packages comes from the `package.json` of `@protobase/cli` and of every `@protobase` package it depends on.
- Packages with a native add-on stay imports too, and the bundle carries them in `node_modules/` (see [Native packages](#native-packages)). Node's built-in modules stay imports.
- Everything else (the project's files and its other packages) is inlined. Nothing is minified.
- Layout files (`@jsxImportSource @protobase/layout`) compile to calls of `@protobase/layout/jsx-runtime`, for production whatever `NODE_ENV` says. The build refuses one with a function, class, `new` value or hook in its JSX, naming the file, line and column ([what a layout may hold](/reference/layouts/#what-a-layout-may-hold)).
- The default export is the project config merged with the configs it [extends](#extending-a-config), with `config` always set:

  ```ts
  export default { config, authenticate, auth?, functions?, options?, db? }   // as protobase.config.ts exports it
  ```

The serve runtime reads the environment when it imports the module, on the host.

### Native packages

A package with a native add-on cannot be inlined: it loads a compiled `.node` file from its own folder at runtime. The build recognises one by a `.node` file or a `binding.gyp` in it, or by optional dependencies that carry the add-on per platform and name a linux one (`@node-rs/argon2-linux-x64-gnu`, sharp's `@img/sharp-linux-x64`). For each such package the config module imports, directly or through an inlined package:

- The import stays an import, which resolves at runtime to `node_modules/<package>` beside the config module.
- The package and everything it needs at runtime (its dependencies and the optional ones that are installed, recursively) are copied to `node_modules/` as one tree: each package at the top, a second version of one under the package that needs it. Files of a package are copied as they are, except native binaries.
- Every native binary in them (ELF, Mach-O or PE, told by its headers, not its name) is copied only when it is for linux x64 or linux arm64 with glibc: the run image is Bun's distroless image (Debian) for amd64 and arm64, and a bundle may run on either. Binaries for macOS, Windows, musl or other architectures stay behind, as do platform packages for them (by their `os`, `cpu` and `libc` fields).
- Every add-on needs a `.node` binary for both, in its package or in its platform packages. Otherwise the build fails and names each package, the platforms it misses and the ones it has. It never ships a binary built for the wrong platform.
- Every binary it copies may link only glibc's libraries, the C++ runtime (`libstdc++.so.6`, `libgcc_s.so.1`) and libraries the bundle carries itself (sharp's libvips); otherwise the build fails and names the binary and the library. Every add-on in common use links `libgcc_s` and, when written in C++, `libstdc++`. Bun's distroless image has glibc only, so the run image adds those two (Debian's `libgcc-s1` and `libstdc++6`); without them an add-on fails to load (`libstdc++.so.6: cannot open shared object file`).

What that means for a package:

- **Prebuilt binaries for every platform inside the npm package** (prebuildify and node-gyp-build: `argon2`, `bcrypt` 6, `bufferutil`): builds anywhere, macOS included.
- **Per-platform optional packages** (napi-rs, such as `@node-rs/argon2`, and sharp): a package manager installs only the build machine's, so the build fails until the linux ones are installed as well. With Bun, `bun install --os='*' --cpu='*'` installs every platform's. With pnpm, in `pnpm-workspace.yaml`:

  ```yaml
  supportedArchitectures:
    os: [current, linux]
    cpu: [current, x64, arm64]
    libc: [current, glibc]
  ```

- **Built or downloaded on install** (node-gyp from source, prebuild-install such as `better-sqlite3`, node-pre-gyp): only the build machine's binary exists, so the build fails, on a linux machine too, which has one architecture.

The bundle then runs on linux only: `protobase serve` of it on macOS cannot load the add-ons. Check it in a linux container of a run image with the C++ runtime, built from this `Dockerfile` (`docker build -t protobase-run .`, with `--platform linux/amd64` for the other architecture):

```dockerfile
FROM debian:trixie-slim AS libs
RUN d=/usr/lib/$(uname -m)-linux-gnu && mkdir -p /out$d && cp -a $d/libstdc++.so.6* $d/libgcc_s.so.1 /out$d/
FROM oven/bun:1.4.2-distroless
COPY --from=libs /out/ /
```

```sh
docker run --rm -p 127.0.0.1:8787:8787 -e DATABASE_URL -e BETTER_AUTH_SECRET \
  -v "$PWD/dist:/app:ro" -v "$PWD/protobase-serve.js:/opt/protobase/protobase-serve.js:ro" \
  protobase-run --no-install /opt/protobase/protobase-serve.js /app/protobase.config.js
```

## `build-plugin`

```sh
protobase build-plugin [dir] [--out <dir>] [--name <name>] [--source-maps]
```

Builds the [plugin](/reference/plugins/) in `dir` (default: the current folder), whose entry is its `protobase.ui.tsx`, into `--out` (default: `dir/dist`):

```
dist/
  plugin.json                 what the app reads first
  assets/index-<hash>.js      the plugin's module, and its chunks beside it
  assets/styles-<hash>.css    the utilities its files use
```

- The output folder is emptied first, so it must not be the plugin's folder or hold it.
- The module is `protobase.ui.tsx` with everything it imports bundled, except the four modules the app shares (`react`, `react/jsx-runtime`, `react-dom`, `@protobase/ui`), which stay imports by those names. Any other module of those packages, such as `react-dom/client`, fails the build. React's production build and JSX runtime are used, whatever `NODE_ENV` says, and every export of `protobase.ui.tsx` is kept.
- The stylesheet is Tailwind's utilities for the classes in the plugin's folder: no reset, no theme values. Each utility reads the theme of the app that loads it, with Tailwind's default as the fallback (`text-sm` is `font-size: var(--text-sm, 0.875rem)`).
- `plugin.json` names the plugin (`--name`, else its `package.json`'s `name`, else its folder's), its own `version`, the plugin API (`api`) and the Protobase versions (`protobase`) it is built for, the module (`entry`) and stylesheet (`css`), relative to it, and the [field types](/reference/plugins/#field-types) it registers (`fields`), each with the storage types it shows. Both versions come from the `@protobase/ui` installed for the plugin, which the build needs: `api` is its plugin API, and `protobase` is `>=` its version unless the plugin's `package.json` names a range in `engines.protobase` (see [Plugins](/reference/plugins/#versions)).
- `--source-maps` ends each script with a `//# debugId=<uuid>` comment, naming no map, and writes its source map, `<script>.js.map` carrying the same `debugId`, beside it, for an error tracker to read the browser's stack frames with.

To read its field types, the build loads the plugin's module once in Node, with everything bundled; nothing is rendered, but code at the top level of its modules runs, so keep browser-only work (`window`, `document`) inside components and handlers. The app loads it from wherever `plugin.json` is served, listed in `PROTOBASE_PLUGINS` or `options.plugins` (see [loading](/reference/plugins/#loading)).

## `build-serve`

```sh
protobase build-serve [--out dist/protobase-serve.js] [--bun]   # or, in this repository: bun run build:serve
```

Bundles the serve runtime (`@protobase/cli`'s `src/serve/main.ts`) and all its dependencies into one file, about 3 MB. A host needs Bun and this file, nothing else. `--bun` has Bun's bundler write the file, as for [`build`](#build), and needs `bun` on `PATH`; the `protobase` image is built from such a file. The file carries the Protobase version it was built from, which decides [the bundles it serves](/reference/versioning/#bundles-and-runtimes).

```sh
bun --no-install protobase-serve.js [serve] <bundle>                 # the folder: the app and the API; the config module: the API
bun --no-install protobase-serve.js migrate <bundle>                 # apply the bundle's migrations to DATABASE_URL
bun --no-install protobase-serve.js create-admin <bundle> <email>    # --generate-password or --password-stdin
```

`migrate` runs none of the app's code and needs only `DATABASE_URL`; `create-admin` loads the app with its settings and refuses an auth schema that is behind. Given the folder, the runtime serves the bundle's own copy of the app. [Deploy](/guides/deploy/#a-self-hosted-image) puts the three in a self-hosted image.

## `serve`

```sh
bun --no-install protobase-serve.js <bundle>/protobase.config.js   # production, under Bun: the API
protobase serve <bundle>/protobase.config.js                       # the same, with the CLI on Node or Bun
protobase serve <bundle>                                           # the whole bundle as a host serves it, e.g. bun run --cwd examples/erp serve
```

Serves the API of a bundle from `protobase build` and owns the process around it. Given the bundle folder, `protobase serve` also serves its UI by [the manifest's rules](#the-manifest), so a bundle can be checked locally exactly as the host will serve it.

**Its own shell.** Given the bundle folder, `protobase serve` serves the manifest's `shell.paths`, the root and navigations from a shell of its own when it has one: the folder `PROTOBASE_SHELL` names, else the prebuilt shell of the installed `@protobase/ui` (none when the CLI runs from this repository's sources). It does so only when every plugin of the bundle loads in that shell's release; otherwise it serves the bundle's copy. Its startup output says which (`app      the app of Protobase 0.12.3 from ...`). The plugins, the theme and the API always come from the bundle.

| Variable | |
| --- | --- |
| `DATABASE_URL` | the API's pool (Kysely over `pg`, 10 connections); not needed when the config exports `db` |
| `PROTOBASE_DB_CONNECTIONS` | the connections that pool opens, such as the database's limit for the app; default 10. [API functions](/guides/api-functions/) and [jobs](/reference/jobs/) hold at most one less, so a long import leaves a connection to page and API requests |
| `PORT` | default 8787 |
| `REQUEST_LOG` | `true` logs every request; default `false` |
| `PROTOBASE_SMTP_URL` | the SMTP server for password-reset mail, emailed sign-in and two-factor codes and the app's own [email](/reference/email/), credential included: `smtp://user:password@host:587` (STARTTLS when offered) or `smtps://...:465`; without it they are off ([Password reset](/reference/auth/#password-reset), [Emailed sign-in codes](/reference/auth/#emailed-sign-in-codes)) |
| `PROTOBASE_MAIL_FROM` | the sender of that mail, a plain address such as `noreply@admin.example.com`; set with `PROTOBASE_SMTP_URL` or not at all |
| `PROTOBASE_APP_NAME` | the app's name, such as `Property Finder`: what its auth emails, its sidebar, its browser tabs and the [installed app](/reference/installable-app/) call it, and the sender's display name of its mail, over [`appName`](/reference/auth/#configuration) |
| `PROTOBASE_SIGN_IN_ISSUER`, `PROTOBASE_SIGN_IN_CLIENT_ID`, `PROTOBASE_SIGN_IN_CLIENT_SECRET` | an OpenID Connect provider people who have an account can sign in with; all three or none. `PROTOBASE_SIGN_IN_PROVIDER` and `PROTOBASE_SIGN_IN_NAME` are optional ([Platform sign-in provider](/reference/auth/#platform-sign-in-provider)) |
| `PROTOBASE_OPERATOR_ISSUER`, `PROTOBASE_OPERATOR_CLIENT_ID`, `PROTOBASE_OPERATOR_CLIENT_SECRET` | the OpenID Connect provider of the operator's staff, for [staff sign-in](/reference/auth/#staff-sign-in) as people of the app; all three or none. `PROTOBASE_OPERATOR_NAME` and `PROTOBASE_OPERATOR_GROUP` are optional ([Operator provider](/reference/auth/#operator-provider)) |
| `PROTOBASE_ORIGINS`, `PROTOBASE_PASSKEY_DOMAIN` | the other origins the app is served on, comma separated, and the host new passkeys are made for ([Several origins](/reference/auth/#several-origins)) |
| `PROTOBASE_CORS_ORIGINS` | other websites whose browser code may call the API, `*` or comma separated http and https origins ([CORS](/reference/api/#cors)) |
| `PROTOBASE_ASSISTANT_URL`, `PROTOBASE_ASSISTANT_API_KEY`, `PROTOBASE_ASSISTANT_MODEL`, `PROTOBASE_ASSISTANT_BASE_URL` | the [assistant](/reference/assistant/#which-backend): a backend elsewhere, or the built-in one on OpenRouter or another OpenAI-compatible endpoint; without them there is none |
| `PROTOBASE_RUNTIME_URL` | the endpoint behind the top bar's [runtime update button](/reference/versioning/#runtime-updates), such as a hosting platform's; without it there is no button |
| `PROTOBASE_SENTRY_DSN` | the DSN of a Sentry-compatible error tracker the app's server and admin app send their errors to, after `options.errorReporting` ([Error reporting](/reference/api/#error-reporting)); without it nothing is sent |
| `PROTOBASE_MAP_STYLE_URL` | the URL of the MapLibre style the record page's [maps](/reference/ui-config/#maps) are drawn with, after `options.maps`; without it there are no maps |
| `PROTOBASE_SOURCES` | other Protobase APIs whose resources the app draws as its own, a JSON list of `{ "url", "label", "resources", "roles"? }` after `options.sources` ([Remote resources](/reference/remote-resources/#declaring-a-source)) |
| `PROTOBASE_FILES_<NAME>`, `PROTOBASE_FILES_RETENTION`, `PROTOBASE_FILES_SECRET` | [file providers](/reference/files/#providers) and their settings, over `files` in the config; a bucket's credentials in `PROTOBASE_FILES_<NAME>_ACCESS_KEY_ID` and `_SECRET_ACCESS_KEY` |
| `PROTOBASE_FILES_CLEANUP_MINUTES` | minutes between runs of the [scheduled file deletes](/reference/files/#deleting-files), default 60; 0 leaves them to `protobase files cleanup` or the platform |
| `PROTOBASE_ENCRYPTION_KEY`, `PROTOBASE_ENCRYPTION_PREVIOUS_KEYS` | the key [encrypted fields](/reference/data-config/#encrypted-fields) are sealed with, 32 random bytes in base64 (`openssl rand -base64 32`), and the comma separated keys they were sealed with before, which still open them |
| `PROTOBASE_JOBS` | `false` runs none of the app's [jobs](/reference/jobs/) in this process, which still enqueues them; default `true` |
| `PROTOBASE_STARTUP_CHECKS` | `false` skips the startup reads of the auth, changes, computed columns, webhooks and jobs schemas, which make a start slower; default `true`. | `PROTOBASE_SHELL` | `protobase serve <bundle>` only: a shell folder, such as the `/opt/protobase/shell` of a protobase image or `@protobase/ui`'s `dist/shell`, to serve the bundle's app from (see [its own shell](#serve)) |
| `PROTOBASE_TRUSTED_PROXIES` | the proxies in front of the server, addresses or CIDR ranges, comma separated: a request from one of them names its client in `X-Forwarded-For`; without it the client is the connection's address ([Client addresses](/reference/auth/#client-addresses)) |
| `PROTOBASE_MOBILE_SIGNING_KEY` | an RSA private key of at least 2048 bits, PEM, its newlines real or written `\n`, that signs every file of the [mobile release](#mobile-releases) in `X-Signature`, for an app whose updater checks signatures with the matching public key; another kind of key, or a shorter one, stops startup |
| `PROTOBASE_JOBS_DRAIN_TOKEN` | the operator's bearer token for `POST /api/jobs/drain`, which [runs the due jobs](/reference/jobs/#hosts-that-sleep) of a host that lets the app sleep; without it there is no such endpoint |

Better Auth and other settings are the project's own variables (`BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, ...), read by its config. `protobase serve` also loads the nearest `.env`, like `dev`; the runtime takes the environment as it is.

- **Routes:** `createAdmin` (`/api/v1`, `/api/meta`, `/api/functions/*`, `/api/auth/*`, ...) and `GET /health`, which answers `{"status":"ok"}` without a token and without touching the database. The runtime never serves the UI; `protobase serve <bundle>` serves `public/` for every path outside the manifest's `api` and `/.well-known/webauthn`, after `/health`, with `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`, so no other site frames its pages.
- **Plugins:** the runtime reads the manifest's `plugins`: `/api/meta` names them, and a view that shows a field with one of their [field types](/reference/plugins/#field-types) that does not show the field's storage type stops startup, naming the view, the field and what the field type shows.
- **Version:** before loading the config module, the runtime reads `protobase.bundle.json` beside it and refuses a bundle built by a Protobase version it does not serve, or one without a version, with an error naming both versions (see [Versioning](/reference/versioning/#bundles-and-runtimes)). A config module needs its manifest beside it.
- **Startup:** a bundle without a default export, `config` or `authenticate`, or with an `options.basePath` other than `/api/v1`, stops startup with a one-line error and exit code 1, as does a missing `DATABASE_URL`, an auth schema that lacks a table or column, or still has the OAuth tables of [MCP](/reference/auth/#oauth-for-mcp-clients) with `mcp` off (see [`auth migration`](#auth-migration)), a resource whose [events](/reference/events/) or [history](/reference/history/) lack their triggers or have out-of-date ones, or a missing history or [comments](/reference/comments/#the-table) table, a [rollup or formula field](/reference/data-config/#rollups-and-formulas) whose column or trigger is missing or out of date, a jobs schema that is missing or behind for a config with [jobs](/reference/jobs/#the-jobs-schema) (see [`migration`](#migration)), an [AI field or action](/reference/ai/#the-model) without a model key, [encrypted fields](/reference/data-config/#encrypted-fields) without a key, or another resource over their column, or a taken port; `PROTOBASE_STARTUP_CHECKS=false` skips the checks of those schemas and the key. `protobase serve listening on port <port>` means it is ready.
- **Jobs:** with [jobs](/reference/jobs/) in the config it runs them beside the API, unless `PROTOBASE_JOBS=false`, and with `PROTOBASE_JOBS_DRAIN_TOKEN` it answers `POST /api/jobs/drain` for the operator.
- **Shutdown:** the first SIGTERM or SIGINT stops accepting connections, closes open WebSockets with 1001 (dropping any still open after 5 seconds), waits for open requests, gives running jobs 30 seconds to finish, drains the pool `serve` created (a `db` the config exports is the project's to close) and exits with 0.
- **Host modules:** under Bun, the runtime registers [the modules it supplies](#the-config-module) as virtual modules, so the bundle needs no `node_modules` for them. `protobase serve`, on Node or Bun, resolves them from the `node_modules` next to the bundle, so keep the bundle inside the project. Native packages load from the bundle's own `node_modules/` under both.
- **Read-only hosts:** nothing is written: no install (`--no-install`), and for a bundle built with `--bun` no transpiling and so no transpiler cache. A bundle with `node_modules/` needs its folder mounted without `noexec`, since its add-ons are mapped as executable code.

### Mobile releases

With a `mobile` section, the server serves the [mobile app](/guides/mobile-app/) a newer copy of its files, for its live updater, so the app gets UI changes without a store release. The release is what the server serves the web, composed at startup: every file of `public/`, with the server's own shell where `protobase serve` uses it, and `index.html` naming the API origin, the auth `baseURL` (https, or plain http to `localhost`, `127.0.0.1` or `[::1]`). There is none when the server serves the API alone, has no such `baseURL`, or the bundle names no `native`.

- `GET /api/mobile/release?fingerprint=<native fingerprint>&shell_version=<x.y.z>` answers `{ "bundleId", "url", "required" }`: the release's id, a hash of its files, and its absolute base URL, both `null` when the release does not run on the asking binary, whose native fingerprint must equal the release's. `required` is true when the shell the app runs no longer works with the server's API: below 1.0 another minor, from 1.0 another major. A missing fingerprint or a shell version that is no x.y.z version gets 400.
- `GET /api/mobile/releases/<bundleId>?href=<file>` serves the release's file `<file>`, such as `assets/index-abc123.js`, and with `href=capawesome-live-update-manifest.json` its manifest, a JSON array of `{ "href", "checksum", "sizeInBytes" }`. Each comes with its sha256 in hex in `X-Checksum` and, with `PROTOBASE_MOBILE_SIGNING_KEY`, its signature in `X-Signature`. Any other file, or another release's id, gets 404.

## `worker`

```sh
protobase worker <bundle>   # a bundle from `protobase build`: its folder or its protobase.config.js
```

Runs the bundle's [jobs](/reference/jobs/), and the delivery of its [events](/reference/webhooks/#delivery-and-retries), and nothing else, until SIGTERM or SIGINT, which let running jobs finish for 30 seconds as `serve` does. It checks the bundle's version and the jobs schema at start like `serve`, reads the `.env` nearest the current directory and needs `DATABASE_URL` unless the config exports `db`. Run it beside a `serve` with `PROTOBASE_JOBS=false`, from the same bundle. `protobase worker running <n> jobs` means it is ready.

## `files cleanup`

```sh
protobase files cleanup            # the project in the current directory
protobase files cleanup <bundle>   # a bundle from `protobase build`: its folder or its protobase.config.js
```

Runs the [scheduled file deletes](/reference/files/#deleting-files) that are due: replaced and cleared files past their retention, and uploads nobody saved. A file a row references again is kept. It prints each file it deleted or kept. It reads the `.env` nearest the current directory and needs `DATABASE_URL` unless the config exports `db`. `protobase serve` runs the same every hour; this is for cron, or a host that turns that off.

## `encryption status`

```sh
protobase encryption status            # the project in the current directory
protobase encryption status <bundle>   # a bundle from `protobase build`: its folder or its protobase.config.js
```

Reads every [encrypted field](/reference/data-config/#encrypted-fields)'s column and prints its values per key id, the current one marked, its plaintext values, and each value that does not decrypt by record key, with why (`not-encrypted`, `malformed`, `unknown-key`, `failed-authentication`) and never the value. It also prints the history rows and undispatched changes that still hold a field's old values, encrypted values in fields that are not encrypted, and foreign keys `on update cascade` that change a record's key. It writes nothing, so it shows what `apply` would do. It exits with 1 when anything is plaintext, under a previous key, unreadable, misplaced or left in history, so a script can gate on it. It takes the keys from the environment and the `.env` nearest the current directory, like `serve`, and needs `DATABASE_URL` unless the config exports `db`.

## `encryption apply`

```sh
protobase encryption apply [bundle]
protobase encryption apply --rebind people --from-table persons          # after a table rename
protobase encryption apply --rebind people.iban --from-column bank_iban  # after a column rename
```

Encrypts every plaintext value of the encrypted fields with the current key, encrypts values under a previous key again with it, and removes the fields' old values from the [history](/reference/history/) and the changes not yet dispatched. Values that do not decrypt are listed and left as they are; it exits with 1 when any remain. Its writes are captured by no event, history or webhook, and a value a write changes while it runs is left to that write. It refuses to run when a column holds values under none of its keys, such as with another key than the app's.

`--rebind <resource>[.<field>]` with `--from-table <table>` (as `.table()` wrote it) or `--from-column <column>` also takes values sealed where the field was before a rename, and seals them where it is now; running it again rebinds nothing more. It refuses a former place another resource still encrypts.

Run it at update time, after the migrations and before the new version serves, and again once an old version that wrote plaintext has stopped. It works over one database connection, so a project's own `db` with a pool of one is enough.

## `users`

```sh
protobase users create <email> [--name <name>] [--role <role>] [--password-stdin | --generate-password | --no-password] [--github-id <id>]
                       [--organization <slug> [--org-role <role>] [--app-roles <a,b>]]
protobase users list
protobase users roles
protobase users set-role <email> <role>
protobase users disable <email>   # and: enable <email>
protobase users delete <email> [--yes]
```

Run inside a project whose `protobase.config.ts` exports `auth` (Better Auth). There is no web setup page, and [open sign-up](/reference/auth/#open-sign-up), when a project turns it on, waits for the first admin: the first admin is created here. The first user is always an admin, whatever `--role` says; later users get `--role`, or the project's default role (`createAuth({ roles, defaultRole })`). `protobase users roles` lists the roles of the project; anything else is refused with that list. `set-role` also takes comma separated roles (`sales,accountant`). `--github-id` links the new user to a GitHub user id (the number, not the login), so signing in with GitHub, the app's own provider or the [platform's](/reference/auth/#platform-sign-in-provider), finds them whatever address GitHub reports; an id that signs in another user already is refused. `createUser(auth, { ..., accounts: [{ providerId, accountId }] })` does the same from code.

The password is typed at a hidden prompt with confirmation, read from stdin with `--password-stdin` (for scripts, e.g. `pass show erp | protobase users create me@example.com --password-stdin`), or generated with `--generate-password` and printed once; it must be 12 to 128 characters, the length the app requires of every new password. `--no-password` makes an account without one, which signs in by [emailed code](/reference/auth/#emailed-sign-in-codes), passkey or a sign-in provider, as with an app whose [sign-in policy](/reference/auth/#sign-in-policy) turns passwords off. A password is never accepted as an argument, since it would end up in shell history. `users list` prints email, role and creation date (and `disabled` for banned users), never credentials.

`delete` asks you to type the email back (or pass `--yes`), and needs a terminal otherwise. `delete`, `set-role` and `disable` refuse to touch the last admin, so the project cannot lock itself out. `disable` bans the user and revokes their sessions; tokens already issued stop working on their next request, and `protobase token` refuses disabled users. With [MCP](/reference/auth/#oauth-for-mcp-clients) on, it also disconnects their MCP clients. `enable` lifts the ban; the clients have to be allowed again. `protobase dev` prints "No users yet. Create the first admin with: protobase users create you@example.com" at startup while the user table is empty.

With [organizations](/reference/auth/#organizations), `--role` is the user's global role (none by default) and `--organization` adds the new user to an organization, with `--org-role` (`owner`, `admin`, or `member`, the default) and `--app-roles` there.

## `organizations`

```sh
protobase organizations list
protobase organizations create <name> --owner <email> [--slug <slug>] [--id <id>] [--members all]
protobase organizations add-member <organization> <email> [--org-role <role>] [--app-roles <a,b>]
protobase organizations set-roles <organization> <email> [--org-role <role>] [--app-roles <a,b>]
protobase organizations remove-member <organization> <email>
protobase organizations add-app-role <role> --to owners
```

For a project with [organizations](/reference/auth/#organizations); `<organization>` is a slug or an id. The host acts as a superuser, so it may give any role. `create` makes `--owner` the owner with every app role; `--id` keeps an existing tenant value, and `--members all` adds every other user, superusers as owners and everyone else as a member with their global roles moved onto the membership, for an app that ran as one organization. `remove-member` and `set-roles` refuse to leave an organization without an owner. `add-app-role` gives a role the project added later to every owner.

## `migration`

```sh
protobase migration [--dir db/migrations] [--extend <dir>]
```

Writes what the database still needs for every feature the config enables, as the project's next migrations in `--dir`, one file per feature: the auth schema when `protobase.config.ts` exports `auth` (`NNN_auth.sql`, as [`auth migration`](#auth-migration) writes it), the [jobs schema](/reference/jobs/#the-jobs-schema) when the config has jobs or a resource has events, history, comments or an [AI field](/reference/ai/) (`NNN_jobs.sql`), the [capture of events](/reference/events/#migrations-and-startup) and the [history table](/reference/history/#the-table) (`NNN_changes.sql`), the columns of [rollup and formula fields](/reference/data-config/#rollups-and-formulas) and the triggers that keep the rollups (`NNN_computed.sql`), the role the [assistant's read-only queries](/reference/assistant/#the-built-in-backend) run as, when it finds the built-in assistant's key (`NNN_query.sql`), the [comments table](/reference/comments/#the-table) (`NNN_comments.sql`), and the [webhook subscriptions](/reference/webhooks/#subscriptions-in-the-admin-app) of `webhooks()` (`NNN_webhooks.sql`). It compares the database, with the project's migrations applied, with the config, merged with the configs it extends and those of `--extend` as `dev` merges them, and writes nothing when the database is current. Apply the files with the project's other migrations. It reads the `.env` nearest the current directory and needs `DATABASE_URL` unless the config exports `db`.

```sh
bun run db:migrate                # the database at the project's current schema
bun run protobase migration       # writes db/migrations/NNN_auth.sql, NNN_jobs.sql, NNN_changes.sql, ... for what the config enables
bun run db:migrate                # applies them
```

## `auth migration`

```sh
protobase auth migration [--dir db/migrations] [--name auth]
```

Run inside a project whose `protobase.config.ts` exports `auth`, against its database with the project's migrations applied. It compares the database with the tables, columns and indexes Better Auth needs (with Protobase's plugins and the project's own) and writes what is missing as the next migration in `--dir`: `009_auth.sql` after `008_...`. Nothing is written when the schema is current. The file only adds, never drops, except the OAuth tables of MCP once `mcp` is off; apply it with the project's other migrations. For a store with the camelCase names of Protobase 0.6 it writes their rename to snake_case instead, and the startup check asks for that. See [migrations](/reference/auth/#migrations).

## `import supabase`

```sh
protobase import supabase [<connection> | --source-env <variable>] [--env DATABASE_URL] [--dir db/migrations] [--config config]
                          [--storage-url <url>] [--storage-key-env SUPABASE_SERVICE_ROLE_KEY] [--yes]
```

Turns a Supabase project's database into the project in the current directory, in two runs with the project's migrations between them. It needs PostgreSQL's `pg_dump` and `psql` on `PATH`, of the Supabase database's major version or newer, and reads the `.env` nearest the current directory for the project's database (`--env`).

1. **The first run** takes the Supabase database's connection string, for its `postgres` role (the session pooler's or the direct one; the transaction pooler cannot hold the snapshot the dumps share). It fails unless the database has Supabase's `auth` and `storage` schemas and its `supabase_admin` role, and while `auth.users` has single sign-on (SAML) users, which Supabase opens only through their identity provider and Better Auth would find by email: merge or delete them in Supabase first. It notes the Supabase CLI's `supabase/config.toml`, `supabase/migrations/` and `supabase/functions/` when the checkout has them. It converts `supabase/functions` into the project's `functions/` (see [functions moved from Supabase](/guides/api-functions/#functions-moved-from-supabase)): `Deno.serve(handler)` and std's `serve(handler)` become `export default defineFunction({ supabase: true }, { fetch: handler })`, an existing default export is wrapped the same way, so each function also answers at `/api/sb/functions/v1/<name>`, `npm:`, `jsr:` and esm.sh imports become bare imports of packages it adds to `package.json`, `Deno.env.get(name)` becomes `process.env[name]`, `EdgeRuntime.waitUntil` becomes `waitUntil` of `@protobase/server`, a function with `verify_jwt = false` in `config.toml` becomes public (`{ public: true, supabase: true }`), and `_shared` and the like are converted beside them. It stops before anything else when `functions/` already has one of their names. It dumps `auth`, `storage` and every schema the app made, schema and data apart, as of one snapshot, leaving out the platform's own migration tables, and writes the schemas as the project's next migration, `NNN_supabase_schema.sql`. It asks the project's database which of the app's extensions its role may create, by trying each in a transaction it rolls back: Postgres alone allows the trusted ones, Supabase's Postgres image all it allowlists, such as pg_net, pgmq and Vault. The migration creates those first, then, where pg_net is among them and the app has Database Webhooks, the `supabase_functions.http_request` function their triggers call, over pg_net; then the dump without what fails there, as comments: grants and default privileges for `dashboard_user`, `supabase_*`, `authenticator` and `postgres`, statements about the `public` schema, Realtime's publication, pgsodium's security labels, the views that decrypt with it and the triggers that encrypt with it, database webhooks without pg_net, functions in plv8, plls or plcoffee where the database has no such language, and a timescaledb hypertable's insert-blocking trigger. It then writes `NNN_supabase_users.sql`, the nullable columns Better Auth needs on `auth.users` (`name`, `email_verified`, `image`, `app_role`, `banned`, `ban_reason`, `ban_expires`) and GoTrue's `'authenticated'` as the default of `role` and `aud`. It points the app at `auth.users`: `auth/auth.ts` gets `...supabaseUsers` in its one `createAuth({` call, from the new `auth/supabase-users.ts` (the table, `role` in `app_role`, `raw_user_meta_data` as the metadata, bcrypt hashes and UUID ids; see [an existing users table](/reference/auth/#an-existing-users-table)). It removes the migrations `protobase auth migration` or `protobase migration` wrote for Protobase's own user table, since `auth.users` replaces it, and stops before writing anything when `auth/auth.ts` is missing or calls `createAuth({` other than once, or when the project's database has a schema the dump creates already, such as the `auth` schema those migrations made. The project's database needs the roles `anon`, `authenticated` and `service_role` that the dump's grants and policies name; the command makes them when its role may, and otherwise stops, naming them. The data dump goes to `supabase-import/`, which it adds to `.gitignore`, since it holds every row and the users' password hashes. Where the project's database can create Vault, pgmq and pg_cron, `supabase-import/replay.sql` holds what a dump cannot carry: Vault's secrets with their values, read decrypted since only Supabase's key opens their ciphertext, pgmq's queues with their messages, since pgmq owns their tables, and pg_cron's jobs, which live in its own schema.
2. **Apply the migration** with the project's other migrations, such as `bun run db:migrate`.
3. **The second run**, without a connection string, loads the data in one transaction, with the app's triggers off so a sign-up trigger on `auth.users` does not run again for users who already have their rows, and fails the transaction unless every table holds the source's number of rows. In the same transaction it makes Vault's secrets and pgmq's queues again through `vault.create_secret`, `pgmq.create` and `pgmq.send`, each message with its headers and the time it becomes visible. Where the project's database has pg_cron, as Supabase's Postgres image does when it serves that database, it schedules pg_cron's jobs again there with `cron.schedule`, run by the importing role, an inactive one inactive. Elsewhere it writes each job of plain SQL as a [recurring job](/reference/jobs/#recurring-jobs) of its own in `jobs/`, of the same name, schedule and `cron.timezone`, that runs its SQL as the app's database role, tried once each time as pg_cron did, exports it from `jobs/index.ts` and adds `jobs` to `protobase.config.ts` (or writes one); they run once [`migration`](#migration) has added the jobs schema. Recurring jobs wake an app that sleeps, so they run where a host stops an idle app too. A job that calls what the database lacks, such as pg_net's `net.http_*`, `cron` or Vault, an inactive one and a schedule recurring jobs do not take, such as `30 seconds` or `$`, stay in the report, as does a job of another database. It loads only into empty tables, deletes the data dump and the replay, runs [`scaffold`](#scaffold) on the imported tables of the app's schemas (not `auth` or `storage`), giving the tables of the `supabase_realtime` publication [`.live()`](/reference/live/) so [`/api/sb/realtime/v1`](/reference/supabase-realtime/) keeps sending their `postgres_changes` once [`migration`](#migration) has written their capture triggers, writes Better Auth's other tables next to `auth.users` as [`auth migration`](#auth-migration) does (`NNN_auth.sql`), then `NNN_supabase_accounts.sql`, and writes `supabase-import/report.md`: the rows loaded, the imported tables' size against the Starter plan's 500 MB, each sign-in provider's identities, what it made again, the tables it made live, and what needs a person: the pg_cron jobs it could not carry over, each with why, Realtime tables it made no resource of, Vault secrets by name and pgmq queues where the database has no such extension (and partitioned queues), the columns pgsodium encrypts, still holding Supabase's ciphertext, whose values to export decrypted in Supabase before declaring them [`.encrypted()`](/reference/data-config/#encrypted-fields) and running [`encryption apply`](#encryption-apply), the extensions it cannot create, hypertables and plv8, plls or plcoffee functions to convert, triggers that call out over HTTP without pg_net, the converted Edge Functions with the packages to install and the code the conversion left (`deno.land/x` imports, Deno's file, KV and WebSocket APIs, `Supabase.ai`), and the indexes [`doctor`](#doctor) finds missing. `NNN_supabase_accounts.sql` fills the user columns from what Supabase Auth recorded and leaves them empty where it recorded nothing: the name from `raw_user_meta_data`'s `full_name` or `name`, the picture from its `avatar_url` or `picture`, `email_verified` from `email_confirmed_at`, and a ban from `banned_until`, which Better Auth lifts once it has passed. It gives each password of a confirmed address, as Supabase hashed it, a `credential` account (a user who never confirmed theirs signs in by code or resets the password, since GoTrue refused their password sign-in too), and each identity of a social provider an account under Better Auth's name for it (`azure` is `microsoft`, keyed on the `oid` claim; `linkedin_oidc` is `linkedin`, `slack_oidc` is `slack`, `x` is `twitter`), unless its user has an address they never confirmed, since GoTrue refused that sign-in too. Email, phone, anonymous and single sign-on identities, sessions, MFA factors and passkeys do not carry over.
4. **Apply the migrations** again. Supabase's users then sign in with their own passwords, and with a social provider once it is in `createAuth`'s `socialProviders`; new users get a UUID in `auth.users`, so the app's triggers there run for them.

5. **Storage's files**: with `--storage-url https://<ref>.supabase.co` and the project's secret key in the variable `--storage-key-env` names, `SUPABASE_SERVICE_ROLE_KEY` by default, the second run, or any run after it, copies the bytes of every object in `storage.objects` from the Supabase project's Storage API into the app's [Storage file provider](/reference/supabase-storage/#where-things-are-kept), where [`/api/sb/storage/v1`](/reference/supabase-storage/) serves them, with the type and cache control the rows recorded. It streams each object, checks its byte count against the size Supabase recorded and its MD5 against the ETag where that is one, and deletes a copy that does not match. It first prints each bucket's size and stops when what is left to copy and what the provider holds exceed the provider's `max_bytes`, unless `--yes`. An object that fails does not stop the rest; the run then fails, listing them in `supabase-import/storage.md`, and a rerun copies only what the provider does not hold yet. The key goes only in the requests' headers, never in a file.

An agent with the `supabase-move` skill of [`skill install`](#skill) finishes what the report leaves: it rewrites each item, checking the project's database for the extensions an item needs, and runs `doctor` and the typecheck until both pass, leaving the values of Vault's secrets for you to enter.

Remove `supabase-import/` to import again.

## `mobile`

```sh
protobase mobile run <ios|android> [--api <url>] [--target <id>] [--live] [--port 5173] [--extend <dir>]
protobase mobile open <ios|android> [--api <url>] [--extend <dir>]
protobase mobile build <ios|android> --app-version <x.y.z> --build-number <n> [--api <url>] [--out mobile-release] [--extend <dir>]
                       [--team <id> [--certificate <name> --profile <name>]]
```

Builds the project in the current directory as an iOS or Android app with Capacitor, from the `mobile` section of its `protobase.config.ts`; without one it stops and says what to add. See [A mobile app](/guides/mobile-app/).

- It installs `@protobase/mobile`, of the CLI's version, which pins Capacitor and its plugins, with the section's `plugins` into `.protobase/mobile/` with npm, when that changed. It builds the app's files as [`build`](#build) does and keeps only `public/`, its `index.html` naming the API origin; writes `capacitor.config.json`, compiling in only the section's plugins; and generates the platform's native project again, replacing the last one.
- `--api` is the server the app calls, the project's auth `baseURL` by default: an http or https origin, plain http only to `localhost`, `127.0.0.1` and, on iOS, `[::1]`, or on Android `10.0.2.2`. An Android app calling `localhost` gets the port forwarded.
- `run` runs the app on `--target`, or asks for one. With `--live` it opens `protobase dev` on `localhost:--port` instead of its own files. `open` opens the native project in Xcode or Android Studio.
- `build` makes a signed release, an `.aab` (Android) or `.ipa` (iOS), and copies it to `--out`, which ignores itself in git when the command creates it, as `<appId>-<version>-<build number>`. Android signs through Gradle with the keystore, alias and passwords in `PROTOBASE_ANDROID_KEYSTORE`, `PROTOBASE_ANDROID_KEY_ALIAS`, `PROTOBASE_ANDROID_KEYSTORE_PASSWORD` and `PROTOBASE_ANDROID_KEY_PASSWORD`; iOS runs Capacitor's build with `--team`, and `--certificate` with `--profile` for manual signing.
- A release calls an https server that is not this machine, and `--app-version` (one to three numbers) and `--build-number` (1 to 2100000000) are required.
- npm and Capacitor get the CLI's environment without any variable named in the current directory's `.env*` files, nor the four `PROTOBASE_ANDROID_*` signing variables, which only Gradle gets, and with `CI=true`, which keeps Capacitor's telemetry off.
- It prints the workspace, the API origin and the native fingerprint, which the app also sends in its user agent as `ProtobaseNative/<fingerprint>`: a hash of the native packages `@protobase/mobile` pins, at their versions, and the section's `plugins`, at the versions they give. A [mobile release](#mobile-releases) runs only on a binary of its own fingerprint. A Protobase release that pins the same native packages keeps it; raise a plugin's version when the app's files start using a newer native feature of it, which changes it.
- The app's files carry the live updater's manifest of them, so an update downloads only the files that changed.

## `token`

```sh
protobase token <email> [--ttl 15m]
```

Prints a bearer token (JWT, signed with the project's Better Auth keys, same claims as a browser token) for an existing user. The lifetime is `30s`, `15m`, `24h`, ... up to 24 hours, default 15 minutes. Only the token goes to stdout and errors go to stderr, so it composes in scripts:

```sh
curl -H "Authorization: Bearer $(protobase token me@x)" http://localhost:5173/api/v1/orders?page_size=1
```

## `skill`

```sh
protobase skill install [name]
```

Copies the agent skills of this CLI's version into the current project, or only the one `name` names. `protobase`, the protobase agent skill, goes to `.agents/skills/protobase/` (read by Codex, Cursor, OpenCode and Amp) and `.claude/skills/protobase/` (read by Claude Code): a short `SKILL.md` with the everyday workflow and the checks before calling a change done, and the guides and reference of this version as files it points to. `protobase-cloud` goes to `.agents/skills/protobase-cloud/` and `.claude/skills/protobase-cloud/`: how an app hosted on protobase-cloud deploys from GitHub, how to check that a change went live, and why a deploy failed. `supabase-move` goes beside them: it has an agent work through `supabase-import/report.md` after [`import supabase`](#import-supabase), item by item, until `doctor` and the app's typecheck pass. Each replaces an earlier copy, and refuses to touch a folder of its name that holds another skill. Commit the folders, and run the command again after upgrading the `@protobase` packages. The skills also ship in `node_modules/@protobase/cli/skills`, where the `skills` CLI's `experimental_sync` finds it.

## ERP example

```sh
bun run db:up && bun run --cwd examples/erp db:migrate && bun run --cwd examples/erp db:seed --scale small
bun run --cwd examples/erp protobase scaffold postgres://protobase:protobase@localhost:55432/protobase \
  --yes --ui --exclude auth --exclude public.schema_migrations --exclude public.seed_info
bun run --cwd examples/erp protobase doctor postgres://protobase:protobase@localhost:55432/protobase
```

Always pass `--exclude auth`: the ERP keeps Better Auth's users, sessions and signing keys in the `auth` schema of the same database, and scaffolding them would expose credentials through the admin API.

The integration test (`packages/cli/tests/scaffold/scaffold.integration.test.ts`) scaffolds into a temp folder and is skipped when the database is unreachable.
