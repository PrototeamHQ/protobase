An app sends mail through one SMTP server: Protobase's own mail ([password reset](/reference/auth/#password-reset), [emailed sign-in codes](/reference/auth/#emailed-sign-in-codes), [invitations](/reference/auth/#organizations), staff sign-in notices and [mentions in comments](/reference/comments/#mentions)) and the emails the app defines itself. Both are React components, rendered to HTML with a plain-text part beside it.

## Configuration

| Variable | |
| --- | --- |
| `PROTOBASE_SMTP_URL` | The SMTP server, credential included: `smtp://user:password@host:587` (STARTTLS when the server offers it) or `smtps://user:password@host:465` (TLS from the start). |
| `PROTOBASE_MAIL_FROM` | The sender, a plain address such as `noreply@shop.example.com`. The client greets the server with its domain; a `?name=` on the URL overrides that. |
| `PROTOBASE_APP_NAME` | Optional: the app's name, such as `Shop`, which mail clients show as the sender's name (`Shop <noreply@shop.example.com>`). [`createAuth`'s `appName`](/reference/auth/#configuration), when set, takes its place. Without either the sender has no name. |

Set both or neither. One without the other, a URL that is not `smtp://` or `smtps://`, or a sender that is not a plain address stops the app at startup. Without them mail is off: password reset and emailed codes are not offered, a job's `mail` is `undefined`, and sending an app's email rejects.

`protobase dev` and `protobase serve` read them from the environment or the nearest `.env`; a host passes them like `DATABASE_URL`. In development, a mail catcher such as [Mailpit](https://mailpit.axllent.org) shows what the app sends without delivering it:

```sh
docker run -d -p 8025:8025 -p 1025:1025 axllent/mailpit   # its inbox is http://localhost:8025

# .env
PROTOBASE_SMTP_URL=smtp://localhost:1025
PROTOBASE_MAIL_FROM=noreply@shop.example.com
```

A project that delivers mail another way passes a `mailer`, `{ send({ to, subject, text, html, headers }) }`, to [`createAuth`](/reference/auth/#password-reset) and `startJobs`, or `mailer: false` to turn mail off whatever the environment says. A template's `send` takes one too, see [Templates](#templates).

## Protobase's own mail

The auth emails (sign-in, two-factor and sign-up codes, the note to an address that asked to sign up while it has an account, password reset, invitations and staff sign-in notices) and the email to someone a [comment mentions](/reference/comments/#mentions) are built with React Email's components: a heading, the message, one code or button, and a footer naming the app.

- They name the app by [`appName`](/reference/auth/#configuration), and link it on the origin the request came to: the footer links its home page, and the note to an address that has an account links its sign-in page.
- The plain-text part has each code on a line of its own and each link in full.
- React Email and the templates are loaded when the first auth email is sent, so an app that sends none never loads them and the server starts as fast without them.

## Templates

An email of the app's own is `defineEmail`: a name, a subject, and a React component whose props are the email's data. The components of [React Email](https://react.email) render the tables and inline styles email clients need. `@protobase/server` brings React's renderer; the project adds the components, and React for its JSX, which a project with a UI has already:

```sh
bun add react-email react
bun add -d @types/react
```

| `defineEmail` option | |
| --- | --- |
| `name` | Names the email in errors. |
| `subject` | The subject line, or a function of the data that makes it. |
| `component` | The body, a React component of the data. It is rendered with React Email's `render` to the HTML part; the plain-text part is made from that HTML, leaving out what React Email marks to skip, such as `<Preview>`. |
| `headers` | Optional: more header fields, or a function of the data that makes them. A value is one line. |

The template that comes back has two methods, both typed by the component's props:

- `render(data)` gives `{ subject, html, text, headers }` without sending anything: for a test, or to look at the result.
- `send(to, data, mailer?)` renders and sends it, through `mailer` when given (a job's `mail`), otherwise through `PROTOBASE_SMTP_URL`. It rejects when mail is off or the server refuses the message.

React and React Email's renderer are loaded on the first email rendered, not when the app starts.

Mail an app sends in bulk, such as alerts or newsletters, should carry a one-click unsubscribe link, which Gmail and Yahoo expect of bulk senders ([RFC 8058](https://www.rfc-editor.org/rfc/rfc8058)): a `List-Unsubscribe` header with the recipient's own link, and `List-Unsubscribe-Post`. The link must stop the mail on a `POST` without a sign-in, such as an [API function](/guides/api-functions/) that takes a token of the recipient's in its address:

```ts
headers: ({ unsubscribeUrl }: Digest) => ({ 'List-Unsubscribe': `<${unsubscribeUrl}>`, 'List-Unsubscribe-Post': 'List-Unsubscribe=One-Click' }),
```

### The look of Protobase's own mail

`@protobase/server/email` exports the components Protobase's own mail is built from, so an app's emails can look the same: a white card on grey with a teal action.

| Component | |
| --- | --- |
| `EmailLayout` | The whole email: `preview`, the line inboxes show after the subject; `heading`; the message as its children; and a footer naming `app`, linked to its home page. `app` is `{ name, url }`. |
| `EmailButton` | The email's one action: a button to `href`, and the label with the link in the plain-text part. |
| `EmailCode` | A code to type in, on a line of its own. |
| `EmailNote` | A remark below the message, such as why the recipient gets the email. |

```tsx
import { defineEmail } from '@protobase/server'
import { EmailButton, EmailLayout, EmailNote, type MailingApp } from '@protobase/server/email'
import { Text } from 'react-email'

type RepairReady = { app: MailingApp; customer: string; bike: string; url: string }

const RepairReadyEmail = ({ app, customer, bike, url }: RepairReady) => (
  <EmailLayout app={app} preview={`Your ${bike} is ready for pickup`} heading="Ready for pickup">
    <Text>Hi {customer}, your {bike} is ready.</Text>
    <EmailButton href={url}>See the repair</EmailButton>
    <EmailNote>You get this email because you brought your bike in for repair.</EmailNote>
  </EmailLayout>
)

export const repairReady = defineEmail({ name: 'repair-ready', subject: 'Your bike is ready', component: RepairReadyEmail })
```

They are apart from `@protobase/server` itself, so an app that imports none never loads React Email's components.

## In a bundle

A [bundle](/reference/cli/#the-config-module) gets React and React Email's renderer from the serve runtime, as it gets `@protobase/server` and `@protobase/server/email`, so an email's component and the renderer share one React and hooks such as `useContext` work. React Email's other components are inlined, though `@protobase/server` uses them too: it loads them only to send its own mail, so the runtime does not supply them. Its `<Tailwind>` component needs `tailwindcss`, which the runtime does not supply, so a served config cannot use it: style with `style` props instead.
