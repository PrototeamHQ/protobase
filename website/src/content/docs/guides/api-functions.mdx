The [REST API](/reference/api/) covers reading and writing records. For anything else you write a function: a webhook from a payment provider, a button that makes three writes and then texts the customer, an endpoint for another app. Each function is one file in the project's `functions/` folder, served at `/api/functions/<name>`.

If you have used Supabase Edge Functions, this will feel familiar. A function is a Web-standard handler that takes a `Request` and returns a `Response`. Only signed-in callers get in unless the function says otherwise. It has a data client that acts as the caller, and the raw database for privileged work.

The examples below come from Pip's bike shop (see [From a table to an admin](/guides/table-to-admin/)). The repository compiles and tests every one of them.

## A first function

<Code code={hello} lang="ts" title="functions/hello.ts" />

`protobase dev` serves it at `http://localhost:5173/api/functions/hello`. A change reloads it on the next request, and a new file appears after the next change inside the project. `protobase build` bundles the functions into the deploy bundle, and `protobase serve` serves them the same way. Call it with a token:

```sh
curl -H "Authorization: Bearer $(protobase token pip@example.com)" http://localhost:5173/api/functions/hello
# {"message":"Hello, 9f3c…","roles":["admin"]}
curl -i http://localhost:5173/api/functions/hello
# HTTP/1.1 401 Unauthorized, an application/problem+json body like every other refusal
```

The app's own `authenticate` checks the token, the same one that guards the REST API, so a function needs no auth code of its own. A call without a valid token is the usual `401` problem, and the handler never runs.

## Files and names

- **One function per file:** `functions/<name>.ts`, or `functions/<name>/index.ts` for a function of several files. The name is the URL segment, so it uses letters, digits, `-` and `_`.
- **Not functions:** files and folders starting with `_` (shared code, such as `functions/_shared/`), dotfiles, `*.test.ts`, `*.spec.ts` and `*.d.ts`. A folder without an `index.ts` is an error that says so.
- **The default export** is `defineFunction(...)` from `@protobase/server`, a bare `(request, context)` handler, or a Hono app. The last two need a signed-in caller.
- **Any method** reaches the function, and so does any path below its name. The request's path is the part after `/api/functions/<name>`: `/` for the function itself, `/42/advance` for `/api/functions/workshop/42/advance`. The query string and the body are passed through unchanged.
- **Only the folder:** `protobase.config.ts` names no functions; they are found in `functions/`. The functions of an [extension](/reference/config/#extensions)'s `functions/` folder are kept, and a name used by two folders is an error that names both.

## The context

The second argument of a handler (`c.env` in a [Hono app](#hono-apps)):

| | |
| --- | --- |
| `session` | The caller: `{ user: { id, roles }, tenant? }`, from the app's `authenticate`. |
| `records` | The app's resources, acting as the caller: `list`, `get`, `create`, `update`, `delete`, `softDeleteField`. |
| `db` | The Kysely instance itself. It skips every access rule, row filter and tenant scope. |
| `caller()` | Resolves to `{ session, records }`. Public functions use it to ask for a caller when they need one. |
| `acceptWebSocket(events)` | Answers a WebSocket upgrade with a socket; return its response. See [WebSockets](#websockets). |
| `name` | The function's name. |

A [public function](#public-functions-and-webhooks) has only `db`, `caller()`, `acceptWebSocket` and `name`.

## Reading and writing records as the caller

<Code code={readyForPickup} lang="ts" title="functions/ready-for-pickup.ts" />

`records` takes the same path as the REST API. The caller's access rules, row filters, field access and tenant scope apply. So do the resource's validation and the write hooks, and a record the caller may not see is not there:

| | |
| --- | --- |
| `list(resource, params?)` | A page as `GET /api/v1/{resource}` gives it: `{ items, next_page_token, total_size_estimate }`. `params` are `filter`, `order_by`, `page_size`, `page_token`, `fields` (an array), `count: 'exact'` and `show_deleted`. |
| `get(resource, key)` | `{ record, etag }`. A composite key is an array of its parts, or `a,b` as in a URL. |
| `create(resource, data)` | `{ record, etag }` of the new record. |
| `update(resource, key, data, { etag }?)` | With `etag`, it fails with `412` when the record changed after it was read. |
| `delete(resource, key, { etag }?)` | `{ record, etag }` of the record as it was. It is a soft delete when the resource has one. |
| `softDeleteField(resource)` | The field a delete sets when the resource has a soft delete, or `undefined` when a delete removes the record. |

A refusal or a missing record rejects with the problem the REST API would answer, such as `403`, `404` or `412`. Left uncaught, that problem becomes the function's response. Each call is its own transaction. Use the [batch endpoint](/reference/api/#batch-writes) when several writes must succeed or fail together.

### Checking input

`readJson(request, schema)` reads the body and checks it against a schema. It takes any [Standard Schema](https://standardschema.dev), such as zod 4, Valibot or ArkType. The result is typed. A body that is not JSON is a `400 malformed-json` problem. A body the schema refuses is a `400 invalid-body` problem with an `errors` list of `{ field, message }`. Without a schema, `readJson(request)` only parses the JSON.

### Roles

`defineFunction({ roles: ['mechanic', 'desk'] }, handler)` lets in callers with at least one of those roles. `defineFunction({ capability: 'vms.update' }, handler)` lets in callers whose roles hold all of that capability ([`roles.holds`](/reference/access/#wildcards-in-has-can-and-holds)): `*`, `vms.*` or a plain `vms.update`, but not `vms.update.own` or a `vms.update` limited to fields or rows. A wildcard means all of it, so `vms.*` needs a role that holds `vms.*` or `*`. Anyone else gets a `403 function-forbidden` problem before the handler runs. Finer rules belong in the resources' [access rules](/reference/access/), which `records` already applies.

In an app with [roles](/reference/access/) (`config/roles.ts`), a function with neither is closed like a resource without a rule: only callers whose roles hold `*`, such as `admin: ['*']`, may call it, unless `defaultAccess` is `allow`. A function for everyone signed in says so with its roles. In an app without roles, every signed-in caller may call it. A `capability` needs the app's roles, and a function takes `roles` or `capability`, not both: the server refuses to start otherwise.

## Public functions and webhooks

<Code code={paymentWebhook} lang="ts" title="functions/payment-webhook.ts" />

`{ public: true }` lets anyone call the function. A sender that signs its requests is checked with one of these helpers. Each returns the body as text once the signature matches, and otherwise throws a `401 invalid-signature` problem:

- `verifySignature(request, { secret, header, prefix?, encoding?, hash? })` checks an HMAC of the body (`hex` and `SHA-256` by default), as GitHub, Shopify and many payment providers sign. GitHub's is `{ header: 'x-hub-signature-256', prefix: 'sha256=' }`, and Shopify's is `{ header: 'x-shopify-hmac-sha256', encoding: 'base64' }`.
- `verifyStandardWebhook(request, { secret })` checks [Standard Webhooks](https://www.standardwebhooks.com) signatures, as Supabase Auth hooks, Svix and Resend send them, including the timestamp (5 minutes of tolerance by default).
- Stripe ships its own check: `stripe.webhooks.constructEventAsync(await request.text(), request.headers.get('stripe-signature'), secret)`.

A public function has no caller, so it has no `records`. Its `db` skips the tenant scope too, so filter by tenant yourself where it matters. When a function should serve anyone but treat a signed-in caller differently, `await context.caller()` resolves the caller from the request, or rejects with the `401` problem.

## WebSockets

A function can answer a WebSocket instead of a request, for a live console, a chat or an agent that keeps one connection open. It returns `acceptWebSocket(events)`:

<Code code={workshopChat} lang="ts" title="functions/workshop-chat.ts" />

A page of the app opens it with the browser's own `WebSocket`. The session cookie signs it in, so the function sees the signed-in user and their roles, as for a plain call:

```ts
const chat = new WebSocket(`${location.origin.replace(/^http/, 'ws')}/api/functions/workshop-chat`)
chat.onmessage = (event) => console.log(event.data)
chat.onopen = () => chat.send('Truing stand is free')
```

A client that is no browser sends `Authorization: Bearer <token>` with its upgrade instead. The events:

| | |
| --- | --- |
| `onOpen(socket)` | The socket is open. |
| `onMessage(data, socket)` | Text arrives as a string, binary as an `ArrayBuffer`, byte for byte. Messages come one at a time and in order. |
| `onClose(code, reason)` | Either side closed it, after the last message. |
| `recheck()` | Runs every minute while the socket is open, after the framework's own check. A `401`, `403` or `404` problem it throws closes the socket with `1008`; any other error is reported and closes it with `1011`, as does a check that has not finished a minute later. What it returns is ignored, so refuse by throwing. |
| `maxMessageBytes` | Not an event: the largest message the socket takes, in bytes, a whole number of at least 1. A larger one closes the socket with `1009` before the server reads it, and `onMessage` never sees it. |

`socket.send(data)` takes a string, an `ArrayBuffer` or a `Uint8Array`, and `socket.close(code?, reason?)` closes it. A handler that throws closes the socket with `1011`, and the error is reported like any other.

Sockets need `@hono/node-server`'s `upgradeWebSocket`, the only upgrade supported, which `protobase dev` and `protobase serve` use. A server of your own that passes another host's upgrade to `createAdmin` gets sockets that misbehave, since they rely on its send callback and `bufferedAmount`.

### Who may open one

- **Refusals come before the socket.** A caller without a valid session or token gets the usual `401`, and one without the function's roles a `403`; the handler never runs. The browser only sees a socket that failed to open, since an upgrade's refusal has a status but no body.
- **Only the app's own pages** may open a socket with the cookie. An upgrade from a page on any other origin is a `403`, so another site cannot borrow a visitor's session.
- **While it is open,** the framework checks the caller again every minute: their session or token, the function's roles, and that the user, tenant, organization and roles are unchanged. It does so for a protected function, and for a public one once `caller()` resolved. Signing out, a ban, a role taken away, or another active role or organization closes the socket with `1008`, and a socket opened with a bearer token closes once the token expires. The client opens it again, as who they are now.
- **The function's own checks are not repeated,** such as whether the caller may still see one record. Pass them as `recheck`, which runs right after the framework's check:

<Code code={repairWatch} lang="ts" title="functions/repair-watch.ts" />
- **A plain request** to a function that accepts a socket is a `426` problem.

### Agents and other clients without a cookie

A [public function](#public-functions-and-webhooks) can accept a socket too. One that admits its caller with `await caller()` is checked again like a protected one. One that checks a credential of its own, for example a host agent's key in a header, passes `recheck` to check it again, since the framework cannot.

A page with no session cookie of the app, such as the workshop's display board on its own origin, gets a short-lived ticket from a plain call with its token and puts it in the socket's address:

<Code code={display} lang="ts" title="functions/display.ts" />

```ts
// On https://workshop.pips-bikes.example, with a client made by createClient
const { ticket } = await client.invoke('display-ticket', { method: 'POST' })
const board = new WebSocket(`wss://pips-bikes.example/api/functions/display?ticket=${encodeURIComponent(ticket)}`)
```

The ticket only lets the socket open, and anyone who holds it may open one with it during its 30 seconds. It is in the address, so it appears in the request log when `REQUEST_LOG` is `true`. Nothing checks the ticket's user again, so `display.ts`'s `recheck` ends the socket after 15 minutes, and the board opens it again with a new ticket, which `display-ticket` mints only after checking the role again.

### Slow readers and large messages

- **Await `send`** when the other side may read slowly: it resolves once the data is written, so a relay that awaits each send never piles up data in the server. It never rejects; after a close it resolves at once.
- **Return a promise from `onMessage`** to hold the next message back until it settles. Above 1 MiB of waiting messages the server stops reading from the client, which slows it down, and reads again once they are handled. Bun's built-in `ws`, which `protobase dev` uses on Bun, cannot stop reading: there the socket closes with `1013` once 16 MiB are waiting.
- **A message** may be up to 100 MiB, or the socket's `maxMessageBytes`, which only lowers it. A larger message closes the socket with `1009` before the server reads it, so a function that only takes small messages sets it, such as `acceptWebSocket({ maxMessageBytes: 64 * 1024, onMessage })`. `protobase dev` and `protobase serve` apply it; a server of your own that hosts `createAdmin` refuses a socket with `maxMessageBytes` with a `500`, since its `ws` server would not apply it.

### Restarts

`protobase dev` closes every open socket with `1012` when you edit the project, so it reconnects to the rebuilt API. `protobase serve` closes them with `1001` when it stops, and drops any still open after 5 seconds. Clients that reconnect on these codes keep working across both.

## Secrets and other APIs

<Code code={notifyCustomer} lang="ts" title="functions/notify-customer.ts" />

`requireEnv(name)` returns an environment variable, or throws when it is not set. The call then fails as a `500` that the app reports, and the request goes nowhere. `protobase dev` and `protobase serve` read the nearest `.env` file. In production the serve runtime takes the host's environment as it is, so set the secret where the host keeps its settings. Keep secrets in functions, never in `protobase.ui.tsx`, which runs in the browser.

## Calling a function

From the admin UI, an [action handler](/reference/custom-components/#action-handlers) gets a `client` that carries the user's token. `client.invoke` calls a function the way `supabase.functions.invoke` does:

```tsx
// protobase.ui.tsx
import { defineUi } from '@protobase/ui'

export default defineUi({
  actions: {
    readyForPickup: async ({ client, record }) => {
      await client.invoke('ready-for-pickup', { body: { repairId: record?.id } })
    },
  },
})
```

`invoke(name, { method?, body?, path?, query?, headers? })` sends a `GET`, or a `POST` with a JSON `body`. It resolves to the parsed JSON, to text, or to `undefined` for a `204`. A problem rejects with an `ApiError`, as any call of the client does. Outside the admin, `createClient` from `@protobase/client` gives the same `invoke`, or you can call the URL with `fetch` and an `Authorization: Bearer` header.

## Hono apps

A function of several routes can be a [Hono](https://hono.dev) app. The context is its `c.env`:

<Code code={workshop} lang="ts" title="functions/workshop/index.ts" />

`functionApp()` is `new Hono()` with one difference: errors and unknown paths reach the app's own error handling, so problems are rendered as problem+json and anything else is reported. Your own Hono instance works too, typed with `FunctionEnv` (or `PublicFunctionEnv`):

```ts
import { Hono } from 'hono'
import type { FunctionEnv } from '@protobase/server'

const app = new Hono<FunctionEnv>()
// Without this, Hono answers errors itself: a plain-text 500 that the app never reports.
app.onError((error) => {
  throw error
})
export default app
```

A Hono app's routes start at `/`, because the request path no longer includes `/api/functions/<name>`. The deploy bundle supplies `hono`, `hono/cors`, `hono/http-exception` and `hono/validator` (see [the config module](/reference/cli/#the-config-module)). Other Hono middleware is bundled with the function, as are its other packages.

### CORS

A function called from a page on another origin needs CORS. Use the `cors` option, which takes the options of `hono/cors`:

```ts
defineFunction({ cors: { origin: 'https://workshop.pips-bikes.example' } }, app)
```

Preflight requests are answered before authentication, because a browser sends them without a token. Every response, including a `401` problem, carries the CORS headers. In a protected function, the `hono/cors` middleware inside a Hono app would never see the preflight, because authentication runs first.

## Long queries

A function's queries through `db` have the database's own statement timeout: on Protobase Cloud, 1 second, so a slow query fails where it runs instead of holding a connection that pages wait for. A function that does bulk work, such as an import, a report or a large delete, asks for longer:

```ts
export default defineFunction({ longQueries: true }, async (request, { db }) => {
  await sql`delete from audit_log where at < now() - interval '1 year'`.execute(db)
  return new Response(null, { status: 204 })
})
```

- **Up to 30 seconds** per query, the most any query of an app may run. Work longer than that belongs in steps, such as a [job](/reference/jobs/) per batch, which takes `longQueries` too.
- **One connection kept for it.** Under `protobase dev` and `serve`, those queries run on a connection of their own, which asks for the longer timeout when it logs in, so long work never takes the connections pages need; a second long call waits for it. A PgBouncer of your own in front of the database must list `statement_timeout` in `track_extra_parameters` to pass that on; Protobase Cloud's does.
- **`records` keep the API's limit,** [`statementTimeoutMs`](/reference/api/#safety).
- **A query past its limit** is stopped, and the call answers `504 statement-timeout` naming the call, its limit and the way out, such as `POST /api/functions/import ran a query longer than the database's statement timeout, so the database stopped it. Make the query faster, such as with an index or a narrower filter, or give it longQueries: true, whose queries may run up to 30 s.` It goes to the app's error hook, `hooks/error.ts`, and the [error tracker](/reference/api/#error-reporting).

## Errors

- **Problems:** throw an `HttpProblem` (or `badRequest`, `unauthorized`, `forbidden`, `notFound` from `@protobase/server`) to answer with an [RFC 9457 problem](/reference/api/#errors). Hono's `HTTPException` works too.
- **A query the database stopped** is a `504 statement-timeout` that names the call; see [Long queries](#long-queries).
- **Everything else:** any other error, or a handler that returns something other than a `Response`, becomes a `500 internal-error` problem without its message. The error goes to the app's error hook, `hooks/error.ts`; without one, `protobase dev` and `serve` print it.

## Functions moved from Supabase

[`protobase import supabase`](/reference/cli/#import-supabase) converts `supabase/functions` into `functions/`. A converted function keeps Supabase's shape, `defineFunction({ supabase: true }, { fetch })`, and keeps working with `@supabase/server` and supabase-js:

- **At `/api/sb/functions/v1/<name>` too,** so `supabase.functions.invoke` callers do not change. Only a function with `supabase: true` answers there, and any other function answers `404`. There a protected function lets in a request with the app's publishable or secret key in the `apikey` header, and a user token of [`/api/sb/auth/v1`](/reference/auth/#supabase-js-and-supabasessr) as the bearer, if any, as Supabase's `verify_jwt` does. A public function lets in anyone. The keys are those of [supabase-js's Realtime](/reference/supabase-realtime/): without them, only public functions answer there. As on Supabase, the request's path starts at the function's name (`/<name>/more/parts`), and a CORS preflight reaches the function, which answers it.
- **Its context there** is `{ name, db, caller() }`, where `caller()` resolves to who the key and token make the request: `{ role: 'anon' }` for the publishable key alone, `{ role: 'app' }` for the secret key, or `{ role: 'authenticated', claims }`. There is no `session` and no `records`. The publishable key alone lets callers in, so give `supabase: true` only to functions written for Supabase's `verify_jwt`. Together with `roles` or `capability`, which the address cannot check, it stops startup.
- **Supabase's variables:** `protobase dev` sets `SUPABASE_URL` to the app's address with `/api/sb`, where supabase-js finds it, `SUPABASE_ANON_KEY`, `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_PUBLISHABLE_KEYS` to the publishable key, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_SECRET_KEY` and `SUPABASE_SECRET_KEYS` to the secret key, `SUPABASE_JWKS_URL` to the key set of `/api/sb/auth/v1`, and `SUPABASE_DB_URL` to the database. A variable set in `.env` wins. Under `protobase serve`, set them where the host keeps its settings.
- **`waitUntil(promise)`** from `@protobase/server` takes the place of `EdgeRuntime.waitUntil`. The response goes out at once, and the process waits for the work when it shuts down gracefully. Work still running when the host kills the process is lost. On Protobase Cloud's Starter plan an app stops 30 seconds after its last request, with 10 seconds to finish, so move longer work into a [job](/reference/jobs/).

## What functions are not

- **Not under `/api/v1`,** which stays resources only. Functions live beside the system endpoints, like `/api/meta`.
- **Not in the OpenAPI document** or the `/api/docs` reference.
- **Not scheduled:** a function runs when it is called. A cron job on the host, or an external scheduler, can call one with a token, or call a public one that checks a signature.
