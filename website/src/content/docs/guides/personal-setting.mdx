Rijnland's accountants want an email for each invoice that passes its due date; the warehouse would rather get none. That is a choice each person makes for themselves, so it belongs on their [account page](/reference/auth/#account-page), and the fields the page shows come from a resource like any other. This guide adds it to the ERP example (`examples/erp`) in four steps: a table, a resource, roles and a tab.

## 1. A table with one row per person

## 3. Roles that have settings

Give each role that should have the setting `.read.own`, `.create.own` and `.update.own` on the resource, in `config/roles.ts`:

```ts
const ownNotificationSettings = ['notification_settings.read.own', 'notification_settings.create.own', 'notification_settings.update.own'] as const

export const roles = defineRoles<ErpName>({
  admin: ['*'],
  auditor: ['*.read', ...ownNotificationSettings],
  sales: [...ownNotificationSettings, 'orders.read.own', ...],
  // the other roles alike: manager holds them already through '*.read', '*.create' and '*.update', and the
  // integration role, which is no person, has none
})
```

A role that may read but not write sees the choice without a control to change it; a role that may not read has no Notifications tab. Once a `Settings` block shows the resource, every caller reads and writes only their own record, an admin holding `*` included, in the block and in the API alike.

## 4. A tab on the account page

Export a page named `account` to replace the standard one: the standard tabs from `accountTabs`, in the order to show them, and a tab of your own with a [`Settings`](/reference/blocks/#settings) block on the resource:

<Code code={account} lang="tsx" title="config/account.tsx" />

Export it from `config/index.ts` too. Open **Account** in the user menu and then **Notifications**, at `/-/account/notifications`: the choice shows as a select with its label and help, set to **For each invoice** until it changes. Picking another value saves it at once; the first save creates the person's row.

## Reading the choice

Code of your own, such as a job that sends the emails, reads the choice with SQL. Someone who never saved has no row, so read the default for them:

```sql
select u.email
from auth."user" u
left join core.notification_settings s on s.user_id = u.id
where coalesce(s.overdue_invoices, 'each') = 'each'
```

The [`Settings` block](/reference/blocks/#settings) has its props, the field types it draws and the checks it runs at startup.
