A resource with [`.live()`](/api/schema/interfaces/resourcebuilder/#live) keeps the pages people have open on its records current: when a record changes, every open list, record page, count and chart of the resource reads it again within a second or two, without a reload. The changes are captured by the same database triggers as [events](/reference/events/), so writes from psql, other services and cron SQL show up too, not only those through the API.

## What a page hears

The server tells each open app which records changed, by resource and key, never their values. The app then reads again what it shows of that resource through the regular API, as its user, so the same tenant, row filters and field rules apply as to any other read. A page only hears of the live resources its user may list or read, in their tenant.

Changes that come close together are read once: a page gathers them for 300 milliseconds. A form with unsaved changes keeps the record it was opened with, so its Save still finds a conflict when someone else changed the record; the record is read again once the form is saved or left.

It is live data, not multiplayer editing: two people editing the same record still see a conflict on Save, as without `.live()`.

## The stream

`GET /api/live` answers a `text/event-stream` to anyone who may read a live resource, a visitor of the anonymous role too. Each event's data is JSON with a `cursor`:

| `type` | |
| --- | --- |
| `current` | Nothing new up to `cursor`. Sent first, and every 25 seconds. |
| `changes` | `changes`: `[{ resource, key, operation }]` in commit order, `operation` being `create`, `update`, `delete` or `undelete`. |
| `resync` | Changes went by that are no longer kept: read everything shown again. |

Connecting again with `?after=<cursor>` catches up on what was missed while disconnected. [`client.live({ onChanges, onResync })`](/reference/client/) of `@protobase/client` follows the stream and connects again by itself, as the app does. However many callers of one client follow it, they share one stream, so a page with many live views holds one connection, which matters under HTTP/1.1, where a browser opens at most six to a host.

Who is on a record's page and what they send each other, which no change of a record says, goes over the record's [channel](/reference/channels/).

## The table

[`protobase migration`](/reference/cli/#migration) adds the table `changes.notices` to the `changes` schema of the event capture (renamed with `events: { schema }`), and the capture triggers of each live resource; apply it with the project's other migrations. `protobase dev` and `protobase serve` do not start while the table or a trigger is missing.

A notice is a resource, a record key, the record's tenant and the operation, written by the `changes.dispatch` job in the transaction that removes the change from the outbox; a live resource therefore needs the [`jobs` schema](/reference/jobs/#the-jobs-schema) and the app's workers. Notices are kept for 10 minutes. Each serving process with at least one page open reads the table once a second, however many pages it serves, so live updates work with several serving processes, with `PROTOBASE_JOBS=false` and through a pooler in transaction mode.
