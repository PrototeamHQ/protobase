An app sends mail through one SMTP server: Protobase's own mail ([password reset](/reference/auth/#password-reset), [emailed sign-in codes](/reference/auth/#emailed-sign-in-codes), [invitations](/reference/auth/#organizations), staff sign-in notices and [mentions in comments](/reference/comments/#mentions)) and the emails the app defines itself. Each is rendered to HTML with a plain-text part beside it.

## Configuration

| Variable | |
| --- | --- |
| `PROTOBASE_SMTP_URL` | The SMTP server, credential included: `smtp://user:password@host:587` (STARTTLS required) or `smtps://user:password@host:465` (TLS from the start). |
| `PROTOBASE_MAIL_FROM` | The sender, a plain address such as `noreply@shop.example.com`. The client greets the server with its domain; a `?name=` on the URL overrides that. |
| `PROTOBASE_APP_NAME` | Optional: the app's name, such as `Shop`, which mail clients show as the sender's name (`Shop <noreply@shop.example.com>`). It overrides the config's [`name`](/reference/config/app/#name). Without either the sender has no name. |

Set both or neither. One without the other, a URL that is not `smtp://` or `smtps://`, or a sender that is not a plain address stops the app at startup. Without them mail is off: password reset and emailed codes are not offered, a job's `mail` is `undefined`, and sending an app's email rejects.

`protobase dev` and `protobase serve` read them from the environment or the nearest `.env`; a host passes them like `DATABASE_URL`. In development, a mail catcher such as [Mailpit](https://mailpit.axllent.org) shows what the app sends without delivering it:

```sh
docker run -d -p 8025:8025 -p 1025:1025 axllent/mailpit   # its inbox is http://localhost:8025

# .env
PROTOBASE_SMTP_URL=smtp://localhost:1025?requireTLS=false
PROTOBASE_MAIL_FROM=noreply@shop.example.com
```

Over `smtp://` the client always upgrades the connection with STARTTLS before it logs in or sends anything, so nobody between the app and the server reads the server's password or the mail, such as a sign-in code or a reset link. A server that does not offer STARTTLS, or an answer from which someone on the way removed it, fails the send, with the code `ETLS` when the server refuses the upgrade. `?requireTLS=false` on the URL is the only way to send in plaintext, for a server that has no TLS, such as the mail catcher above or a server on the same host. `smtps://` uses TLS from the start.

A project that delivers its mail another way exports a mailer, `{ send({ to, subject, text, html, headers }) }`, resolving to `{ messageId }` when it knows the message's `Message-ID` and `{}` when not, as the default of `auth/mailer.ts`: sign-in and the jobs (`mail` in their context) both send with it. `auth: { mailer: false }` turns sign-in's mail off whatever the environment says. A host that runs jobs itself passes a mailer to `startJobs`. A template's `send` takes one too, see [Templates](#templates).

### When the server does not answer

A send through `PROTOBASE_SMTP_URL` gets 30 seconds in all: looking up the server, connecting to each of its addresses, its greeting, TLS, the login and the message. One that has not finished by then rejects with a `MailServerTimeoutError` (exported by `@protobase/server`) whose `code` is `MAIL_SERVER_TIMEOUT`, as when a firewall drops the mail port's packets or the server never greets; it is not retried. Options on the URL, such as `?connectionTimeout=`, cannot lift the limit. A server that answers and refuses keeps its own error code, such as `EAUTH` for a refused login or `EENVELOPE` for a refused sender. <gap>A send that ran out cannot close its connection at the limit because cancelling a send in progress is not implemented in the SMTP client; the client's own timers, 10 seconds for each of the server's addresses, close it soon after.</gap>

## Protobase's own mail

The auth emails (sign-in, two-factor and sign-up codes, the note to an address that asked to sign up while it has an account, password reset, invitations and staff sign-in notices) and the email to someone a [comment mentions](/reference/comments/#mentions) are email templates: a heading, the message, one code or button, and a footer naming the app.

- They come in English and Dutch. An auth email is in the app's [`locale`](/reference/languages/#choosing-the-language) when the app sets one, else in the language of the browser that asked for it, such as the one that asked for a sign-in code, else in English. The mention email is in the app's `locale`, else in English: it is sent by a job, after the request.
- They name the app by its [`name`](/reference/config/app/#name), and link it on the origin the request came to: the footer links its home page, and the note to an address that has an account links its sign-in page.
- The plain-text part has each code on a line of its own and each link in full. A date, such as when an invitation's link stops working, is written in the email's language, in UTC: `October 15, 2026 at 12:00 PM UTC`, `15 oktober 2026 om 12:00 UTC`.
- React Email and the templates are loaded when the first auth email is sent, so an app that sends none never loads them and the server starts as fast without them.

## Templates

An email of the app's own is a template: `defineTemplate`, with its data typed, its text in each language it is sent in, and its body written in mail blocks, as a [typed layout](/reference/layouts/#typed-layouts) is. The body is built once, as the config loads, into a static tree: `data.name` is the placeholder `{{name}}`, `<Show when>` and `<Switch>` choose by the data, and an `ArrayField` repeats a list of it. Export the template from `config/index.ts`, so the workflow step [Send email](/reference/workflows/#appmailtemplate) lists it.

```tsx title="config/emails/contact-reply.tsx"
/** @jsxImportSource @protobase/layout */
import { Button, Show, Text, Trans, translations } from '@protobase/layout'
import { defineTemplate } from '@protobase/server'
import { z } from 'zod'
import en from './contact-reply.en.json'
import nl from './contact-reply.nl.json'

export const contactReply = defineTemplate({
  name: 'contact-reply',
  texts: translations({ en, nl }),
  schema: z.object({ name: z.string(), topic: z.enum(['sales', 'support']), days: z.number(), id: z.string() }),
  subject: ({ data }) => <Trans i18nKey="subject" values={{ name: data.name }} />,
  body: ({ data, app }) => (
    <>
      <Text as="h1"><Trans i18nKey="greeting" values={{ name: data.name }} /></Text>
      <Text><Trans i18nKey="thanks" values={{ days: data.days }} /></Text>
      <Show when={data.topic.eq('sales')}>
        <Text><Trans i18nKey="sales" components={{ b: <Text as="strong" /> }} /></Text>
      </Show>
      <Button href={`${app.url}/contact/${data.id}`}><Trans i18nKey="cta" /></Button>
    </>
  ),
})
```

```json title="config/emails/contact-reply.nl.json"
{
  "subject": "We hebben je bericht ontvangen, {name}",
  "greeting": "Hoi {name},",
  "thanks": "{days, plural, one {We antwoorden binnen # werkdag.} other {We antwoorden binnen # werkdagen.}}",
  "sales": "Een collega van sales <b>belt je</b>.",
  "cta": "Bekijk je bericht"
}
```

| `defineTemplate` option | |
| --- | --- |
| `name` | Names the template, in errors and in the step's list: a lowercase letter, then lowercase letters, digits and dashes. Each template of the app has its own. |
| `texts` | Its texts in each language it is sent in, `translations({ en, nl })` of ICU messages, which its `<Trans>` elements show, as the app's own [texts](/reference/languages/#your-own-texts) are. Without it, the template is in one language, as written. |
| `subject` | The subject line: text, or a function of `{ data, app }` that gives text or a `<Trans>`. |
| `preview` | Optional: the line inboxes show after the subject, as `subject` is written. |
| `schema` | Optional: a [Standard Schema](https://standardschema.dev), such as a zod 4 schema, or Valibot's with `toStandardJsonSchema`, which checks the data before each send and types it. |
| `headers` | Optional: more header fields, or a function of `{ data, app }` that gives them, each one line. |
| `body` | A function of `{ data, app }` that gives the mail's blocks. `app.name` and `app.url` are the app the mail comes from. |

The body takes the mail blocks: `Text` (a paragraph, `as="h1"` to `h4` for a heading, `strong`, `em` or `span` in a line), `Trans`, `Link` with an `href`, `Button` with an `href`, `Image`, `Divider`, `Box`, `Row` and `Column`, `Show`, `Switch` and `Match`, `ArrayField` with `RecordsIterator`, and `Field`. Any other block, such as a `Table`, fails as the config loads, as does a `<Trans>` key the texts lack.

The template that comes back has two methods, both typed by the data:

- `render(data, { locale, app })` gives `{ subject, html, text, headers, locale }` without sending anything: for a test, or to look at the result.
- `send(to, data, { locale, mailer, app, attachments })` renders and sends it, through `mailer` when given (a job's `mail`), otherwise through `PROTOBASE_SMTP_URL`, and gives what it rendered. It rejects when mail is off or the server refuses the message.

A send is in the language of its texts closest to `locale`, by its tag (`nl-BE`) or its language (`nl`), else the app's `locale` when the texts have it, else English, else the first; `locale` says which it was. With a `schema`, data the schema refuses rejects with `TemplateDataError`, naming each path, before anything is sent. The data's JSON Schema, which the step draws its pins from, is the schema's own, or without one each path the template reads, such as `name` and a list `items` with its `title`.

### Emails in React

An email can also be `defineEmail`: a name, a subject, and a React component whose props are the email's data, for a layout the mail blocks cannot draw. The components of [React Email](https://react.email) render the tables and inline styles email clients need. `@protobase/server` brings React's renderer; the project adds the components, and React for its JSX, which a project with a UI has already:

```sh
bun add react-email react
bun add -d @types/react
```

| `defineEmail` option | |
| --- | --- |
| `name` | Names the email in errors. |
| `subject` | The subject line, or a function of the data that makes it. |
| `component` | The body, a React component of the data. It is rendered with React Email's `render` to the HTML part; the plain-text part is made from that HTML, leaving out what React Email marks to skip, such as `<Preview>`. |
| `headers` | Optional: more header fields, or a function of the data that makes them. A value is one line. |
| `bulk` | Optional: `true` marks bulk mail, which carries a one-click unsubscribe from its `topic` (see [Unsubscribe](#unsubscribe)). |
| `topic` | The kind of mail, such as `newsletter`, which a recipient unsubscribes from; required with `bulk`. |

The template that comes back has two methods, both typed by the component's props:

- `render(data)` gives `{ subject, html, text, headers }` without sending anything: for a test, or to look at the result.
- `send(to, data, mailer?)` renders and sends it, through `mailer` when given (a job's `mail`), otherwise through `PROTOBASE_SMTP_URL`. It rejects when mail is off or the server refuses the message, and a bulk email without a job's `mail` as `mailer`.

React and React Email's renderer are loaded on the first email rendered, not when the app starts.

Mail an app sends in bulk, such as alerts or newsletters, is marked `bulk` with a `topic`, and Protobase gives it a one-click unsubscribe: see [Unsubscribe](#unsubscribe).

### The look of Protobase's own mail

`@protobase/server/email` exports React Email components with the look of Protobase's own mail, so an app's `defineEmail` emails can look the same: a white card on grey with a teal action.

| Component | |
| --- | --- |
| `EmailLayout` | The whole email: `preview`, the line inboxes show after the subject; `heading`; the message as its children; and a footer naming `app`, linked to its home page. `app` is `{ name, url }`. |
| `EmailButton` | The email's one action: a button to `href`, and the label with the link in the plain-text part. |
| `EmailCode` | A code to type in, on a line of its own. |
| `EmailNote` | A remark below the message, such as why the recipient gets the email. |

```tsx
import { defineEmail } from '@protobase/server'
import { EmailButton, EmailLayout, EmailNote, type MailingApp } from '@protobase/server/email'
import { Text } from 'react-email'

type RepairReady = { app: MailingApp; customer: string; bike: string; url: string }

const RepairReadyEmail = ({ app, customer, bike, url }: RepairReady) => (
  <EmailLayout app={app} preview={`Your ${bike} is ready for pickup`} heading="Ready for pickup">
    <Text>Hi {customer}, your {bike} is ready.</Text>
    <EmailButton href={url}>See the repair</EmailButton>
    <EmailNote>You get this email because you brought your bike in for repair.</EmailNote>
  </EmailLayout>
)

export const repairReady = defineEmail({ name: 'repair-ready', subject: 'Your bike is ready', component: RepairReadyEmail })
```

They are apart from `@protobase/server` itself, so an app that imports none never loads React Email's components.

### Message id

`mail.send` and a template's `send` resolve to `{ messageId }`, the `Message-ID` header the recipient sees, such as `<3f9c2a7e0b4d4e51a1c6f0d2b8e7a913@shop.example.com>`. Store it with the record the mail was about, so a reply, bounce or complaint that comes back later, which names that id, can be matched to the mail it answers. A mailer that does not know the id resolves to `{}`, so store `null` then:

```ts
const { messageId } = await invoiceEmail.send(client.email, { number: 7 }, mail)
await db.updateTable('invoices').set({ message_id: messageId ?? null }).where('id', '=', invoice.id).execute()
```

Protobase gives every message through `PROTOBASE_SMTP_URL` a new id on the sender's domain before it goes out, in place of a `Message-ID` among the message's own `headers`. A relay that rewrites the `Message-ID` changes what the recipient sees, so check that yours keeps it. A mailer of the project's own resolves to the id it sends, or to `{}` without one; mail from someone's own mailbox resolves to `{}` (see below).

## Unsubscribe

:::caution[Beta]
There is no preferences page yet, and no way to subscribe again once unsubscribed.
:::

Mail you mark as bulk carries a one-click unsubscribe, as large mailbox providers expect of bulk senders ([RFC 8058](https://www.rfc-editor.org/rfc/rfc8058)): the mail client shows an unsubscribe button, and one click stops that kind of mail to that recipient. Protobase records who unsubscribed from which topic, and does not send that topic to them from the next send on.

**Bulk** is mail the recipient did not ask for by an action of their own: newsletters, digests, announcements and marketing. **Transactional** mail answers something the recipient did or needs to act on, such as a password reset, a sign-in code, a receipt or an invoice: it is not marked bulk and carries no unsubscribe. Protobase's own mail is transactional.

Turn it on in the config, then run `protobase migration`, which writes its table, `mail.unsubscribes`, as a migration of the project's own, and apply it with the project's migrations: `protobase serve` refuses to start while the table or its unique index is missing, and names the migration to write. Its links are on the app's [`url`](/reference/config/app/#url), which must be `https://` but on `localhost`, and signed with its [`secret`](/reference/config/app/#secret):

```ts
export default defineConfig({ unsubscribe: true })
```

Mark an email as bulk with a `topic`, the kind of mail someone unsubscribes from, such as `newsletter` or `weekly-digest`: a lowercase letter, then lowercase letters, digits, `_` and `-`. Send it from a job with the job's `mail`:

```ts
export const weeklyDigest = defineEmail({ name: 'weekly-digest', subject: 'This week', component: Digest, bulk: true, topic: 'weekly-digest' })

// jobs/send-digest.ts
const { skipped } = await weeklyDigest.send(member.email, digest, mail)
await mail.send({ to: member.email, subject: 'News', text: '...', bulk: true, topic: 'newsletter' })
```

- **The headers:** each message gets `List-Unsubscribe` with the recipient's own link, `https://<app>/api/unsubscribe/<token>` with the default [`apiPath`](/reference/config/api/#apipath), and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, in place of such headers of its own. The token names the recipient and the topic, signed so that nobody can change either: a link cannot be made for someone else or for another topic. It is a bearer link, though: whoever holds it, such as someone the mail was forwarded to, can unsubscribe its recipient from its topic.
- **The button:** mail clients show their unsubscribe button only on mail whose DKIM signature covers both headers. Protobase sends the headers; the server that signs your mail must sign `List-Unsubscribe` and `List-Unsubscribe-Post` too, or the mail still goes out without a button.
- **A message per recipient:** `to` takes one plain address or several separated by commas, and each recipient gets a message of their own with their own link. A named address (`Ada <ada@example.com>`) is refused.
- **The click:** the mail client's `POST` with `List-Unsubscribe=One-Click` records the opt-out and answers `200`; doing it again changes nothing. Opening the link in a browser shows a page with an **Unsubscribe** button that sends that `POST`, so a scanner that follows links in mail unsubscribes no one. A link the app did not sign answers `400` and records nothing.
- **Skipped sends:** whoever unsubscribed from the topic is left out, found in one query, and the send resolves to them as `skipped` beside `sent`, each recipient it went to with its message id: `{ skipped: ['bob@example.com'], sent: [{ to: 'ada@example.com', messageId: '<…>' }], messageId: '<…>' }`, with `messageId` only when it went to exactly one. Other topics still reach them. Who unsubscribed is read once, before the first message goes out; one who unsubscribes while a send to several is going out is skipped from the next send on.
- **A refused message:** when the server refuses one recipient's message, the send rejects with a `BulkMailError` (exported by `@protobase/server`, its `code` `BULK_MAIL_FAILED`) after the messages before it went out. It fails the try, which is retried, and names the recipient it failed on as `to`, those it went to as `sent`, those skipped as `skipped`, and the server's error as `cause`. A retried try sends to everyone again, so catch it, record `error.sent`, rethrow, and leave those addresses out of the next try; or send to one recipient per call.
- **From a workflow:** a workflow's mail steps send bulk mail as an [email series](/reference/workflows/#email-series), whose name is the topic.
- **Who unsubscribed:** admins see each recipient, topic and time under **Unsubscribes** in the admin app, and the app's code reads them as the `mail_unsubscribes` resource, `GET /api/v1/mail_unsubscribes?filter=topic = "newsletter"`. Nobody changes them but the link.
- **Refused:** `bulk` without a `topic` is refused, as the email is defined or the message sent. Bulk mail without `unsubscribe: true`, or sent another way than a job's `mail`, such as through `PROTOBASE_SMTP_URL` directly or from someone's own mailbox, is refused before anything is sent. A mailer of the project's own (`auth/mailer.ts`) that is handed bulk mail directly, outside a job's `mail`, gets it without its unsubscribe: send it through the job's `mail` instead.
- <gap>Bulk mail cannot be sent from an API function because only a job's `mail` adds the unsubscribe; enqueue a job instead.</gap>
- <gap>Email templates cannot be marked bulk because `defineTemplate` does not take `bulk` and `topic` yet.</gap>

## Bounces and complaints

:::caution[Beta]
Amazon SES (through SNS) and Resend report to their own endpoints so far, beside the `protobase` one a platform reports to.
:::

A mail provider tells the app when a message bounced or its recipient marked it as spam. With `mailFeedback` on, each report becomes a `mail_feedback` record, one per recipient, with the events `mail_feedback.bounced` and `mail_feedback.complained`, which [workflows](/reference/workflows/), [subscriptions](/reference/webhooks/) and your own code act on, such as marking a contact's address undeliverable. Protobase records and notifies only: it keeps sending to the address, and the app decides what a bounce means.

Turn it on in the config, then run `protobase migration`, which writes its table, `mail.feedback`, and the capture of its events as migrations of the project's own; apply them with the project's migrations, as `protobase serve` refuses to start while the table is missing:

```ts
export default defineConfig({ mailFeedback: true })
```

Each provider reports to `POST /api/mail/feedback/<provider>` with the default [`apiPath`](/reference/config/api/#apipath), without sign-in, and has that endpoint only once its variable is set:

| Provider | Variable | |
| --- | --- | --- |
| `ses` | `PROTOBASE_MAIL_FEEDBACK_SES_TOPICS` | The ARNs of the SNS topics SES publishes bounces and complaints to, separated by commas. Subscribe the endpoint to each topic over HTTPS: the endpoint confirms the subscription itself. |
| `resend` | `PROTOBASE_MAIL_FEEDBACK_RESEND_SECRET` | The webhook's signing secret, `whsec_...`, of a webhook that sends `email.bounced` and `email.complained` to the endpoint. |
| `protobase` | `PROTOBASE_SECRET` | The platform secret, which a hosting platform reports bounces and complaints with. |

A value that is not a topic ARN or a signing secret stops startup, naming the variable.

- **Signatures:** a report writes nothing unless its signature checks out. `ses` takes SNS's signature, versions 1 and 2, with the signing certificate fetched from an SNS host over HTTPS and kept an hour, and only messages of the named topics, since anyone can sign with a topic of their own. `resend` and `protobase` take [Standard Webhooks](https://www.standardwebhooks.com) signatures, made at most five minutes before. A missing or wrong signature answers `401`, another topic `403`.
- **The record:** `type` is `bounce` or `complaint`; `bounce_type` `hard` (permanent) or `soft` (transient), and empty when the provider could not tell; `recipient`, lower-cased; `message_id`, the `Message-ID` header of the message it is about, when the report states it; `provider_message_id`, the provider's own id of that message; `reason`, as the provider gives it, such as the receiving server's diagnostic, a bounce subtype or a complaint's feedback type; `occurred_at`, when the provider says it happened; `provider`, `event_id`, the provider's id of the report, and `created_at`. A value the report does not state is empty, never guessed. Match it to the mail it answers by the [message id](#message-id) you stored.
- **Once:** a provider sends a report again when it got no answer in time; the same report writes nothing new. A report of another kind, such as a delivery, answers `204` and writes nothing.
- **Who sees it:** admins see the reports under **Mail feedback** in the admin app, and the app's code reads them as the `mail_feedback` resource, `GET /api/v1/mail_feedback?filter=recipient = "ada@example.com"`, filtered by `recipient`, `type`, `message_id` or `provider_message_id`. Nobody changes them but the endpoints.
- **The `protobase` endpoint:** its body is one record as above, without `provider`, `event_id` and `created_at`, such as `{ "type": "bounce", "bounce_type": "hard", "recipient": "ada@example.com", "message_id": "<...>", "reason": "smtp; 550 5.1.1 user unknown" }`, signed as Standard Webhooks with a key derived from `PROTOBASE_SECRET`, so the secret itself never travels: `mailFeedbackHeaders(secret, id, body)` of `@protobase/server` makes the headers. `webhook-id` names the report, and a retry keeps it.
- <gap>Other mail providers cannot report bounces and complaints because only the `ses`, `resend` and `protobase` endpoints are implemented.</gap>

## Attachments

A message takes files beside its body, such as an invoice's PDF: `attachments`, each a `filename`, its bytes as `content` (a `Uint8Array`, such as a `Buffer`) and, optionally, its `contentType`, else the one the name implies. A template's `send` takes them as its fourth argument:

```ts
await invoiceEmail.send(client.email, { number: 7 }, mail, { attachments: [{ filename: 'invoice-7.pdf', content: pdf, contentType: 'application/pdf' }] })
await mail.send({ to: client.email, subject: 'Invoice 7', text: 'Attached.', attachments: [{ filename: 'invoice-7.pdf', content: pdf }] })
```

An attachment is only the bytes given: a file path or URL is never read in its place. A mailer of the project's own (`auth/mailer.ts`) gets them in `message.attachments`.

## From someone's own mailbox

:::caution[Beta]
Gmail is the only mail provider so far. API functions, and workflow steps that the person turned on themselves, send from a mailbox. A job's own code cannot yet.
:::

An app can send mail from the signed-in person's own mailbox instead of the app's address, such as an invoice from the account holder's Gmail, so replies reach them. They link the mailbox once on the [account page](/reference/auth/#account-page) ("Connect Gmail" under **Mailbox**), which asks the provider for leave to send mail and nothing else; the app's functions then send through it. `auth.personalMail` names the providers people may link, each through the app's sign-in provider of the same company; Gmail links through Google sign-in (see [Send mail from Gmail](/guides/send-from-gmail/) for the Google setup):

```ts
export default defineConfig(({ env }) => ({
  auth: {
    socialProviders: { google: { clientId: env.GOOGLE_CLIENT_ID!, clientSecret: env.GOOGLE_CLIENT_SECRET! } },
    personalMail: ['gmail'],
    encryptOAuthTokens: true,
  },
}))
```

A protected [API function](/guides/api-functions/) gets the caller's mailbox as `personalMail`, a mailer like any other, so a template sends through it too:

```ts
import { defineFunction } from '@protobase/server'
import { invoiceEmail } from '../emails/invoice'

export default defineFunction(async (request, { personalMail }) => {
  const { to, number, pdf } = await readInvoice(request)
  await invoiceEmail.send(to, { number }, personalMail, { attachments: [{ filename: `invoice-${number}.pdf`, content: pdf, contentType: 'application/pdf' }] })
  return new Response(null, { status: 204 })
})
```

- **Tokens:** the link is the sign-in provider's account Better Auth keeps for the person, with its access and refresh tokens, encrypted: `auth.personalMail` needs `encryptOAuthTokens: true`, and startup stops without it. The tokens never leave the server. An access token that has expired is refreshed before the message goes out, and the new one is stored.
- **When it cannot send:** `send` rejects with a `PersonalMailError` and sends nothing. Its `code` is `not_linked` when the person linked no mailbox, or signed in with Google without allowing it to send mail, and `link_expired` when the provider no longer honours the link, as when they revoked it or its refresh token expired: they connect it again under Account → Mailbox. Thrown on, it answers the function's caller as a `409` problem with that `code` (`urn:protobase:problem:personal-mail-not-linked` or `-link-expired`), and an [action](/reference/ui-config/#actions-that-send-from-someones-mailbox) whose handler gets it offers to connect the mailbox right there:

  ```json
  { "type": "urn:protobase:problem:personal-mail-link-expired", "status": 409, "code": "link_expired", "provider": "gmail" }
  ```

- **Sender:** without a [From address](#from-addresses), the provider sends as the linked address; Gmail sets the From header to it.
- **Which account:** mail goes out through the account the person connected for mail last. Connecting Gmail with another Google account takes the mail scopes off the earlier one in the app's store, and signing in with the earlier one does not take the mail back; connecting it again does. When the chosen account's link fails, sending fails: it never falls back to another account. Of two accounts that both still hold the mail scopes, as when both connected before this rule came in, mail goes through the one linked to the person last, until they connect one again.
- **Only the person:** mail goes out from a mailbox only for someone signed in as themselves, or from a [workflow step's `mailbox`](/reference/workflow-plugins/#step-types) in a version that person turned on while signed in as themselves, and only while they may still change the workflow. Staff [signed in as them](/reference/auth/#staff-sign-in), an outside app acting for them, and a job's own code cannot send from it; a request is refused with a `403` problem (`own-sign-in-only`), a step fails with `not_linked`, and nothing is sent. Turning the workflow off, or someone else turning a new version on, ends the first person's consent.
- **Providers:** Gmail, through Google sign-in. A provider is added to Protobase behind the same `PersonalMailProvider` shape: its sign-in provider, the scopes linking asks for, and how it sends.
- **Sign-in is not a mailbox:** under **Mailbox**, the account page says when someone signs in with Google without having allowed it to send mail, so a linked Google sign-in is not taken for a connected mailbox.
- <gap>The account page cannot show which account a mailbox is linked through or disconnect it because unlinking a mailbox is not implemented.</gap>
- <gap>Mailboxes other than Gmail cannot be linked because no other mail provider is implemented.</gap>
- **Bounces:** mail sent from someone's own mailbox bounces back to the sender, not to the app. It reaches none of the [mail feedback](#bounces-and-complaints) endpoints, so it makes no `mail_feedback` records and no `bounced` or `complained` events. Handling its bounces is the sender's own concern.
- <gap>A send through Gmail cannot return its [message id](#message-id) because Gmail sets its own and reading it back needs a scope that reads the mailbox, which the link does not ask for.</gap>

### From addresses

A mailbox may send as more than its own address, such as Gmail's send-as addresses (Gmail's settings → Accounts → **Send mail as**). The person enters each such address once on the account page, under **Mailbox** → **From addresses**; only they can send from it. For each they choose:

- **Name:** an address may carry a display name, which the From header shows beside it, such as `From: Shop billing <billing@shop.example>`, as mail sent by hand from a send-as address shows the name set up for it; a name that is not ASCII is encoded. Left empty, the header holds the bare address. To give the mailbox's own address a name, enter it as well.
- **Signature:** an address may carry its own signature, which takes the place of the app's generic one; left empty, the generic one applies.
- **Default:** one address, theirs or their mailbox's own, is the one mail goes out from when the app names none.

A function then names the From address with `from`, matched without regard to case. To send a template from it, render it and send the result:

```ts
export default defineFunction(async (request, { personalMail }) => {
  const { to, number, pdf } = await readInvoice(request)
  const sender = await personalMail.sender('billing@shop.example')
  const email = await invoiceEmail.render({ number, signature: sender.signature ?? defaultSignature })
  await personalMail.send({ from: sender.address, to, ...email, attachments: [{ filename: `invoice-${number}.pdf`, content: pdf, contentType: 'application/pdf' }] })
  return new Response(null, { status: 204 })
})
```

- **`send({ from, ... })`:** sends from `from`, else the person's default address, else their mailbox's own. Gmail keeps the From header when the address is one of the account's verified send-as addresses; when it is not, Gmail sends from the account's own address instead, without an error.
- **`sender(from?)`:** the address a send with `from` goes out as: `address`, `name` when it has one, `signature` when it has its own, and `ownerId`, whose mailbox it goes through. It refuses as `send` does.
- **`senders()`:** every address the caller may choose, such as for a send dialog: their mailbox's own, then those they entered.
- **Refused addresses:** a From address that is not the mailbox's own and not one the caller entered is refused before anything is sent, with a `MailSenderRefusedError` that answers as a `403` problem naming it; so is an address someone else entered, in the same words:

  ```json
  { "type": "urn:protobase:problem:mail-sender-refused", "status": 403, "address": "ceo@shop.example", "detail": "You may not send mail from ceo@shop.example: add it to the Mailbox section of your account page first" }
  ```

- **The mailbox's own address** is the one its provider's ID token names; Google gives it with the `email` scope sign-in asks for.
- **The account page's calls:** `GET /api/auth/account/mail-senders` lists the person's addresses with their mailbox's own `address`; `POST .../mail-senders/add { address, name?, signature? }`, `POST .../mail-senders/update { id, name?, signature?, isDefault? }` (`name: null` drops the name, `signature: null` drops its own) and `POST .../mail-senders/remove { id }` change them. Each acts on the signed-in person's own addresses only.
- <gap>An address cannot be shared with others who send mail because proving that the person owns the address is not implemented.</gap>

### Checking a From address

:::note[Coming soon]
The app's side is built; the hosting platform's service that receives the test messages is not live yet.
:::

Gmail sends from the account's own address, without an error, when a From address is not one of its verified send-as addresses. So the account page checks an address by sending one test message from it through the person's mailbox, to a one-time address of a mail check service, and showing the From it arrived with:

- **When:** adding an address checks it at once; its dialog, under **Edit**, checks it again with **Check address**, and after a result with **Check again**.
- **Waiting:** the dialog asks every 3 seconds whether the message arrived, for up to 2 minutes, then says it did not arrive in time. Closing the dialog stops asking.
- **The result:** a From equal to the address, without regard to case, confirms it; any other shows the address the mailbox used instead, with how to set the address up in Gmail. The message also shows in the person's Sent folder.
- **The service:** the hosting platform names it in `PROTOBASE_MAIL_CHECK_URL`, a URL the app treats as opaque. The app makes two signed JSON `POST`s under it: `/alias-checks` answers `{ token, address }`, a one-time address and its token, and `/alias-checks/result { token }` answers `{ received: false }`, or `{ received: true, from }` with the address in the message's From header. Each carries [Standard Webhooks](https://www.standardwebhooks.com) headers under a key derived from `PROTOBASE_SECRET` by HKDF (`mailCheckSecret` and `mailCheckHeaders` of `@protobase/server`), which the service checks with `verifyStandardWebhook`. `PROTOBASE_MAIL_CHECK_URL` without `PROTOBASE_SECRET` stops startup.
- **Unchecked:** without the service, the dialog says the app cannot check From addresses, and how to check one by hand.
- **The account page's calls:** `GET /api/auth/account/mail-senders` says `checks: true` where the app can check; `POST .../mail-senders/check { id }` sends the test message and answers `{ status: 'waiting', check }`, or `{ status: 'unchecked' }`; `POST .../mail-senders/check-result { id, check }` answers `waiting`, `confirmed` or `mismatch` with `from`. Each acts on the signed-in person's own addresses only, and staff signed in as them cannot send a check.
- <gap>Self-hosted apps cannot check a From address because no mail check service that receives the test messages is implemented outside Protobase Cloud.</gap>

### A From address on a record

:::caution[Beta]
A removal refused over records does not say which records hold the address; and since addresses cannot be shared yet, everyone else sees an address on a shared record as not available.
:::

A record can hold the address its mail goes out from, such as a client's or the seller's "Send from": declare the field with `f.mailSender()`, on a `text` column, and pass its value to `send({ from })`.

```ts
send_from: f.mailSender().optional(),
```

- **The form:** a dropdown of the signed-in person's addresses, their mailbox's own first, then those they entered, each as `Name <address>` when it has a name. The empty choice, **Sender's default address**, stores `null`: mail goes out from the default address of whoever sends it.
- **Saving:** a create or update may only set an address the saving person may send from, by the rule `send` uses; the address is stored as their sender spells it. Any other is refused with a `400` naming the field and the address. A visitor, and anyone on an app without personal mail, can set none.
- **An address no longer offered,** such as one another person entered, still shows, marked **not available**, with a link to the account page. Saving other fields, or giving the same address again, leaves it as it is.
- **Read views** show the address, with its name when it is one of the reader's.
- **Removing an address in use:** while a record that is not soft-deleted holds it in an `f.mailSender()` field, removing it on the account page, or disconnecting the mailbox whose own address it is (`POST /api/auth/unlink-account`), is refused with a `409` and changes nothing:

  ```json
  { "code": "MAIL_SENDER_IN_USE", "message": "billing@shop.example is still the From address of records in this app. Give them another From address first." }
  ```

  The refusal names no records, since they may be records the person cannot read, such as another organization's. It is in the language the request's `Accept-Language` asks for. The address is matched without regard to case, as sending matches it, so an index on the column's `lower()` serves it.
- <gap>A refused removal cannot name the records that hold the address because checking which of them the person may read is not implemented.</gap>
- <gap>A mail sender field cannot offer addresses shared with the person, nor refuse unsharing one a record holds, because sharing an address is not implemented.</gap>

## In a bundle

A [bundle](/reference/cli/#the-config-module) gets React and React Email's renderer from the serve runtime, as it gets `@protobase/server` and `@protobase/server/email`, so an email's component and the renderer share one React and hooks such as `useContext` work. React Email's other components are inlined, though `@protobase/server` uses them too: it loads them only to send its own mail, so the runtime does not supply them. Its `<Tailwind>` component needs `tailwindcss`, which the runtime does not supply, so a served config cannot use it: style with `style` props instead.
