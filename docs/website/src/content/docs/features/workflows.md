---
title: Workflows
description: Graphs of steps the server runs along their edges, written in a language a model writes well, with every step kept in a trace.
---

- [Workflows](/reference/workflows/#turning-them-on) (beta): Workflows kept in the app's database, each changed definition checked and kept as a version, run on the app's own jobs.
- [Workflow language](/reference/workflows/#the-document) (beta): The States Language with JSONata expressions, every value read by name, so a model writes and edits it as a small, local change.
- [Checked on save](/reference/workflows/#reading-values-by-name) (beta): A definition that does not fit the language, has an edge to no step, reads a value nothing gives or leaves out an argument its step type needs is refused, naming the step and the field.
- [Workflow editor](/reference/workflows/#the-editor) (beta): The admin app draws a workflow as a graph that lays itself out around the nodes you move, to add, connect and remove steps of every trigger and step type of the app, its plugins' included, each with a form for its input beside the graph, with every problem the save would refuse shown on its step as it is edited.
- [One page per workflow](/reference/workflows/#the-workflows-page) (beta): A workflow's focus page is its graph, with Add step, Test run, Runs and Publish beside it in a panel, so you build, test and debug without leaving it; in the sidebar, Workflows lists the workflows.
- [Pins and wires](/reference/workflows/#the-workflows-page) (beta): A step's inputs and the values it gives are pins coloured by type; drag an output pin to an input to read that value there, and a wire that does not fit is refused, saying why.
- [Break and Make](/reference/workflows/#the-workflows-page) (beta): Take an object apart into a pin for each field, such as a record's fields, or build one from a pin per field, with no extra step to run.
- [Condition nodes](/reference/workflows/#the-workflows-page) (beta): In data order, build when a step runs from Equals, Not equals, Greater, Less and Matches, All of, Any of and Not on the graph, or drop a step's status on another step's Only when pin to run it once the first succeeded; any other condition is one Expression node, kept as you wrote it.
- [Select](/reference/workflows/#the-workflows-page) (beta): Choose an argument by another value on the graph, such as a mail's address by a form's topic, a value per case and one otherwise.
- [Move nodes by hand](/reference/workflows/#the-workflows-page) (beta): Drag a node of the graph where you want it; it stays there, marked, for everyone who edits the workflow, and the rest lays itself out around it until you unpin it or tidy up. Pins and Simple each keep their own places, and moving nodes makes no new version.
- [Pins or Simple](/reference/workflows/#the-workflows-page) (beta): Draw the graph with every pin and wire, or with only the steps and the lines between them, and switch at any time; nothing saved changes.
- [Build on the graph](/reference/workflows/#the-workflows-page) (beta): Click a step's handle to add a step right there, or drag from it to another step to connect them; the wheel and a pinch zoom the graph, and dragging pans it.
- [Branches, steps per item and retries](/reference/workflows/#states) (beta): Choices, a step per item with their results merged, waits, and per-step retries, timeouts and error paths.
- [Order from the data](/reference/workflows/#execution-order-from-the-data) (beta): A workflow in data order runs each step once the steps it reads from have ended, steps that read nothing of each other at once, with a Condition on any step and skips that pass on; switch a workflow between data order and the States Language's own sequence in the editor.
- [Waiting for an outside result](/reference/workflows/#waiting-for-an-outside-result) (beta): A step hands its work off with a token and the run waits, holding nothing, until an approver, a job elsewhere or a service sends the token back with a result, a failure or a heartbeat, through the app's API or over MCP, failing with `States.Timeout` or `States.HeartbeatTimeout` when it does not come in time.
- [HTTP request step](/reference/workflows/#apphttp) (beta): Calls a URL built at run time through the outgoing-address guard, only at public addresses unless the config allows private ones, reading at most 10 MiB of the answer as JSON, text or a file, by its Content-Type unless the step says which. It can send its body as JSON whatever it holds, and check the answer's body against a JSON Schema, whose fields the editor then offers.
- [Records steps](/reference/workflows/#apprecords) (beta): Create, update, get and list records as the workflow's last editor, with the roles they hold now.
- [Mail step](/reference/workflows/#appmailsend) (beta): Sends mail, with files the run downloaded attached, from the app's own sender.
- [Send email step](/reference/workflows/#appmailtemplate) (beta): Sends one of the app's email templates in a language of its own, with a pin for each field of the template's data, checked before it is sent.
- [Email series](/reference/workflows/#email-series) (beta): Mail steps that share a series' name, with waits between them, send each person a timed series, such as after sign-up; the series is a mail category of its own with one-click unsubscribe in every mail, and an unsubscribe stops the rest of the series for that person.
- [Storing files](/reference/workflows/#storing-files) (beta): The HTTP request step streams an answer of any size into a named storage configuration, an S3-compatible bucket, a file share or a local directory, past its 10 MiB read limit; later steps pass the stored file on or read it back, up to 10 MiB. Changing where a configuration points leaves the workflows that use it unchanged.
- [Runs and their traces](/reference/workflows/#traces) (beta): Each run started by hand through the API, from the app's code or by a trigger keeps every step's input, output, logs, timing, tries and error as a JSONL trace in the app's private file storage, whole by the time the run is marked ended, secrets blanked out; every run, only failing ones, or none, set by the app, the workflow or the run.
- [Run debugger](/reference/workflows/#following-and-debugging-a-run) (beta): Each workflow lists its runs with their status, who started them, when and for how long; a run chosen there marks every step's status on the graph of the version it ran on from its trace, and a run's own address shows it on the latest version, with the way to the one it ran on, live while it runs, with each step's input, output, logs, timing, tries and error, secrets blanked out.
- [Run status](/reference/workflows/#run-status) (beta): The sidebar lists your workflows under Workflows, each marked by how its last 10 ended runs went, red, orange, green or gray, in a shape of its own; a workflow's page says why in words, links to the run, and offers Mark as resolved.
- [Save, test, then publish](/reference/workflows/#the-workflows-page) (beta): A save makes a version and changes nothing that is live; publishing puts a saved version live, warning when it has no test run, and puts an older one back.
- [Use a run's data](/reference/workflows/#the-workflows-page) (beta): Read each step's input and output beside its form, start a test run from the run's input or any step's output, and insert an earlier step's value into a field from a real run's samples.
- [Re-run from a step](/reference/workflows/#re-running-a-failed-run) (beta): After you fix the workflow, a failed run resumes from its last checkpoint, so no write with a saved checkpoint happens again. If a run kept its trace, you can re-run it from any step it reached, except one inside For each. Earlier steps keep their results. From the chosen step on, anything the steps send goes out again. On the workflow's page, you can start a test run with a sample input.
- [Replay a run](/reference/workflows/#replaying-a-run) (beta): replay a finished run on your workflow as it is now, with the same input. Steps that write are held back and give what the run's trace says they gave, and reads come from the step cache or run again, so you can try a change on the same data without sending anything again.
- [Runs that survive restarts](/reference/workflows/#how-a-run-is-run) (beta): A run takes up where it stood after a restart or a crashed worker from checkpoints that hold only what it needs to go on, never repeating a write whose checkpoint was saved, and every limit fails closed.
- [Same values after a crash](/reference/workflows/#reading-values-by-name) (beta): `$now`, `$millis`, `$random` and `$shuffle` give a step the same values when a crash makes it run again, new ones on each retry, and each Map item its own; a recorded Task fetched again after a crash gives the time of that fetch.
- [Values kept up to 256 KiB](/reference/workflows/#how-a-run-is-run) (beta): A run's input and each value a step keeps are at most 256 KiB as JSON; a larger one fails with its size, so large data goes to a store and the run passes a reference.
- [Who may run workflows](/reference/workflows/#who-may-do-what) (beta): Making, changing and running workflows and reading their runs are each granted by name, within the tenant.
- [Workflows over MCP](/reference/mcp/#workflows) (beta): AI clients find, write, validate, change by a small edit and test-run workflows as the signed-in person, and read each step of a run to fix the one that failed and re-run it from there.
- [Record triggers](/reference/workflows/#apprecord) (beta): A workflow starts once for each record that becomes ready, at once or when a time in it comes, read as the user who saved the enabled version.
- [Triggers turned on while the app runs](/reference/workflows/#turning-a-trigger-on) (beta): Publishing a saved version registers its trigger on every server process, and turning the workflow off stops it, with no restart; a save goes live only once it is published.
- [Workflow plugins](/reference/workflow-plugins/) (beta): A file of the app or a package adds trigger and step types through the same public interface the built-in types use.
- [Custom workflow steps](/reference/workflows/#custom-workflow-steps) (in development): Keep a step type of your own as a record, a container built from a Dockerfile with its input and output as JSON Schema, each saved version a step type a workflow names and is checked against; a run hands it to one of your runners, which builds its image and runs it in a container with no network, taking and giving files through your storage configurations.
- [Runners](/reference/workflows/#runners) (in development): Install a runner on a Linux machine with one command and a one-time token, copied from its page; it claims your custom steps' jobs over HTTP and runs each in a hardened Docker or Podman container, each job placed with the runner that has its image, waiting a moment for one; revoking a runner puts its jobs back in the queue.
- [Custom step builds](/reference/workflows/#builds) (in development): Each runner builds the images of the custom step versions it runs from their Dockerfiles, listed on each version's page, and builds a custom step's new version as you save it and those of a workflow as you publish it, so its first run finds them ready.
- [Testing a custom step](/reference/workflows/#testing-a-custom-step) (in development): Run one job of a custom step version on a sample input without a workflow, and read its output, or its error with the end of its log.
- [Custom steps over MCP](/reference/mcp/#workflows) (in development): An AI client saves a custom step, waits for its build, tests it on a sample file, lists the runners and makes one with its install command, each write after your approval.
- [From a Dockerfile to a workflow](/reference/workflows/#from-a-dockerfile-to-a-workflow) (in development): Make a runner, save a custom step, wait for its build, test it and use it in a workflow, in the admin app or over MCP.
- [Blocks](/reference/workflows/#blocks) (beta): build your own step from other steps. A block runs once and is cached by what it reads, so a workflow that reaches it again, in this run or another, reuses its result, such as a file fetched from a link that expires.
- [Step cache](/reference/workflow-plugins/#caching-results) (beta): A plugin's step reuses the result of an identical earlier call from any run or workflow, as its plugin decides, while secrets always come in with their current value; a workflow can force it on, and the graph marks a step forced on against its plugin's advice.
- [Guarded requests for plugins](/reference/workflow-plugins/#sending-requests) (beta): A plugin's requests reach only public addresses, follow no redirect and read at most 10 MiB.
- [Webhook trigger](/reference/workflows/#appwebhook) (beta): A workflow starts from a signed call to a URL of its own, limited in size and rate; one call creates it, publishes it and issues its URL.
- [Polling triggers](/reference/workflow-plugins/#polling-and-webhook) (beta): A workflow starts once for each new item a plugin finds on a schedule, or at each time of a cron with `app:schedule`.
- [Incoming Gmail mail](/reference/workflow-plugins/#incoming-gmail-mail) (beta): A workflow starts once for each new mail on a label of a connected Gmail mailbox that passes optional sender, recipient and subject filters, read with read-only access within about a minute.
- [Connected accounts](/reference/workflows/#connecting-an-account) (beta): People connect their own accounts at other services through OAuth from the account page, see which workflows use each one, and MCP clients list them to bind. A workflow's steps and triggers sign in with one only once its owner turned the workflow on, with tokens encrypted and refreshed. Disconnecting deletes the token and revokes it at a provider that has a revocation endpoint, trying again for a few hours when the provider does not take it, and says which it did.
